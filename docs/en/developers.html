Developers

Set up localmelo for development, run the tests and checks, add a backend, a built-in tool or a check, and send a change.

The repository

  • The folder that holds pyproject.toml is the localmelo package itself; there is no localmelo/localmelo/.
  • melo/agent/agent.py is imported as localmelo.melo.agent.agent; keep the clone named localmelo.
  • melo/ is the core: the run loop, the checks, the executor, memory and the provider contracts.
  • support/ is everything around it: the backends and model providers, the gateway, the terminal UI, MCP, configuration and the setup wizard.
  • tests/ mirrors the two. docs/ holds the Markdown pages and the website.

The core does not import support/. The one bridge is Agent(config=...).

  • tests/test_layering.py fails on any import of support/ under melo/: plain, relative or through importlib.
  • It allows two: Config for type checking, and get_backend inside _providers_from_config.
  • prompt_toolkit and rich stay out of the core and the backends; sessions and the terminal UI stay clear of the gateway.
  • Need code from support/ in the core? Push a contract into melo/contracts/.

Set up

You need Python 3.11 or later, Git and uv; Node (the version in .nvmrc) only for the console's JavaScript tests.

  • uv builds .venv/ from uv.lock, with Python 3.13 from .python-version; localmelo supports 3.11 or later.
  • --extra dev adds pytest, ruff, black, mypy and pre-commit; --extra gateway adds FastAPI and uvicorn.
  • uv run pre-commit install adds hooks that run ruff, black, mypy and the whole suite on every commit.

Run the CLI

melo lands in .venv/bin/, not on your PATH. Inside the clone, run it through uv:

  • Elsewhere, name the checkout: uv run --project DIR melo ….
  • A run needs a model server: pass -u http://127.0.0.1:11434/v1 -m qwen3:8b, or run uv run melo setup once.
  • Point HOME at a temporary folder so a run never touches your own ~/.cache/localmelo.

Tests

While you work, run only the tests your change affects; pytest-testmon picks them:

Before you send a pull request, run the whole offline suite once, in parallel:

  • The suite needs no model server and sends no request to one; a few CLI tests serve a fake API on loopback.
  • To run one folder, name it: uv run pytest tests/agent -q.
  • Every test runs with HOME in a temporary folder; one that writes the real ~/.cache/localmelo fails.
  • A test that genuinely needs the real home is marked @pytest.mark.allow_real_cache.

Lint and types

Black formats at 88 columns. Ruff selects E, W, F, I, N, UP, B and SIM; E501 is left to black. Mypy requires an annotation on every function (disallow_untyped_defs), checks untyped function bodies, and exempts __main__.py. The same three run from pre-commit.

Add a backend

Backends are pure connectors: they validate configuration and build provider objects, and never start or serve a model. To add one:

  1. Write a class in support/backends/local/ or support/backends/cloud/ that implements BaseBackend (support/backends/base.py): key, display_name, validate, validate_embedding, has_embedding, build_chat_provider and build_embedding_provider. Most servers share the OpenAI-compatible code in support/backends/openai_compat.py.
  2. Register it in ensure_defaults_registered() in support/backends/registry.py.
  3. Add its key to VALID_CHAT_BACKENDS in support/config.py, and to VALID_EMBEDDING_BACKENDS if it serves embeddings.
  4. Give it a config table: a field on Config and its name in _LOCAL_SECTIONS or _CLOUD_SECTIONS, so that load() and save() handle it. When you change the schema, add a migration in load() rather than break existing config files.
  5. Add it to the setup wizard in support/onboard.py: CHAT_BACKENDS, EMBEDDING_BACKENDS, the defaults (_LOCAL_DEFAULTS, _CLOUD_DEFAULTS or _EMBEDDING_DEFAULTS) and _CHAT_SETUP.
  6. Add tests in tests/backends/. Mock the connectivity probes: never let a test contact a real server.
  7. Document it: the backend table and an example in docs/configuration.md.

Add a built-in tool

A built-in is a ToolDef (a name, a description, JSON parameters and semantic tags) and an async function that returns text. Both live in melo/executor/builtins.py, and the _builtin() decorator adds the pair to BUILTINS. register_builtins() in melo/executor/__init__.py registers every one with the executor and the memory's tool registry, and marks the tools whose permission tier is not read as requiring approval.

  1. Add the ToolDef and the function in melo/executor/builtins.py, decorated with @_builtin(...). The semantic tags are terms the BM25 search matches a task against. Every registered built-in is offered in every step; among the other, provided tools, retrieve mode offers the ones the model has already called and the three best matches for the task.
  2. Give it a permission tier: add its name to BUILTIN_TIERS in melo/checker/tiers.py (read, write, exec or network). A test keeps that table equal to the built-in names, so a new built-in cannot be added without one. A run with an approval policy asks before every call whose tier is not read; APPROVAL_BUILTINS is derived from the table.
  3. If it needs a workspace root, add its rooted variant to rooted_builtins() in the same file. A tool that starts a child process appends its status to TOOL_EXIT_CODE, so tool.finished carries exit_code.
  4. Add tests in tests/executor/.
  5. Document it in docs/tools.md, and in docs/for-agents.md and docs/llms.txt when an agent has to know it.

Add a check

The checker validates at every boundary. A failed check is control flow, not an exception: it returns allowed=False with a reason, and the agent replans or reflects. A structured boundary is three pieces and one call site:

  1. A payload dataclass in melo/checker/payloads.py.
  2. A validator in melo/checker/validators.py that returns a ValidationResult.
  3. A method on Checker in melo/checker/checker.py that calls the validator.
  4. The call site, routed through that method.

The Checker's own checkpoints, pre_plan, post_plan and pre_execute, return a CheckResult instead. The existing boundaries are the gateway ingress, session transitions, tool resolution, executor results, memory writes, the planning prompt and the tool-call shape. Add tests in tests/checker/, naming the refused input and the reason.

Commits and pull requests

  • Write the commit subject as [Area] Imperative summary, as in [Agent] Sort the retrieved extra tools by name. Areas include CLI, Agent, Executor, Memory, Tests, Docs, Gateway, Backends, Sessions and Scheduler.
  • Pull request titles add the type, as in [Feature][CLI] … or [Bug][Memory] ….
  • Keep one focused change per pull request. For a larger change, open an issue first; the roadmap is the roadmap issue.
  • A behaviour change needs tests. Never weaken or delete an existing test to make a change pass; say in the pull request why a test had to change.
  • Change the docs in the same pull request: the English page, the Chinese twins (README.zh-CN.md and docs/zh-CN/), docs/for-agents.md and docs/llms.txt for behaviour agents rely on, and a CHANGELOG.md entry under Unreleased with the pull request's number, as ([#NN]), and its link at the bottom of the file.
  • A change to what melo draws in a terminal, or to the website, comes with screenshots in the pull request.
  • Write the code, the comments, the tests and the documentation in English.

Docs and the website

  • GitHub Pages publishes the docs/ folder of main; the website pages are in docs/en/ and docs/zh-CN/.
  • An English page and its Chinese twin share ids, sections, order, code and pictures.
  • Website pages and the READMEs follow Pages people read: short points, pictures first, no PR numbers.
  • Pictures go in docs/assets/img/ as WebP, at most 1280 pixels wide.
  • A page in docs/ links outside it with absolute github.com URLs.

A new Markdown page goes into the index in docs/README.md; Maintaining the docs has the layout and the glossary.
