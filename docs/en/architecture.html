Components

What each component does today, and where its code lives. Paths are relative to the repository root.

Command line

The melo command. Given a task, it runs in direct mode: it builds one agent, runs the task, prints the result as text or as one JSON line, and exits with a code that tells how the run ended. Without a task, in a terminal, it opens the interactive UI: an input box and a status bar stay at the bottom, and each turn prints into the scrollback as it runs, with a block for each tool call, a spinner with the step and the time, and the answer as Markdown. The UI runs its turns on a session (stored in ~/.cache/localmelo/cli/sessions.db), asks in a panel before shell_exec, python_exec and file_write run, keeps the file tools in its workspace, and saves the model and server that /model and /backend pick to the config file (a session opened with --base-url saves nothing). Without a terminal, bare melo exits with code 2. An empty task (melo "") opens the plain conversation loop, where each turn sees the earlier answers. --serve starts the gateway; --daemon manages the macOS background service. With --base-url, the agent talks to that server and the config file is not read; without it, the configured backends are used. --chat-model and --request-timeout set the chat model and the chat request timeout in both cases, and never change the config file.

Key files: __main__.py; the UI in support/cli/: launch.py (the terminal check, the workspace and the model server), app.py (the input box and the keys), session.py (turns and commands), render.py (tool blocks, the spinner and answers) and approvals.py; and support/sessions/agents.py.

Gateway

The HTTP server that melo --serve starts. It serves the HTTP API (/v1/health, /v1/agent/run, /v1/sessions) and keeps up to 50 sessions, each with its own agent built from the config file. A session's agent keeps its answers, so each request sees the earlier ones. It checks each request, the task's length and the session id, before a run.

At / it serves the web workspace, which does not read the config file: it lists the models of a server whose URL you enter, and keeps up to 12 chats of its own, with search, a draft for each chat, and Stop, which ends the run as cancelled. Each chat has its own agent, with the four built-in tools and its own working memory. All chats save to one history and, with an embedding model, one long-term memory, in ~/.cache/localmelo/playground/. Chats last while the gateway runs, but creating a chat closes those idle for 2 hours and, at 12 chats, replaces the oldest idle one.

The gateway has no authentication. When it listens on localhost or a loopback address, such as the default 127.0.0.1:8401, it refuses requests whose Host is not 127.0.0.1, localhost or [::1] with its port (HTTP 421), and requests to its API that web pages at another origin send through your browser (HTTP 403). No web page can show it in a frame. On any other host, such as 0.0.0.0, it makes none of these checks and logs a warning when it starts.

Key files: support/gateway/__init__.py, session.py, guard.py (the Host and Origin checks), webapp.py and playground.py (the web workspace's routes and chats), static/ (its page), and daemon.py for the macOS background service.

MCP servers

Local servers that speak the Model Context Protocol over stdio, listed in the JSON file that --mcp-config names. At the start of the first run, support/mcp starts each server, lists its tools and registers them, as mcp__<server>__<tool>, with the tool registry and the executor. MCP tools work in direct mode and the Python API, not in gateway sessions or the interactive UI. A server's require_approval makes calls of its tools, or of the tools it names, ask the run's approval policy first; a run without a policy, such as a direct run, runs them without asking.

Key files: support/mcp/config.py, client.py, provider.py, and the tool provider interface in melo/contracts/tools.py.

Agent

The run loop. Each step builds a prompt from the task, working memory, recalled long-term memory and the latest reflection, offers the model a list of tools, sends one planning request, and runs the tool calls of the reply. A reply with text and no tool call is the answer, and the run ends as completed. With the default reflect policy, steps come in attempts of up to 10; after an attempt that ends without an answer, a reflection decides whether another attempt starts. Every run ends with one of nine statuses, or as cancelled when an interactive run (below) is stopped, and returns a RunResult. A failed model request is retried up to twice when a retry may succeed.

Python code that calls run_task can follow and steer a run. With on_event, it receives each step, model reply, tool call, notice and reflection as an event, with secrets in the model's text redacted. With approval, a policy decides whether each call of a tool that requires approval may run. A run with either one is interactive: cancelling it ends it as cancelled and closes the interrupted step. With AgentOptions(record_answers=True), working memory keeps each run's answer, and conversation() and load_conversation() carry a conversation to another agent. Direct mode and the HTTP API pass no event sink and no policy. The web workspace passes an event sink, so its Stop ends a run as cancelled.

Key files: melo/agent/agent.py, melo/agent/options.py (AgentOptions), melo/agent/_chat.py (planning and reflection requests, retries), melo/agent/_events.py and melo/contracts/events.py (events), melo/contracts/approvals.py (approval policies), melo/schema.py (RunResult and the limits).

Checker

The checks at each boundary of a run:

  • before a planning request: the prompt may hold at most 100,000 characters, and the list of offered tools must be valid;
  • after it: each tool call in the reply needs a name and an id of its own;
  • before a tool runs: shell_exec refuses six destructive command patterns;
  • after a tool runs: output longer than 50,000 characters is cut;
  • before a memory write: its size is limited;
  • before an event reaches Python code: API keys of well-known shapes, bearer tokens and one-time codes in a model reply's text are replaced with [redacted];
  • in the gateway: each request's task and session id.

A failed check before or after a planning request ends the run as failed. A refused tool call does not run: the model sees the refusal as the tool's error.

Key files: melo/checker/checker.py, validators.py, payloads.py, redaction.py.

Executor

Runs the tool calls of a step, in order. A call is refused when the step did not offer the tool, when its arguments are not a JSON object, or when an argument of a built-in tool has the wrong type; the checker then sees every call that is left. With a workspace root, the workspace policy then resolves the path of a file tool and refuses one outside the root. With an approval policy, a call of a tool that requires approval then waits for the policy's decision, and once it is allowed, a file path under a workspace root is resolved again and refused if it changed in the meantime. Each tool runs with a time limit, which starts after the approval: shell_exec 30 seconds, file_read and file_write 60 seconds, an MCP tool its server's timeout. In the interactive UI, shell_exec and python_exec get 10 minutes. python_exec code always runs in a child process, which a time limit or a cancellation kills, in the current directory without a workspace root and in the root with one. A refusal, a denial, a time-out or an error comes back as the tool's error.

The four built-in tools are shell_exec, python_exec, file_read and file_write. Direct mode and the gateway give them no workspace root, so file tools reach any file you can. In the Python API, AgentOptions(workspace_root=…) turns policy.py on: the file tools then reach only files inside the root, and shell_exec and python_exec run there in a child process, without that limit. Approvals apply only to a run with an approval policy.

Key files: melo/executor/executor.py, builtins.py, policy.py, melo/contracts/approvals.py.

Memory

Working memory holds the conversation of a run or a gateway session: the last 20 messages, in RAM. History records every task and step and, with persistence on, every model call and its reasoning. Long-term memory needs an embedding backend: it stores step summaries and reflections with their embeddings, and recalls the 5 closest entries on each step. Procedural memory keeps the steps of each run and learns the steps of tasks you repeat. History, long-term and procedural memory stay in RAM, or go to history.db, long_term.db and procedures.db when persistence is on. The tool registry holds every registered tool, with the BM25 index that retrieve mode searches.

melo/memory/retrieval/ holds three switchable retrievers, bm25, llm and embedding. They search documents built from a run's model calls: the notes on the model's reasoning, code drafts and chunks of its thinking that melo/memory/notes.py builds from a model reply, and reflections. Runs do not use them yet: the melo-retrieve command (support/retrieve.py) compares them offline on labelled queries, and turns model calls recorded as raw-call JSONL into a corpus. With persistence on, the history.db that melo writes records model calls too, and melo-retrieve exports it as well. See Offline retrieval.

Sessions (experimental) keep whole conversations in sessions.db: each turn is a stored row that ends exactly once with a status and a cause, the session's events are stored with it, and a window checkpoint lets a fresh agent resume where the last one stopped. The gateway's file and the terminal's file are separate. The interactive UI runs its turns on sessions, though it cannot resume one yet; the gateway does not use them (code: support/sessions/). See Sessions.

Key files: melo/memory/coordinator.py, short/ (working memory), history/, long/, tools/ (the tool registry), bm25.py.

Memory design (planned): the memory design page keeps the maintainer's design for memory, parts of which are not built yet.

Config and setup

~/.cache/localmelo/config.toml names the chat and embedding backends and their settings. On a first run in a terminal, melo finds a model server with GET /v1/models, asks for its URL and model and saves them. The setup wizard (melo --reconfigure) asks for every backend, sends a test request to each server, saves the file, then opens the interactive UI, or with --serve starts the gateway. Direct mode and the gateway build their agents from this file.

Key files: support/config.py, support/onboard.py, support/onboard_probe.py, support/backends/discovery.py.

Providers

The HTTP clients for model servers: OpenAI-compatible chat (/chat/completions), Ollama's own /api/chat, and OpenAI-compatible embeddings. They implement the interfaces in melo/contracts/providers.py, apply the chat request timeout, and report each failed request as a ProviderError that says whether a retry may succeed.

Key files: melo/contracts/providers.py, support/providers/llm/, support/providers/embedding/.

Backends

One adapter for each backend key: mlc, ollama, vllm and sglang for servers you run, and openai, anthropic, gemini and nvidia for cloud APIs. Each adapter checks its table of the config file and builds the providers. Backends only connect: you start and stop the model servers yourself.

Key files: support/backends/registry.py, base.py, local/, cloud/.

melo/sleep/, melo/memory/personalized/ and support/melo_serving/ hold code that the agent does not use yet. melo/memory/retrieval/ and melo/memory/notes.py serve only melo-retrieve, and support/scheduler/, the scheduling policy core and its simulator, only its tests.

Boundaries

BoundaryRuleWhy it matters
melo/ and support/ melo/ holds the agent and the interfaces that providers implement, and does not import support/ at module level. The one bridge is Agent(config=…), which builds its providers through support/backends when it is called. The agent runs with providers you build yourself, such as test fakes, and a new backend changes only support/.
Agent and executor A step runs only the tools it offered, and every call passes the checks first. The checks are guardrails, not a sandbox: tools run with your account's permissions. The model can call only what the step showed it, and a refused call never runs.
Agent and memory Memory writes pass the checker's size limits. Long-term memory is written only when an embedding backend is configured and memory is on. The prompt and the stores stay bounded.
Backends and model servers Backends only connect to a URL. localmelo does not download, start or serve models. You keep control of your model servers.

What exists today

  • Direct mode with run options, nine run statuses, text or JSON output, and fixed exit codes.
  • The interactive UI in the terminal (bare melo, support/cli/): live tool blocks and a spinner, approvals, / commands with completion, /model and /backend; and the plain conversation loop (melo "").
  • Four built-in tools, and tools from local MCP servers in direct mode and the Python API.
  • The Python API (experimental): run events, stopping a run, approval policies for tool calls, a workspace root for the file tools, and conversations that carry over between runs.
  • Sessions (experimental): conversations kept in SQLite whose turns each end exactly once, survive a restart and resume on a fresh agent (support/sessions/). The interactive UI keeps its turns in them; the gateway does not use them yet.
  • The gateway: the HTTP API, sessions, the web workspace, checks that, on a loopback host, refuse requests from other sites, and a macOS background service.
  • Backends for Ollama, MLC LLM, vLLM, SGLang and four cloud APIs.
  • Working memory, history and long-term memory, saved to SQLite when persistence is on; the saved history also keeps every model call with its reasoning, for 30 days by default.
  • melo-retrieve, which compares the bm25, llm and embedding memory retrievers offline. Runs do not use the retrievers yet.
  • Procedural memory: each run records its steps, and a completed run updates the step template of its task, in procedures.db with persistence on. Python callers get run.progress events with progress=True, without a percent bar for now. On a terminal, melo "<task>" draws them as a progress line on stderr (support/progress_line.py). melo-procedures replays the progress rules offline.
  • The scheduler's policy core and a simulator that tests it offline (support/scheduler/). Runs and the gateway do not use it yet.

What comes next is on the roadmap.
