Components

Each card says what a part does; its link opens the reference page.

Terminal

melo opens a chat; melo "task" runs one task.

  • Prints the answer, or one JSON line, and exits with a code that says how the run ended.
  • Asks before commands and file writes; file tools stay in the folder.
  • Runs its chats itself, without the gateway.
Command-line reference

Gateway

melo serve: the local server behind the console, the app and the HTTP API.

  • Serves the console's API v2 under /api and the HTTP API under /v1.
  • Requires a bearer token or browser session, and listens on loopback only.
  • A token holder can act as you; same-user processes are not isolated.
API v2 reference

Chats

Each chat is a session whose turns survive a restart.

  • A turn runs on the chat's own agent, one turn at a time.
  • Before a turn, memory adds what it recalls for it.
  • The chat you are in is the scheduler's focus; a main chat that hands work to tasks is planned.
Sessions reference

Scheduler

Orders tasks, and model calls when you turn its gate on.

  • A task queue with priorities P0 to P5, kept in the gateway's session file.
  • A gate on model calls: off by default, or first come first served, or by class.
  • Reads the shared GPU lock and the battery; can wait while the lock is held.
Scheduler guide

Workers

Headless sessions that run tasks without a chat window.

  • The gateway starts queued tasks by priority, a few at a time.
  • melo worker runs one from a brief file and returns a JSON result.
  • The console's Workers view lists every run.
Worker reference

Planner

The agent loop: plan a step, run its tools, reflect between attempts.

  • Each step's request holds the task, working memory, recalled memory and the last reflection.
  • The model calls only the tools the step offers.
  • A reflection decides whether the next attempt starts.
How it works

Checker

Checks each boundary of a run.

  • Checks each plan, tool call and tool result.
  • A refused call does not run; the model sees why.
  • Calls that send, delete or publish always ask, and say why.
What the checks do

Executor

Runs a step's tool calls in order, with time limits.

  • Built-in tools: shell_exec, python_exec, file_read, file_write and list_files.
  • Asks for approval by permission tier.
  • On macOS, worker runs and saved tasks write only in their workspace.
Tools reference

Tools: MCP and browser

More tools beside the built-ins.

  • Local MCP servers from --mcp PATH run as stdio processes.
  • Their tools are named mcp__<server>__<tool>.
  • With browsing on, melo reads pages in Safari's automation windows.
Tools and MCP guide

Memory

What melo keeps within a run and across chats.

  • Working memory: a run's recent messages, in RAM.
  • Notes about you and an index of every chat, recalled with their source.
  • History and long-term memory, in SQLite when persistence is on.
Memory concepts

Config and setup

One config file, and a first run that finds your server.

  • ~/.cache/localmelo/config.toml names the chat and embedding servers.
  • The first run looks for a model server and offers what it finds.
  • melo setup and melo config change it later.
Configuration reference

Providers

The HTTP clients that talk to model servers.

  • OpenAI-compatible chat, Ollama's /api/chat and OpenAI-compatible embeddings.
  • Apply the chat request timeout to every request.
Model servers guide

Model servers

Backends connect to servers you run or to cloud APIs.

  • oMLX (through vllm), Ollama, MLC LLM, vLLM and SGLang.
  • The OpenAI, Anthropic, Google and NVIDIA APIs.
  • localmelo never downloads, starts or serves a model.
