Components

What each component does today, and where its code lives. Paths are relative to the repository root.

Command line

The melo command. Given a task, it runs in direct mode: it builds one agent, runs the task, prints the result as text or as one JSON line, and exits with a code that tells how the run ended. Without a task it opens an interactive terminal conversation. --serve starts the gateway; --daemon manages the macOS background service. With --base-url, the agent talks to that server and the config file is not read.

Key files: __main__.py.

Gateway

The HTTP server that melo --serve starts. It serves the HTTP API (/v1/health, /v1/agent/run, /v1/sessions) and keeps up to 50 sessions, each with its own agent built from the config file. It checks each request, the task's length and the session id, before a run. At / it serves the web UI (playground), which keeps sessions of its own. The gateway has no authentication and listens on 127.0.0.1:8401 by default.

Key files: support/gateway/__init__.py, session.py, webapp.py, playground.py, and daemon.py for the macOS background service.

MCP servers

Local servers that speak the Model Context Protocol over stdio, listed in the JSON file that --mcp-config names. At the start of the first run, support/mcp starts each server, lists its tools and registers them, as mcp__<server>__<tool>, with the tool registry and the executor. MCP tools work in direct mode and the Python API, not in gateway sessions.

Key files: support/mcp/config.py, client.py, provider.py, and the tool provider interface in melo/contracts/tools.py.

Agent

The run loop. Each step builds a prompt from the task, working memory, recalled long-term memory and the latest reflection, offers the model a list of tools, sends one planning request, and runs the tool calls of the reply. A reply with text and no tool call is the answer, and the run ends as completed. With the default reflect policy, steps come in attempts of up to 10; after an attempt that ends without an answer, a reflection decides whether another attempt starts. Every run ends with one of nine statuses and returns a RunResult. A failed model request is retried up to twice when a retry may succeed.

Key files: melo/agent/agent.py, melo/agent/options.py (AgentOptions), melo/agent/_chat.py (planning and reflection requests, retries), melo/schema.py (RunResult and the limits).

Checker

The checks at each boundary of a run:

  • before a planning request: the prompt may hold at most 100,000 characters, and the list of offered tools must be valid;
  • after it: each tool call in the reply needs a name and an id of its own;
  • before a tool runs: shell_exec refuses six destructive command patterns;
  • after a tool runs: output longer than 50,000 characters is cut;
  • before a memory write: its size is limited;
  • in the gateway: each request's task and session id.

A failed check before or after a planning request ends the run as failed. A refused tool call does not run: the model sees the refusal as the tool's error.

Key files: melo/checker/checker.py, validators.py, payloads.py.

Executor

Runs the tool calls of a step, in order. A call is refused when the step did not offer the tool, when its arguments are not a JSON object, or when an argument of a built-in tool has the wrong type; the checker then sees every call that is left. Each tool runs with a time limit: shell_exec 30 seconds, file_read and file_write 60 seconds, an MCP tool its server's timeout. python_exec code runs inside localmelo and cannot be interrupted. A refusal, a time-out or an error comes back as the tool's error.

The four built-in tools are shell_exec, python_exec, file_read and file_write. policy.py can limit the file tools to one directory, but the agent does not turn it on: file tools reach any file you can.

Key files: melo/executor/executor.py, builtins.py, policy.py.

Memory

Working memory holds the conversation of a run or a gateway session: the last 20 messages, in RAM. History records every task and step. Long-term memory needs an embedding backend: it stores step summaries and reflections with their embeddings, and recalls the 5 closest entries on each step. History and long-term memory stay in RAM, or go to history.db and long_term.db when persistence is on. The tool registry holds every registered tool, with the BM25 index that retrieve mode searches.

Key files: melo/memory/coordinator.py, short/ (working memory), history/, long/, tools/ (the tool registry), bm25.py.

Memory design (planned): the memory design page keeps the maintainer's design for memory, parts of which are not built yet.

Config and setup

~/.cache/localmelo/config.toml names the chat and embedding backends and their settings. The setup wizard (melo --serve --reconfigure) asks for them, sends a test request to each server, saves the file and starts the gateway. Direct mode and the gateway build their agents from this file.

Key files: support/config.py, support/onboard.py, support/onboard_probe.py.

Providers

The HTTP clients for model servers: OpenAI-compatible chat (/chat/completions), Ollama's own /api/chat, and OpenAI-compatible embeddings. They implement the interfaces in melo/contracts/providers.py, apply the chat request timeout, and report each failed request as a ProviderError that says whether a retry may succeed.

Key files: melo/contracts/providers.py, support/providers/llm/, support/providers/embedding/.

Backends

One adapter for each backend key: mlc, ollama, vllm and sglang for servers you run, and openai, anthropic, gemini and nvidia for cloud APIs. Each adapter checks its table of the config file and builds the providers. Backends only connect: you start and stop the model servers yourself.

Key files: support/backends/registry.py, base.py, local/, cloud/.

melo/sleep/, melo/memory/personalized/ and support/melo_serving/ hold code that the agent does not use yet.

Boundaries

BoundaryRuleWhy it matters
melo/ and support/ melo/ holds the agent and the interfaces that providers implement, and does not import support/ at module level. The one bridge is Agent(config=…), which builds its providers through support/backends when it is called. The agent runs with providers you build yourself, such as test fakes, and a new backend changes only support/.
Agent and executor A step runs only the tools it offered, and every call passes the checks first. The checks are guardrails, not a sandbox: tools run with your account's permissions. The model can call only what the step showed it, and a refused call never runs.
Agent and memory Memory writes pass the checker's size limits. Long-term memory is written only when an embedding backend is configured and memory is on. The prompt and the stores stay bounded.
Backends and model servers Backends only connect to a URL. localmelo does not download, start or serve models. You keep control of your model servers.

What exists today

  • Direct mode with run options, nine run statuses, text or JSON output, and fixed exit codes.
  • Four built-in tools, and tools from local MCP servers in direct mode and the Python API.
  • The gateway: the HTTP API, sessions, the web UI and a macOS background service.
  • Backends for Ollama, MLC LLM, vLLM, SGLang and four cloud APIs.
  • Working memory, history and long-term memory, saved to SQLite when persistence is on.

What comes next is on the roadmap.
