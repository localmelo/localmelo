Components

What each component does today, and where its code lives. Paths are relative to the repository root.

Command line

The melo command. Given a task, it runs in direct mode: it builds one agent, runs the task, prints the result as text or as one JSON line, and exits with a code that tells how the run ended. Without a task, in a terminal, it opens the interactive UI: an input box and a status bar stay at the bottom, and each turn prints into the scrollback as it runs: the model's thinking, a block for each tool call, retries, notices and reflections, with the answer as Markdown and, when the turn wrote files, a line under its footer that names them. A live area above the input box shows what melo is doing, the time, the tokens and the running tool; developer mode adds the step, the phase and the run's progress facts. On a session's first turn (every turn in developer mode) it shows the past runs the progress line would show. The UI runs its turns on a session (stored in ~/.cache/localmelo/cli/sessions.db), resumes a saved chat in its workspace with melo -c or melo -r (/sessions and /resume open the same picker), asks in a panel before shell_exec, python_exec and file_write run, keeps the file tools in its workspace, and saves the model and server that /model and /backend pick to the config file (a session opened with -u saves nothing). It also names, undoes, inspects and copies the conversation with /title, /undo, /usage, /memory and /copy. Without a terminal, bare melo exits with code 2. An empty task (melo "") opens the plain conversation loop, where each turn sees the earlier answers. melo serve starts the gateway; melo serve install, uninstall and status manage the macOS background service. With -u (--url), the agent talks to that server and the config file is not read; without it, the configured backends are used. -m (--model) and --request-timeout set the chat model and the chat request timeout in both cases, and never change the config file.

Key files: __main__.py; the UI in support/cli/: launch.py (the terminal check, the workspace and the model server), app.py (the input box and the keys), session.py (turns and commands), render.py (thinking, notices, reflections, tool blocks, the live rows and answers) and approvals.py; and support/sessions/agents.py.

Direct workers read a brief and an optional explicit inbox at planning boundaries, and report a versioned JSON result or NDJSON event stream. --inbox FILE is append-only; a complete UTF-8 line is inserted once per live run, a trailing partial line waits for its newline, and an instruction must fit the planning request before it is acknowledged. The file must sit outside the workspace, or the worker refuses it as setup_error before any model call, because the default file and Python tools could rewrite it. --inbox-fd N reads an inherited pipe instead; the worker makes it close-on-exec before tools start, so python, shell and MCP subprocesses get no copy and cannot write it, and the fd form is the one for untrusted tasks. Both forms are steering channels, not trust boundaries, and acknowledgement offsets mean live context insertion, not model receipt. After a valid brief, a worker that cannot start returns a startup_error result with the redacted cause; an event-output failure attempts transport_error, a broken output pipe exits 1, and a record without a final result is incomplete.

Direct runs are recorded as one-turn worker sessions by default (--no-save-session or [sessions] record_direct = false opts out); JSONL logs from another worker tool can be imported. The gateway reads worker history from the CLI file without allowing edits. The web workspace lists those runs with server-side filters and paging and opens each as a read-only view that reads an unfinished run once and then follows its event stream.

Gateway

melo-task is a separate authenticated loopback client for gateway tasks and their event streams, and never starts the gateway; it does not change direct runs. It creates a task from text, a brief file or stdin, lists and shows tasks, pauses, resumes, stops or reprioritizes one, and follows its events as one readable line each with reconnects on durable event IDs. --json gives versioned JSON, and the private token is read from its file rather than accepted as an argument.

The HTTP server that melo serve starts. It serves the HTTP API (/v1/health, /v1/agent/run, /v1/sessions) and keeps up to 50 sessions, each with its own agent built from the config file. A session's agent keeps its answers, so each request sees the earlier ones. It checks each request, the task's length and the session id, before a run.

Under /api/ it serves API v2, the web console's API: health, the sessions list and one session, a session's turns with their events, a Server-Sent Events stream, image blobs, submission lookups, and a session's tools, grants, memory and runs; and the writes that run a session — create it, with or without a first turn, start, retry and stop its turns, cancel a message by its key, answer an approval, rename or move it, and delete it. A console turn runs in the gateway process, one at a time, and its model calls pass the same scheduler gate a workspace chat's do. The console opens a session's agent on demand and resumes its conversation when an idle sweep or the open cap closed it, or when the gateway restarted. API v2 is served only on a loopback address, carries one error envelope and Cache-Control: no-store, and only grows. See API v2.

At / the web workspace uses the console's API v2 and persistent session store. It shows the turn's work and answer, settings, earlier turns, stopped or failed runs and approval cards when requests are present; a file write over an existing file shows a numbered diff of what it replaces. A details drawer shows tools, session grants, memory and runs; settings include connection testing and a browser-local theme. Console sessions use RememberingPolicy to ask before file_write and python_exec; legacy /v1 has no approval policy. Each chat uses the configured model and the built-in file_read, file_write, list_files and python_exec tools (no shell_exec). Model calls share the scheduler gate, and the header shows its GPU lock and battery readings. The page lists sessions newest first with search and per-chat drafts, displays tool work, folded reasoning, notices, progress and answers, and reopens its event stream from the last stored event. Sessions in ~/.cache/localmelo/gateway/sessions.db survive restart; agents open on demand (at most eight, closed after 15 minutes idle while their conversations are kept).

The gateway requires a bearer token or browser session and refuses non-loopback binds. At a terminal on this computer, melo serve opens the console in your browser, signed in with a one-use link, and melo console opens it again; over SSH it prints the link. A token holder can act as you; same-user processes are not isolated, and browser cookies are not isolated by localhost port.

Key files: support/gateway/__init__.py, session.py, guard.py (the Host and Origin checks), webapp.py and playground.py (the legacy /v1/playground routes and the chats behind them), console/ (the console's session store, its API v2 routes and the page's data), static/ (the page: workspace.js, turns.mjs and markdown.mjs), and daemon.py for the macOS background service.

MCP servers

Local servers that speak the Model Context Protocol over stdio, listed in the JSON file that --mcp-config names. At the start of the first run, support/mcp starts each server, lists its tools and registers them, as mcp__<server>__<tool>, with the tool registry and the executor. MCP tools work in direct mode, the Python API and the interactive UI (--mcp-config, else the config's mcp_config key); the gateway does not load them yet. A server's require_approval makes calls of its tools, or of the tools it names, ask the run's approval policy first; a run without a policy, such as a direct run, runs them without asking. Each server starts with the same minimal environment as a tool's child process, plus the env its entry names.

Key files: support/mcp/config.py, client.py, provider.py, and the tool provider interface in melo/contracts/tools.py.

Agent

The run loop. Each step builds a prompt from the task, working memory, recalled long-term memory and the latest reflection, offers the model a list of tools (in the default retrieve mode, the built-ins, the ones it has already called in this conversation and the three closest matches for the task), sends one planning request, and runs the tool calls of the reply. A reply with text and no tool call is the answer, and the run ends as completed, unless the reply is only unfinished thinking: the model is then asked once more, and a second such reply ends the run as failed (#288). With the default reflect policy, steps come in attempts of up to 10; after an attempt that ends without an answer, a reflection decides whether another attempt starts. Every run ends with one of ten statuses, or as cancelled when an interactive run (below) is stopped, and returns a RunResult. A failed model request is retried up to twice when a retry may succeed.

Python code that calls run_task can follow and steer a run. With on_event, it receives each step, model reply, tool call, notice and reflection as an event, with secrets in the model's text redacted. With approval, a policy decides whether each call of a tool that requires approval may run. A run with either one is interactive: cancelling it ends it as cancelled and closes the interrupted step. With AgentOptions(record_answers=True), working memory keeps each run's answer, and conversation() and load_conversation() carry a conversation to another agent. Direct mode and legacy /v1 pass no event sink and no policy. The web workspace passes an event sink and an approval policy, so its Stop ends a run as cancelled.

Key files: melo/agent/agent.py, melo/agent/options.py (AgentOptions), melo/agent/_chat.py (planning and reflection requests, retries), melo/agent/_events.py and melo/contracts/events.py (events), melo/contracts/approvals.py (approval policies), melo/schema.py (RunResult and the limits).

Checker

The checks at each boundary of a run:

  • before a planning request: the prompt may hold at most 100,000 characters, and the list of offered tools must be valid;
  • after it: each tool call in the reply needs a name and an id of its own;
  • before a tool runs: the tool's tier and the mode decide. The interactive UI offers shell_exec; direct, python and gateway do not offer it by default, and refuse an exec call registered anyway unless a direct or python caller named it in builtins; the gateway refuses it even when named. A run with an approval policy asks before a call whose tier is not read, and no command is refused by its spelling;
  • before the approval policy decides: each shell_exec, python_exec and file_write call is reviewed by fixed rules as routine, high-impact or undecided, and a session grant covers routine calls only (#290);
  • after a tool runs: output longer than 50,000 characters is cut;
  • before a memory write: its size is limited;
  • before an event reaches Python code: API keys of well-known shapes, bearer tokens and one-time codes in a model reply's text are replaced with [redacted];
  • in the gateway: each request's task and session id.

A failed check before or after a planning request ends the run as failed. A refused tool call does not run: the model sees the refusal as the tool's error.

Key files: melo/checker/checker.py, validators.py, payloads.py, redaction.py, review/ (the action review).

Executor

Runs the tool calls of a step, in order. A call is refused when the step did not offer the tool, when its arguments are not a JSON object, or when an argument of a built-in tool has the wrong type; the checker then sees every call that is left. With a workspace root, the workspace policy then resolves the path of a file tool and refuses one outside the root. With an approval policy, a call of a tool whose permission tier is not read, or that is marked as requiring approval, then waits for the policy's decision, and once it is allowed, a file path under a workspace root is resolved again and refused if it changed in the meantime. Each tool runs with a time limit, which starts after the approval: shell_exec 30 seconds, file_read and file_write 60 seconds, an MCP tool its server's timeout. In the interactive UI, shell_exec and python_exec get 10 minutes. A shell command's standard input is /dev/null, so it never reads the terminal. python_exec code always runs in a child process, which a time limit or a cancellation kills: in the current directory without a workspace root, in the root with one. The child of shell_exec or python_exec gets only PATH, HOME, USER, LOGNAME, SHELL, TERM, LANG, every LC_* variable and TMPDIR, plus AgentOptions(tool_env=…): an API key in melo's environment reaches no tool unless explicitly named in tool_env, and VIRTUAL_ENV, PYTHONPATH, SSH_AUTH_SOCK and the proxy variables pass only through tool_env. A refusal, a denial, a time-out or an error comes back as the tool's error.

The five built-in tools are shell_exec, python_exec, file_read, file_write and list_files. Only the interactive UI gets all five by default; the gateway and a console session get all but shell_exec; a direct run and the library's default python mode get file_read, file_write and python_exec. list_files only reads names and sizes, so it never asks. The other modes leave shell_exec out: direct and python mode have no approval policy, and the gateway's /v1 routes do not ask either; the console asks over API v2 and runs in the same gateway mode, so it gets no shell either (Python code can still start a process). --builtins all (or naming shell_exec) is a direct or python caller's opt-in; the gateway and console refuse it even when named. Direct mode and a /v1 gateway session give the tools no workspace root, so file tools reach any file you can; direct mode's --workspace DIR sets the same root as the Python API below, and a console chat gets [gateway] workspace (default ~/localmelo-workspace) as its root. In the Python API, AgentOptions(workspace_root=…) turns policy.py on: the file tools then reach only files inside the root, and shell_exec and python_exec run there in a child process, without that limit. Approvals apply only to a run with an approval policy.

On macOS, a worker run and a saved task start the commands of shell_exec and python_exec under a sandbox-exec profile that allows file writes only in the workspace and a short list of other places (#274); [agent] confine_direct_runs does the same for plain direct runs (#284). A provider can add a group of tools to every step: the eight browser tools, in the terminal chat and the console, while [browser] driver is safari-automation (#297).

Key files: melo/executor/executor.py, builtins.py, policy.py, sandbox.py, melo/contracts/approvals.py.

Memory

In compress modes, heuristic notes can extract up to 12 facts, including a bounded set of English negative and Chinese residence or cancellation statements, kept verbatim. Matching a negative assertion requires its full text in the record, and conflicting event times reject a match. Extraction and attribution are heuristic; similar assertions of opposite detected polarity are kept as conflicts, while structured supersession is off by default and available experimentally through Python. See reasoning notes.

Working memory holds the conversation of a run or a gateway session: the last 20 messages, in RAM. History records every task and step and, with persistence on, every model call and its reasoning. In legacy, long-term memory needs an embedding backend: it stores step summaries and reflections with their embeddings, and recalls the 5 closest entries on each step. In the compress modes it is a typed store instead: every entry has a kind (semantic, episodic, profile or reflection), a source, a status and the signal that admitted it, with its provenance beside the text and the vector, and one decision (NEW, UPDATE, RELATED, CONFLICT or IGNORE) is kept for each candidate; a candidate is admitted only by a rehearsal, a user request or statement, or --admit-on-outcome on for the final digest. Procedural memory keeps the steps of each run and learns the steps of tasks you repeat. History, long-term and procedural memory stay in RAM, or go to history.db, long_term.db and procedures.db when persistence is on. New files are created readable only by you (mode 0600). The text history and long-term memory keep is redacted before it is written: sk- keys, GitHub tokens, AWS access key ids, the token after Bearer and a one-time code next to its keyword, as events and model calls already were; the run, its requests and the model keep the text. The Python API can forget a task's history rows and the long-term reflections that name it with Hippo.forget(task_id), and empty history and long-term memory, step summaries included, with forget_all(). The tool registry holds every registered tool, with the BM25 index that retrieve mode searches.

In the compress and compress+replay reasoning modes, each reply becomes a short note (its plan, what it found, decided and left open, and what its tools returned) with its code drafts, kept in a RAM-only note store beside the working window and rehearsed into an attempt digest as later notes, calls and reflections use it. Every note, draft and digest passes the check_memory_candidate boundary (redact, sanitize, cap) before it reaches the window or the store. The compress modes recall them back: at start, attempt and step a delimited, data-framed block carries this task's notes, drafts and thought chunks and earlier tasks' long-term entries, chosen by --retriever auto|off|bm25|llm|embedding (embedding when configured, else llm at start and attempt and bm25 at step and tool, with bm25 as the fallback), placed by --recall-at and --recall-placement, checked and bounded; a thought chunk is recallable only after the turn that produced it left the window. history.db version 2 records each new block in recall_json, and the recall event carries its hits. See Reasoning notes and Recall in the loop.

melo/memory/retrieval/ holds three switchable retrievers, bm25, llm and embedding. They search documents built from a run's model calls: the notes on the model's reasoning, code drafts and chunks of its thinking that melo/memory/notes.py builds from a model reply, and reflections. The compress modes use them in the loop (see above), and the melo-retrieve command (support/retrieve.py) compares them offline on labelled queries, and turns model calls recorded as raw-call JSONL into a corpus. With persistence on, the history.db that melo writes records model calls too, and melo-retrieve exports it as well. See Offline retrieval.

Sessions (experimental) keep whole conversations in sessions.db: each turn is a stored row that ends exactly once with a status and a cause, the session's events are stored with it, and a window checkpoint lets a fresh agent resume where the last one stopped. A runner built with progress=True asks each turn's run for its run.progress events and stores them with the turn. The gateway's file and the terminal's file are separate. The interactive UI runs its turns on sessions and resumes a saved chat with melo -c or melo -r; the web console runs and reads its sessions in the gateway's own file, while its /v1 sessions stay in RAM (code: support/sessions/, support/gateway/console/). See Sessions.

Key files: melo/memory/coordinator.py, short/ (working memory), history/, long/, tools/ (the tool registry), bm25.py.

Memory design (planned): the memory design page keeps the maintainer's design for memory, parts of which are not built yet.

Config and setup

~/.cache/localmelo/config.toml names the chat and embedding backends and their settings. On a first run in a terminal, melo finds a model server with GET /v1/models, offers the one it finds (Use this model server?, a list), asks for a model and saves them, as the ollama backend for an Ollama server and as vllm for any other OpenAI-compatible server, oMLX included. With no server running it prints this computer's commands for starting one and looks again when you press Enter. When the server lists an embedding model, it offers one for long-term memory; the embedding guide covers Ollama, oMLX, vLLM, SGLang and MLC. The setup wizard (melo setup) asks for every backend, sends a test request to each server, saves the file, then opens the interactive UI, or with melo --serve --reconfigure starts the gateway. Direct mode and the gateway build their agents from this file.

Key files: support/config.py, support/onboard.py, support/onboard_probe.py, support/backends/discovery.py.

Providers

The HTTP clients for model servers: OpenAI-compatible chat (/chat/completions), Ollama's own /api/chat, and OpenAI-compatible embeddings. They implement the interfaces in melo/contracts/providers.py, apply the chat request timeout, and report each failed request as a ProviderError that says whether a retry may succeed.

Key files: melo/contracts/providers.py, support/providers/llm/, support/providers/embedding/.

Backends

One adapter for each backend key: mlc, ollama, vllm and sglang for servers you run (oMLX uses vllm), and openai, anthropic, gemini and nvidia for cloud APIs. Each adapter checks its table of the config file and builds the providers. Backends only connect: you start and stop the model servers yourself.

Key files: support/backends/registry.py, base.py, local/, cloud/.

melo/sleep/, melo/memory/personalized/ and support/melo_serving/ hold code that the agent does not use yet. melo/memory/retrieval/ and melo/memory/notes.py serve recall in the loop and melo-retrieve; support/scheduler/ is the scheduling policy core and its simulator, which the gateway's gate uses for the web workspace's chats and the console's turns, and support/gateway/machine_monitor.py reads the GPU lock and the battery.

Boundaries

BoundaryRuleWhy it matters
melo/ and support/ melo/ holds the agent and the interfaces that providers implement, and does not import support/ at module level. The one bridge is Agent(config=…), which builds its providers through support/backends when it is called. The agent runs with providers you build yourself, such as test fakes, and a new backend changes only support/.
Agent and executor A step runs only the tools it offered, and every call passes the checks first. The checks are guardrails, not a sandbox: tools run with your account's permissions. The model can call only what the step showed it, and a refused call never runs.
Agent and memory Memory writes pass the checker's size limits. With memory on, legacy long-term writes need an embedding backend; explicit reasoning modes can also admit text-only entries without one. The prompt and the stores stay bounded.
Backends and model servers Backends only connect to a URL. localmelo does not download, start or serve models. You keep control of your model servers.

What exists today

  • Direct mode with run options, including --workspace DIR for the folder a task works in and how a reply's reasoning is sent back or kept (legacy, drop, replay, compress or compress+replay), ten run statuses, text or JSON output, fixed exit codes, and --brief FILE to run one direct task as a worker and end with a versioned JSON result (--output-format stream-json adds redacted events). A worker that cannot start after a valid brief returns a startup_error result with the redacted cause; its explicit --inbox FILE or --inbox-fd N is a steering channel, not a trust boundary.
  • Brief runs (--brief FILE) add a fixed paragraph of working rules to the task. At an attempt boundary where the workspace has not changed since the run began, the next attempt is told to write the part of the task it can already write. A continue reflection starts the next attempt while steps and attempts remain, whatever its three flags say (#193). After six planning steps in a row without a workspace change, the next step asks for the part of the task the model can already write, and each planning request ends with a note of the tool output that the window dropped (#197). The brief's Check: commands run before a run ends completed, in every mode; a check that still fails after its two retries leaves the run completed with tests set to failed, and the run exits 4 (#195, #205). In the last attempt, with two steps of the budget left and the workspace changed since the checks last ran, they run once more; a failure goes back to the model and uses one of the two retries. The brief_check notice and each tests.items entry carry output_tail, the last 20 lines of the output, redacted and at most 4,000 characters (#214). Runs without --brief are unchanged.
  • Experimental Python-only typed assertions, opted into with AgentOptions(typed_assertions=True), can retain verified same-task changes with ordered source times, keep superseded rows as labelled history, and label historical recall; missing, ambiguous or unlinked assertions are not automatically linked, and only exact duplicates are ignored.
  • Opt-in context accounting ([agent] context_window, output_reserve and safety_margin) estimates planning and reflection requests; fitting shortens request copies when needed, but the output reserve is not enforced. A fixed prefix (fixed_prefix, on by default) freezes the local date and stable instructions per run; retrieved context and reflections remain data. Chunked window eviction (window_eviction = "chunk") and the reflection tool guard (reflect_tool_guard) are also on by default (#223), and --fixed-prefix off --window-eviction slide --reflect-tool-guard off send the earlier requests. Optional captured tool history (captured_history) is bounded and pattern-redacted separately from the model preview.
  • A provider streaming contract: the OpenAI-compatible adapter parses SSE and assembles tool calls only when complete, and display text is released line by line after redaction with the rules frozen for each stream. The interactive terminal consumes it for live replies (opt-in in #175, on by default since #245: [cli] stream is true unless set, and /stream off, melo -X cli.stream=false or melo config set cli.stream false turn it off); direct runs, workers and the gateway never stream. A model whose reasoning format is declared in [cli.reasoning_tags], or whose server sends reasoning in a field of its own, shows its reply as it is written; any other model shows it when complete (developer mode notes this once per model). A server that answers a stream request with one JSON body is read as the ordinary completion, and one that ends a stream before it delivered anything is asked once more without streaming; the adapter then stops asking that server to stream, and the terminal says so once (#245).
  • Reading a turn in the terminal (#245): outside developer mode the record is quiet. Thinking is one line (✻ Thought for 8.0s; /thinking on and developer mode show its first three rows, /verbose forty); a call that succeeded shows the first line of its output with +N lines (/expand T.C) on the same row, and a call that failed, or a command that exited with another code than 0, shows up to three lines; only the mark of a tool row carries the status color; and the live row keeps the activity, the time, the tokens and the stop key, with the step, the attempt and the phase in developer mode. The theme reads COLORFGBG and queries no terminal: a warning is yellow only on a background it reports as dark and bold otherwise, the approval's warning and keys and the hint row are default text, and code blocks use rich's light theme on a light background.
  • Prompt-cache telemetry: assistant.message and reflection events carry the server's cached_tokens and reasoning_tokens in usage when it sends them, and a prefix object that compares each request with the best earlier request of the run (#190). scripts/cache_report.py LOG reads a stream-json log and prints one row per request. Chunked window eviction (#191), the fixed prefix (opt-in since #142) and the reflection tool guard (#210) were opt-in until #223 made them the defaults. A further experiment holds the window cut across requests in the chunk and boundary modes (#204, off by default).
  • Cache layout and window options, shown by melo --developer --help (#228): with the fixed prefix on, --cache-layout v3 ([agent] cache_layout, now the default; v2 sends the earlier requests) appends each reflection to the window once, at the attempt boundary, and keeps the reflection request and its reply there, so each request extends the one before. --window-messages N ([agent] window_messages, 8 to 256, default 64 on a local server and 20 on a cloud vendor) sets the working window's message cap. Each request after a run's first also reports fresh_chars and request_chars in its prefix object, and scripts/cache_report.py prints a reusable share for each run and pooled.
  • Experimental brief-items reminder, off by default and listed by melo --developer --help only (#232): with --brief-items on ([agent] brief_items), a --brief run marks each top-level numbered item of the brief as changed, not yet or no file named, from the files that git status lists as edited since the run started. The items with no edit yet are named in each reflection request and in the deadline check two steps before the last attempt ends, and each naming records a brief_items notice.
  • The interactive UI in the terminal (bare melo, support/cli/): live tool blocks and a spinner, approvals with the diff a file write will make, / commands with completion, /model and /backend, /approvals, /status, /mcp, /retry, /clear (a new chat on a cleared screen, #304) and /browser, an MCP servers file (--mcp-config or the config's mcp_config), saved chats that melo -c, melo -r, /sessions and /resume resume, /title, /undo, /usage, /memory and /copy to name, undo, inspect and copy a conversation, a reasoning and recall mode for the whole chat (--reasoning, --reasoning-field, --replay-turns, --note-writer, --retriever, and --recall-*, from flags or saved defaults; --retrieval-extra-body is flag-only), /attach, /attachments and /detach N|all to stage workspace text files (at most 8, 256 KiB each, 512 KiB in total) into the next message, whose snapshot /retry reuses, and the plain conversation loop (melo "").
  • In the interactive UI, ! COMMAND runs a command in the user's shell ($SHELL, else /bin/sh), in the workspace, on a terminal of its own. It is not a sandbox, and its output is not sent to the model unless the user attaches it with /attach ! The page's chats and a console session's turns go through it; direct runs, melo "" and the /v1 HTTP API do not.
  • The scheduler's task store (component version 4 in the gateway's sessions.db): tasks with P0-P5, dependencies, priority events, questions, rules, the log, idle windows, park priority and recovery provenance, created in one transaction with a task's kind="task" session, idempotent on (origin, request_key), with workspaces under the user's home or [gateway] workspace; ChatGate.register_task() gives a worker its lifecycle, and a paused held worker parks at a safe point. /api/tasks provides task creation, inspection and control, with in-process workers. At startup, tasks left running, held or parked are reconciled from durable evidence, and a task proved never started launches behind a durable fence. Version 4 also holds dormant per-execution capture state, and every task launch now starts through the capture gate: python and shell calls record the process group, leader, boot ID and start time before the child is released, while a tool provider or arbitrary-code call marks capture incomplete. The controlled Resume API (POST /api/tasks/{task_id}/resume, #177) reads this evidence: a task the store proves never started is queued as its first start, a started task resumes without a confirmation only with a trusted complete capture and every recorded process group verifiably gone, and anything else needs the user's confirmation token. An unreadable or unsupported check counts as unknown, never as stopped, and a missing card blocks. The console's task card with Resume and Stop landed (#189); deadlines and worker accounting follow later.
  • A task that waits for a tool approval carries pending_approvals. The console's Tasks view shows the approval card with the state "Waiting for your approval", melo-task show and list print the same wait, and answers go to the existing approval endpoint (#208).
  • The documentation manifest registers each English page and its Chinese twin where one exists, and a parity test checks their anchors and code examples; the start guides, concept pages, guides and reference pages have Chinese twins, and #202 and #203 added the last six reference pages.
