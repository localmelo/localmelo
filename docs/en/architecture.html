Components

What each component does today, and where its code lives. Paths are relative to the repository root.

Command line

The melo command. Given a task, it runs in direct mode: it builds one agent, runs the task, prints the result as text or as one JSON line, and exits with a code that tells how the run ended. Without a task, in a terminal, it opens the interactive UI: an input box and a status bar stay at the bottom, and each turn prints into the scrollback as it runs: the model's thinking, a block for each tool call, retries, notices and reflections, with the answer as Markdown. A live area above the input box shows the step, the phase, the running tool and the run's progress facts, and on a session's first turn the past runs the progress line would show. The UI runs its turns on a session (stored in ~/.cache/localmelo/cli/sessions.db), resumes a saved chat in its workspace with melo -c or melo -r (/sessions and /resume open the same picker), asks in a panel before shell_exec, python_exec and file_write run, keeps the file tools in its workspace, and saves the model and server that /model and /backend pick to the config file (a session opened with --base-url saves nothing). It also names, undoes, inspects and copies the conversation with /title, /undo, /usage, /memory and /copy. Without a terminal, bare melo exits with code 2. An empty task (melo "") opens the plain conversation loop, where each turn sees the earlier answers. --serve starts the gateway; --daemon manages the macOS background service. With --base-url, the agent talks to that server and the config file is not read; without it, the configured backends are used. --chat-model and --request-timeout set the chat model and the chat request timeout in both cases, and never change the config file.

Key files: __main__.py; the UI in support/cli/: launch.py (the terminal check, the workspace and the model server), app.py (the input box and the keys), session.py (turns and commands), render.py (thinking, notices, reflections, tool blocks, the live rows and answers) and approvals.py; and support/sessions/agents.py.

Gateway

The HTTP server that melo --serve starts. It serves the HTTP API (/v1/health, /v1/agent/run, /v1/sessions) and keeps up to 50 sessions, each with its own agent built from the config file. A session's agent keeps its answers, so each request sees the earlier ones. It checks each request, the task's length and the session id, before a run.

Under /api/ it serves API v2, the web console's API: health, the sessions list and one session, a session's turns with their events, a Server-Sent Events stream, image blobs, submission lookups, and a session's tools, grants, memory and runs; and the writes that run a session — create it, with or without a first turn, start, retry and stop its turns, cancel a message by its key, answer an approval, rename or move it, and delete it. A console turn runs in the gateway process, one at a time, and its model calls pass the same scheduler gate a workspace chat's do. The console opens a session's agent on demand and resumes its conversation when an idle sweep or the open cap closed it, or when the gateway restarted. API v2 is served only on a loopback address, carries one error envelope and Cache-Control: no-store, and only grows. See API v2.

At / it serves the web workspace, the console's live page, which talks only to /api and uses the gateway's configured model (melo --reconfigure sets it; connection settings in the page arrive in a later update). It lists the console's sessions newest first, with search and each chat's draft, and draws one chat's turns as the terminal does: the user's message, a work card for each tool call, folded reasoning and reflections, notices, the live progress row and the answer with its facts and Copy response. Its event stream reopens from the last stored event, a send carries a key the store is asked about before Retry is offered, and Stop ends the turn as cancelled. Each chat has its own agent, in the gateway tool mode (file_read, file_write and python_exec, no shell_exec) and with its own working memory; its model calls pass the scheduler gate, and the header shows the GPU lock and the battery. The chats are sessions in ~/.cache/localmelo/gateway/sessions.db: they survive a restart and reopen from their transcript, while an agent is opened on demand (at most 8 at once, an idle one closed after 15 minutes, its conversation kept). Approval cards, the failure block's Continue/Try again and the settings dialog follow in a later update; until then a waiting approval shows as Needs approval and is answered over API v2.

The gateway has no authentication. When it listens on localhost or a loopback address, such as the default 127.0.0.1:8401, it refuses requests whose Host is not 127.0.0.1, localhost or [::1] with its port (HTTP 421), and requests to its API that web pages at another origin send through your browser (HTTP 403). No web page can show it in a frame. On any other host, such as 0.0.0.0, it makes none of these checks and logs a warning when it starts.

Key files: support/gateway/__init__.py, session.py, guard.py (the Host and Origin checks), webapp.py and playground.py (the legacy /v1/playground routes and the chats behind them), console/ (the console's session store, its API v2 routes and the page's data), static/ (the page: workspace.js, turns.mjs and markdown.mjs), and daemon.py for the macOS background service.

MCP servers

Local servers that speak the Model Context Protocol over stdio, listed in the JSON file that --mcp-config names. At the start of the first run, support/mcp starts each server, lists its tools and registers them, as mcp__<server>__<tool>, with the tool registry and the executor. MCP tools work in direct mode, the Python API and the interactive UI (--mcp-config, else the config's mcp_config key); the gateway does not load them yet. A server's require_approval makes calls of its tools, or of the tools it names, ask the run's approval policy first; a run without a policy, such as a direct run, runs them without asking. Each server starts with the same minimal environment as a tool's child process, plus the env its entry names.

Key files: support/mcp/config.py, client.py, provider.py, and the tool provider interface in melo/contracts/tools.py.

Agent

The run loop. Each step builds a prompt from the task, working memory, recalled long-term memory and the latest reflection, offers the model a list of tools (in the default retrieve mode, the built-ins, the ones it has already called in this conversation and the three closest matches for the task), sends one planning request, and runs the tool calls of the reply. A reply with text and no tool call is the answer, and the run ends as completed. With the default reflect policy, steps come in attempts of up to 10; after an attempt that ends without an answer, a reflection decides whether another attempt starts. Every run ends with one of nine statuses, or as cancelled when an interactive run (below) is stopped, and returns a RunResult. A failed model request is retried up to twice when a retry may succeed.

Python code that calls run_task can follow and steer a run. With on_event, it receives each step, model reply, tool call, notice and reflection as an event, with secrets in the model's text redacted. With approval, a policy decides whether each call of a tool that requires approval may run. A run with either one is interactive: cancelling it ends it as cancelled and closes the interrupted step. With AgentOptions(record_answers=True), working memory keeps each run's answer, and conversation() and load_conversation() carry a conversation to another agent. Direct mode and the HTTP API pass no event sink and no policy. A console turn passes both: its Stop ends the run as cancelled, and a call of a tool whose tier is not read waits for the answer given over API v2.

Key files: melo/agent/agent.py, melo/agent/options.py (AgentOptions), melo/agent/_chat.py (planning and reflection requests, retries), melo/agent/_events.py and melo/contracts/events.py (events), melo/contracts/approvals.py (approval policies), melo/schema.py (RunResult and the limits).

Checker

The checks at each boundary of a run:

  • before a planning request: the prompt may hold at most 100,000 characters, and the list of offered tools must be valid;
  • after it: each tool call in the reply needs a name and an id of its own;
  • before a tool runs: the tool's tier and the mode decide. The interactive UI offers shell_exec; direct, python and gateway do not offer it by default, and refuse an exec call registered anyway unless a direct or python caller named it in builtins; the gateway refuses it even when named. A run with an approval policy asks before a call whose tier is not read, and no command is refused by its spelling;
  • after a tool runs: output longer than 50,000 characters is cut;
  • before a memory write: its size is limited;
  • before an event reaches Python code: API keys of well-known shapes, bearer tokens and one-time codes in a model reply's text are replaced with [redacted];
  • in the gateway: each request's task and session id.

A failed check before or after a planning request ends the run as failed. A refused tool call does not run: the model sees the refusal as the tool's error.

Key files: melo/checker/checker.py, validators.py, payloads.py, redaction.py.

Executor

Runs the tool calls of a step, in order. A call is refused when the step did not offer the tool, when its arguments are not a JSON object, or when an argument of a built-in tool has the wrong type; the checker then sees every call that is left. With a workspace root, the workspace policy then resolves the path of a file tool and refuses one outside the root. With an approval policy, a call of a tool whose permission tier is not read, or that is marked as requiring approval, then waits for the policy's decision, and once it is allowed, a file path under a workspace root is resolved again and refused if it changed in the meantime. Each tool runs with a time limit, which starts after the approval: shell_exec 30 seconds, file_read and file_write 60 seconds, an MCP tool its server's timeout. In the interactive UI, shell_exec and python_exec get 10 minutes. A shell command's standard input is /dev/null, so it never reads the terminal. python_exec code always runs in a child process, which a time limit or a cancellation kills: in the current directory without a workspace root, in the root with one. The child of shell_exec or python_exec gets only PATH, HOME, USER, LOGNAME, SHELL, TERM, LANG, every LC_* variable and TMPDIR, plus AgentOptions(tool_env=…): an API key in melo's environment reaches no tool, and VIRTUAL_ENV, PYTHONPATH, SSH_AUTH_SOCK and the proxy variables pass only through tool_env. A refusal, a denial, a time-out or an error comes back as the tool's error.

The four built-in tools are shell_exec, python_exec, file_read and file_write. Only the interactive UI gets all four by default; a direct run, the gateway and a console session get file_read, file_write and python_exec, and the library's default python mode does too. Their modes leave shell_exec out: direct and python mode have no approval policy, and the gateway's /v1 routes do not ask either; the console asks over API v2 and runs in the same gateway mode, so it gets no shell either (Python code can still start a process). --builtins all (or naming shell_exec) is a direct or python caller's opt-in; the gateway and console refuse it even when named. Direct mode and a /v1 gateway session give the tools no workspace root, so file tools reach any file you can; direct mode's --workspace DIR sets the same root as the Python API below, and a console chat gets [gateway] workspace (default ~/localmelo-workspace) as its root. In the Python API, AgentOptions(workspace_root=…) turns policy.py on: the file tools then reach only files inside the root, and shell_exec and python_exec run there in a child process, without that limit. Approvals apply only to a run with an approval policy.

Key files: melo/executor/executor.py, builtins.py, policy.py, melo/contracts/approvals.py.

Memory

In compress modes, heuristic notes can extract up to 12 keyed facts from a visible reply without a note block, and an explicit note can also hold 12. Questions, options, plans and negated or cancelled statements are not positive facts; a claim about the agent's own work is filtered unless a keyed content clause follows it; source matching scores typed keys, rejects conflicts and leaves ties and unmatched items unsourced; CJK-only keys are not extracted. See reasoning notes.

Working memory holds the conversation of a run or a gateway session: the last 20 messages, in RAM. History records every task and step and, with persistence on, every model call and its reasoning. In legacy, long-term memory needs an embedding backend: it stores step summaries and reflections with their embeddings, and recalls the 5 closest entries on each step. In the compress modes it is a typed store instead: every entry has a kind (semantic, episodic, profile or reflection), a source, a status and the signal that admitted it, with its provenance beside the text and the vector, and one decision (NEW, UPDATE, RELATED, CONFLICT or IGNORE) is kept for each candidate; a candidate is admitted only by a rehearsal, a user request or statement, or --admit-on-outcome on for the final digest. Procedural memory keeps the steps of each run and learns the steps of tasks you repeat. History, long-term and procedural memory stay in RAM, or go to history.db, long_term.db and procedures.db when persistence is on. New files are created readable only by you (mode 0600). The text history and long-term memory keep is redacted before it is written: sk- keys, GitHub tokens, AWS access key ids, the token after Bearer and a one-time code next to its keyword, as events and model calls already were; the run, its requests and the model keep the text. The Python API can forget a task's history rows and the long-term reflections that name it with Hippo.forget(task_id), and empty history and long-term memory, step summaries included, with forget_all(). The tool registry holds every registered tool, with the BM25 index that retrieve mode searches.

In the compress and compress+replay reasoning modes, each reply becomes a short note (its plan, what it found, decided and left open, and what its tools returned) with its code drafts, kept in a RAM-only note store beside the working window and rehearsed into an attempt digest as later notes, calls and reflections use it. Every note, draft and digest passes the check_memory_candidate boundary (redact, sanitize, cap) before it reaches the window or the store. The compress modes recall them back: at start, attempt and step a delimited, data-framed block carries this task's notes, drafts and thought chunks and earlier tasks' long-term entries, chosen by --retriever auto|off|bm25|llm|embedding (embedding when configured, else llm at start and attempt and bm25 at step and tool, with bm25 as the fallback), placed by --recall-at and --recall-placement, checked and bounded; a thought chunk is recallable only after the turn that produced it left the window. history.db version 2 records each new block in recall_json, and the recall event carries its hits. See Reasoning notes and Recall in the loop.

melo/memory/retrieval/ holds three switchable retrievers, bm25, llm and embedding. They search documents built from a run's model calls: the notes on the model's reasoning, code drafts and chunks of its thinking that melo/memory/notes.py builds from a model reply, and reflections. The compress modes use them in the loop (see above), and the melo-retrieve command (support/retrieve.py) compares them offline on labelled queries, and turns model calls recorded as raw-call JSONL into a corpus. With persistence on, the history.db that melo writes records model calls too, and melo-retrieve exports it as well. See Offline retrieval.

Sessions (experimental) keep whole conversations in sessions.db: each turn is a stored row that ends exactly once with a status and a cause, the session's events are stored with it, and a window checkpoint lets a fresh agent resume where the last one stopped. A runner built with progress=True asks each turn's run for its run.progress events and stores them with the turn. The gateway's file and the terminal's file are separate. The interactive UI runs its turns on sessions and resumes a saved chat with melo -c or melo -r; the web console runs and reads its sessions in the gateway's own file, while its /v1 sessions stay in RAM (code: support/sessions/, support/gateway/console/). See Sessions.

Key files: melo/memory/coordinator.py, short/ (working memory), history/, long/, tools/ (the tool registry), bm25.py.

Memory design (planned): the memory design page keeps the maintainer's design for memory, parts of which are not built yet.

Config and setup

~/.cache/localmelo/config.toml names the chat and embedding backends and their settings. On a first run in a terminal, melo finds a model server with GET /v1/models, asks for its URL and model and saves them, as the ollama backend for an Ollama server and as vllm for any other OpenAI-compatible server. When the server lists an embedding model, it offers one for long-term memory; the embedding guide covers Ollama, oMLX, vLLM, SGLang and MLC. The setup wizard (melo --reconfigure) asks for every backend, sends a test request to each server, saves the file, then opens the interactive UI, or with --serve starts the gateway. Direct mode and the gateway build their agents from this file.

Key files: support/config.py, support/onboard.py, support/onboard_probe.py, support/backends/discovery.py.

Providers

The HTTP clients for model servers: OpenAI-compatible chat (/chat/completions), Ollama's own /api/chat, and OpenAI-compatible embeddings. They implement the interfaces in melo/contracts/providers.py, apply the chat request timeout, and report each failed request as a ProviderError that says whether a retry may succeed.

Key files: melo/contracts/providers.py, support/providers/llm/, support/providers/embedding/.

Backends

One adapter for each backend key: mlc, ollama, vllm and sglang for servers you run, and openai, anthropic, gemini and nvidia for cloud APIs. Each adapter checks its table of the config file and builds the providers. Backends only connect: you start and stop the model servers yourself.

Key files: support/backends/registry.py, base.py, local/, cloud/.

melo/sleep/, melo/memory/personalized/ and support/melo_serving/ hold code that the agent does not use yet. melo/memory/retrieval/ and melo/memory/notes.py serve recall in the loop and melo-retrieve; support/scheduler/ is the scheduling policy core and its simulator, which the gateway's gate uses for the web workspace's chats and the console's turns, and support/gateway/machine_monitor.py reads the GPU lock and the battery.

Boundaries

BoundaryRuleWhy it matters
melo/ and support/ melo/ holds the agent and the interfaces that providers implement, and does not import support/ at module level. The one bridge is Agent(config=…), which builds its providers through support/backends when it is called. The agent runs with providers you build yourself, such as test fakes, and a new backend changes only support/.
Agent and executor A step runs only the tools it offered, and every call passes the checks first. The checks are guardrails, not a sandbox: tools run with your account's permissions. The model can call only what the step showed it, and a refused call never runs.
Agent and memory Memory writes pass the checker's size limits. Long-term memory is written only when an embedding backend is configured and memory is on. The prompt and the stores stay bounded.
Backends and model servers Backends only connect to a URL. localmelo does not download, start or serve models. You keep control of your model servers.

What exists today

  • Direct mode with run options, including --workspace DIR for the folder a task works in and how a reply's reasoning is sent back or kept (legacy, drop, replay, compress or compress+replay), nine run statuses, text or JSON output, and fixed exit codes.
  • The interactive UI in the terminal (bare melo, support/cli/): live tool blocks and a spinner, approvals with the diff a file write will make, / commands with completion, /model and /backend, /approvals, /status, /mcp and /retry, an MCP servers file (--mcp-config or the config's mcp_config), saved chats that melo -c, melo -r, /sessions and /resume resume, /title, /undo, /usage, /memory and /copy to name, undo, inspect and copy a conversation, a reasoning and recall mode for the whole chat (--reasoning, --reasoning-field, --replay-turns, --note-writer, --retriever, --recall-* and --retrieval-extra-body, from flags or saved defaults), and the plain conversation loop (melo "").
  • Four built-in tools, with python_exec in a child process in every mode; a direct run, the Python API's default python mode, gateway sessions and console sessions get three, without shell_exec; and tools from local MCP servers in direct mode, the Python API and the interactive UI.
  • Tool children and MCP servers run with a minimal environment (PATH, HOME, USER, LOGNAME, SHELL, TERM, LANG, LC_*, TMPDIR), plus AgentOptions(tool_env) or the server's env; config-backed direct runs, the UI and console sessions also resolve the names in [agent] tool_env, and nothing else is inherited.
  • A step offers the built-in tools, the tools the model has already called in the conversation and the three closest matches for the task (the default retrieve mode); all offers every tool on every step.
  • The Python API (experimental): run events, stopping a run, approval policies for tool calls, a workspace root for the file tools, and conversations that carry over between runs.
  • Sessions (experimental): conversations kept in SQLite whose turns each end exactly once, survive a restart and resume on a fresh agent (support/sessions/); a runner can ask its turns for progress events. The interactive UI keeps its turns in them, and the web console runs and reads its sessions in the gateway's own store; the /v1 HTTP API does not use sessions yet.
  • The gateway: the HTTP API, the console's API v2 under /api (health, sessions, turns, an event stream, blobs, submissions, tools, grants, memory and runs, and the writes that create a session and start, retry, stop and approve its turns), sessions that close on request only when idle, and the console's live page at / (the session list, a chat's turns and stored events over SSE, a work card for each tool call, the live progress row, Stop, the level chip and the typing heartbeat; it talks only to /api and uses the configured model). The page's chats and console turns pass through the scheduler's policy (off by default) and the header shows the GPU lock and the battery. The gateway also keeps the legacy /v1/playground routes as they were, checks that, on a loopback host, refuse requests from other sites, and a macOS background service.
  • Backends for Ollama, MLC LLM, vLLM, SGLang and four cloud APIs.
  • Working memory, history and long-term memory, saved to SQLite when persistence is on; in the compress modes long-term memory is a typed store whose entries carry a kind, a source, a status, the signal that admitted them and their provenance, with one decision per candidate; the saved text is redacted first, the saved history also keeps every model call with its reasoning, for 30 days by default, and the Python API can forget a task's memory or all of it.
  • Reasoning notes: the compress and compress+replay modes keep a short note of each reply and its code drafts in a RAM-only store beside the working window and rehearse them into an attempt digest that names the files the attempt wrote, its last check and result, its decisions and the outcome, and recall them, with the task's drafts and thought chunks and earlier tasks' long-term entries, at start, attempt and step (--retriever, --recall-* and the recall tool).
  • melo-retrieve, which compares the bm25, llm and embedding memory retrievers offline, exports a typed store or its decisions, and scores candidate files for the bench. The compress modes use the same retrievers in the loop; legacy runs do not.
  • Procedural memory: each run records its steps, and a completed run updates the step template of its task, in procedures.db with persistence on. Python callers get run.progress events with progress=True, without a percent bar for now. On a terminal, melo "<task>" draws them as a progress line on stderr (support/progress_line.py). melo-procedures replays the progress rules offline.
  • The scheduler's policy core and a simulator that tests it offline (support/scheduler/), and the gateway's shared gate, GPU-lock reader and battery reader (support/gateway/chat_gate.py, machine_monitor.py). The page's chats and a console session's turns go through it; direct runs, melo "" and the /v1 HTTP API do not.
  • The scheduler's task store (component version 1 in the gateway's sessions.db): tasks with P0-P5, dependencies, priority events, questions, rules, the log and idle windows, created in one transaction together with a task's kind="task" session, idempotent on (origin, request_key), with workspaces resolved under the user's home or [gateway] workspace; ChatGate.register_task() gives a worker its lifecycle. No /api/tasks route or worker run is on main yet.

What comes next is on the roadmap.
