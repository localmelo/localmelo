Quickstart

This tutorial installs localmelo, runs a first task against a local model server, saves a configuration and starts the gateway.

Before you begin

You need:

  • macOS (developed and tested) or Linux (should work, untested). Windows is not supported.
  • Python 3.11 or later, Git, and uv (or pip, see Install with pip).
  • A model server. The commands below use Ollama: install it, start it, and pull a model with ollama pull qwen3:8b. On a Mac with Apple silicon, oMLX is the recommended server: use http://127.0.0.1:8000/v1 and your model's folder name in the commands instead. Any server with an OpenAI-compatible API works too: use its /v1 URL and its model name.

Install

git clone https://github.com/localmelo/localmelo.git
cd localmelo
uv sync --extra gateway
source .venv/bin/activate

uv creates the virtual environment .venv/ (installing Python 3.13 if you do not have it) and installs localmelo with the gateway's dependencies.

Keep the directory name localmelo: the package is built from it. A renamed folder or a ZIP download (localmelo-main) fails with ModuleNotFoundError: No module named 'localmelo'.

On a Mac with Apple silicon, the macOS development app puts a native window around the console. One command, uv run python scripts/build_macos_app.py --install, builds it, signs it ad hoc and installs it in ~/Applications without admin rights. It needs no Apple developer account and stays on the Mac that builds it, and it needs a Swift compiler, from the release Xcode or the Command Line Tools: it is a development bundle, not a notarized release or a Homebrew cask.

The rest of this guide calls melo directly. Activation lasts for this terminal only: in a new terminal, run source <clone>/.venv/bin/activate again, where <clone> is your localmelo directory. With uv you can also run uv run melo … inside the clone, or uv run --project <clone> melo … from anywhere else.

Install with pip

git clone https://github.com/localmelo/localmelo.git
cd localmelo
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[gateway]"

python3 must be Python 3.11 or later. The -e flag keeps the installation linked to this checkout, so source changes apply without reinstalling.

Run your first task

The model can run shell commands and Python code, and read or write any file you can: there is no sandbox. To run a task without tools, add --builtins none. See the security policy and what the checks do. 

melo -u http://127.0.0.1:11434/v1 -m qwen3:8b "What is 6*7?"

The answer is printed on stdout, and the command exits with code 0 (echo $? prints 0). -u (--url) points localmelo at an OpenAI-compatible server for this one run, without a configuration file, and -m (--model) names the model. The old spellings --base-url and --chat-model still work (old spelling to new). It sends no API key, so use it for local servers; for a cloud API, save a configuration (below).

With oMLX, use its URL and the name of a model folder: 

melo -u http://127.0.0.1:8000/v1 -m Qwen3-8B-4bit "What is 6*7?"

For every option, see the command-line reference.

Get the result as JSON

melo -u http://127.0.0.1:11434/v1 -m qwen3:8b -o json "What is 6*7?"

Example output (values vary):

{"task_id": "f52e785a84a144ff8c3b8e70e0451eb1", "status": "completed", "result": "42", "error": "", "steps": 1, "attempts": 1, "n_llm": 1, "n_main": 1, "n_aux": 0, "n_tool": 0, "llm_errors": 0, "usage": {"prompt_tokens": 120, "completion_tokens": 12, "total_tokens": 132}, "duration_s": 1.9, "config": {"max_steps": 30, "attempt_policy": "reflect", "steps_per_attempt": 10, "max_attempts": 5, "reflection_gate": "flags", "tool_exposure": "retrieve", "mode": "direct", "builtins": ["file_read", "file_write", "python_exec"], "memory": true, "memory_dir": null, "timeout_s": null, "tools": ["file_read", "file_write", "python_exec"]}, "localmelo_version": "603f40d"}

Run results

status says how the run ended, for example completed, budget_exhausted or provider_error. The counters say how many steps, model requests and tool calls the run took, and config records the options it ran with. See Run results for every status and field.

Save a configuration

A configuration file saves the backends, so that melo, melo "<task>" and the gateway work without -u.

For a local server, run melo in a terminal. With no configuration yet, it first says what it needs, a model server on this computer. It then looks for one (oMLX on port 8000, Ollama on 11434), asks whether to use the one it found (Use this model server?, a list: Enter takes the selected Use it) and for a model from the server's list, which shows chat models first and tags an embedding or reranking model, saves ~/.cache/localmelo/config.toml and opens the interactive UI: 

$ melo
melo uses a model server on this computer (oMLX, Ollama, LM Studio…).
Found a model server at http://127.0.0.1:11434/v1 (1 model).
✓ http://127.0.0.1:11434/v1 lists 1 model; using qwen3:8b.
melo remembers across chats by words only; melo setup adds search by meaning.
Saved to ~/.cache/localmelo/config.toml (melo setup changes it).
melo 0.1.0 · qwen3:8b (/model to change)
~/demo-project
Try: What is this project? · / commands · ctrl+d quit

The first row shows the package version, and on a git checkout the short commit, as in melo 0.1.0 (baab21e); melo --version prints the same line and exits 0. /status checks that the model answers and shows the folder, session, approvals and context use; /status all adds the tools, memory, limits and files.

Type a message and press Enter, or /exit to leave. From then on, melo goes straight in and melo "<task>" uses the saved server. The server here is Ollama, so it is saved as the ollama backend; an oMLX server is saved as omlx and any other OpenAI-compatible server as vllm, the key for those. When the server lists an embedding model, the first run asks one more question, Remember across chats with <model>?, a list whose selected row, Use it, saves it. Every question with a fixed set of answers is a list on a terminal (↑ ↓ or a number move, Enter confirms, Esc takes the safe answer); piped answers keep the typed questions. See First run and Set up an embedding model.

With no model server running, melo prints this computer's commands for starting one (oMLX on a Mac, Ollama elsewhere, the ones in the model servers guide) and asks No model server found. What now? with Check again, Enter an address and Quit (piped: Press Enter to check again, type an address, or q to quit:). Start the server in another terminal, then choose Check again; melo installs and starts nothing itself.

With the setup wizard

The setup wizard also sets up an embedding server or a cloud API. For a cloud API, first run export OPENAI_API_KEY="<your key>" (or your vendor's variable) in this terminal: the wizard's test request uses that key. Run the wizard, then start the gateway: 

melo setup
melo serve

In default mode melo setup first offers the server it finds (Use this model server?); choose Use another server for the full menu, which developer mode (melo config set ui.mode developer) shows at once. The wizard asks:

PromptWhat to enter
Chat backendYour server type, such as 2. Ollama (local endpoint): move with ↑ ↓ and press Enter, or press the number (piped: type it). The saved backend is selected first, else MLC (1). For oMLX or another OpenAI-compatible server, choose oMLX or vLLM (3).
Base URLYour server's URL. Press Enter to accept the default shown in brackets: the saved URL, else the backend's usual one.
Chat model nameThe model, such as qwen3:8b.
Save these settings?Press Enter on Save and continue, or choose Cancel setup (piped: Save and continue? [Y]:).
Embedding backend5. None (no long-term memory). Without a saved embedding, the chat server's own embedding models are appended as 6, 7, … with the first selected; choosing one is enough.
Embedding endpoint URL, Embedding model nameOnly asked when you chose one of the fixed embedding backends 1–4, not a detected model.

For a cloud API, choose the vendor. The wizard then asks for API key env var, the name of the variable you exported, and Chat model instead of Base URL and Chat model name.

For Ollama, the default URL http://localhost:11434 has no /v1. That is correct: the ollama backend uses Ollama's own API, not the OpenAI-compatible one.

Next, the wizard sends a short test request to each server (Probing backends ...). If the chat server does not answer, it prints Probe failed: … and asks The check failed. What now? with Try again, Save anyway and Cancel setup (piped: [r]etry, [s]ave anyway, [N]o [N]:); Try again asks for the URL and model again, and Enter, which takes the selected Cancel setup, saves nothing. If only the embedding server fails, the wizard saves with embedding off and says so. On success it prints Config saved to …, the path of ~/.cache/localmelo/config.toml, and opens the interactive UI; leave it with Ctrl+D. Then melo serve starts the gateway on http://127.0.0.1:8401, and it keeps running in this terminal. In default mode melo setup starts with the first run's question: it prints Found a model server at … and asks Use this model server?. The full menu above follows only after Use another server, in developer mode, or when no server is found while a backend is saved; with nothing saved, it prints the commands that start a server instead.

Set up an embedding model

Long-term memory needs an embedding model. localmelo never downloads or starts one: point it at a model your server already serves. The guide covers Ollama, oMLX, vLLM, SGLang and MLC.

With Ollama:

ollama pull qwen3-embedding:0.6b
curl -sS http://127.0.0.1:11434/v1/embeddings \
  -H 'Content-Type: application/json' \
  -d '{"model": "qwen3-embedding:0.6b", "input": "ping"}'
melo setup    # Embedding backend: 2 (Ollama); URL http://localhost:11434; model qwen3-embedding:0.6b

The reply must hold a non-empty data[0].embedding. nomic-embed-text is a smaller English-only alternative.

With oMLX the chat server also serves the model:

curl -sS http://127.0.0.1:8000/v1/models
curl -sS http://127.0.0.1:8000/v1/embeddings \
  -H 'Content-Type: application/json' \
  -d '{"model": "Qwen3-Embedding-0.6B", "input": "ping"}'

GET /v1/models gives ids but no type, so the embeddings request is the check. Keep the chat server and set embedding_backend = "vllm" with that table's embedding_url and embedding_model; see oMLX.

Changing the model changes the vector space: stored vectors of another dimension are skipped, so old entries stop ranking. To reclaim the space, stop localmelo and remove ~/.cache/localmelo/memory/long_term.db*.

Start the gateway

Once the configuration is saved, by melo or by the wizard above, start the gateway with melo serve. From a second terminal, check the gateway and run a task through it:

API examples pipe the gateway token to curl, keeping it out of command-line arguments and shell history. Do not enable verbose curl output or log the header; same-user processes can still read the token file.

{ printf 'Authorization: Bearer '; cat ~/.cache/localmelo/gateway/auth/token; printf '\n'; } | curl -H @- http://127.0.0.1:8401/v1/health
{ printf 'Authorization: Bearer '; cat ~/.cache/localmelo/gateway/auth/token; printf '\n'; } | curl -H @- -X POST http://127.0.0.1:8401/v1/agent/run \
  -H "Content-Type: application/json" \
  -d '{"query": "What is 6*7?"}'

Example output (values vary):

{"status":"ok","uptime":12.3,"sessions":{"active":0,"busy":0,"max":50},"chat_backend":"ollama","embedding_backend":"none"}
{"result":"42","session_id":"a7e8f646ca2e"}

The health check does not contact the model server; a task does. The web workspace opens in your browser when melo serve starts at a terminal on this computer; melo console opens it again. Over SSH, or when no browser starts, melo console prints a one-use link to open within 60 seconds; do not share it (see Interactive conversations).

Press Ctrl+C in the first terminal to stop the gateway. Tasks use the saved configuration: 

melo "What is 6*7?"

To start the gateway again, run melo serve.

The separate melo-task client creates, inspects, follows and controls gateway tasks over authenticated loopback HTTP, and never starts the gateway. See the task command.

Interactive conversations

Run melo without a task to chat in the terminal. A turn shows its work as it happens: the model's thinking on one line, each tool call as it finishes, retries, notices and reflections, and a live area with what melo is doing, the time, the tokens and the running tool (developer mode adds the step, the phase and the run's progress facts). The answer prints as Markdown, and a turn that wrote files ends with a line that names them: 

melo
# Or talk to an OpenAI-compatible server that is not saved. Without
# -m it uses the server's only chat model or its one loaded model;
# with several chat models and not exactly one loaded, it exits 2 and lists them:
melo -u http://127.0.0.1:8000/v1
melo -u http://127.0.0.1:8000/v1 -m YOUR_MODEL_ID
  • Type / for the commands (/help lists the everyday ones, /help all every one): /model lists the server's models and switches to one, /backend switches to another server (both saved as the default), /verbose and /thinking add or leave out detail, /expand prints a tool call's whole output, /progress the facts the live area rests on, /approvals the mode and grants, /status the session's facts, /mcp the MCP servers, /retry the newest turn again, /attach PATH stages one workspace text file (at most 256 KiB) for the next message, /attachments and /detach N|all list and remove the staged files, /new starts over, /exit or Ctrl+D leaves.
  • melo asks before it runs a shell command, Python code or a file write: press 1 to allow it, 2 to allow that tool for the session, 3 to refuse and tell melo why. Esc stops a turn.
  • melo works in the current folder (-w DIR picks another): file tools stay in it; commands and Python can reach other files, so melo asks first.

The interactive UI has the keys and the rest. melo "" opens the plain conversation loop of earlier releases. Without a terminal, melo alone exits with code 2; start the gateway with melo serve.

The web workspace at http://127.0.0.1:8401/ is the console's live page and talks only to /api: it uses the gateway's configured model, which you can change in Settings or with melo setup. On a first run, with no model set up, its welcome shows a card that finds the model server already running on this Mac and connects it with Use this model, without opening settings. It lists your chats newest first, with search and a draft for each, and draws a turn as the terminal does: your message, a work card for each tool call, folded reasoning and reflections, notices, the live progress row and the answer with its facts and Copy response. Stop cancels the turn, a waiting approval shows as Needs approval, and the chats are saved in the gateway's sessions.db, so a restart keeps them. Other browser tabs on the same gateway see the same chats. Approval cards let you allow or deny tool calls, and show a numbered diff of what a file write replaces; Settings changes the model server. The Workers section shows saved worker runs read-only. The gateway requires authentication; use melo console to sign in. Approvals are not a security boundary against same-user processes or other localhost services.

Serve a model with oMLX

oMLX serves MLX models through an OpenAI-compatible API on a Mac with Apple silicon and macOS 15 or later. localmelo supports it as a local server: first-run setup finds it on port 8000 and asks it which models are loaded. In the config file it is the vllm backend, also spelled omlx; the guide explains why. To use it instead of Ollama:

  1. Install oMLX with Homebrew:

    brew tap jundot/omlx https://github.com/jundot/omlx
brew install jundot/omlx/omlx

    The oMLX macOS app also installs the command, as ~/.omlx/bin/omlx. Its README has the other ways to install it. The Homebrew command above installs oMLX without its optional native kernels, which a few model families (Qwen3.5, for example) need to run at full speed; the app ships them, and the README explains the Homebrew option.

  2. Put each model in a folder of its own inside one models folder. oMLX serves every subfolder that holds a model (a config.json and its weights), and a subfolder's name is its model id. For example, with the Hugging Face command line (hf, from uv tool install huggingface_hub): 

    hf download mlx-community/Qwen3-8B-4bit --local-dir ~/models/Qwen3-8B-4bit

  3. Start the server, and leave it running in its own terminal:

    omlx serve --model-dir ~/models --port 8000

    It listens on http://127.0.0.1:8000. oMLX saves --model-dir and --port in its settings.json (under ~/.omlx by default) and uses them when you leave the flags out, so a port saved earlier wins over the default 8000; giving --port avoids that. The oMLX app and omlx start run the server in the background instead, with the folder and port saved in oMLX (the Homebrew service starts with ~/.omlx/models and port 8000): then skip the command above.

    Keep the default host and do not set --api-key: localmelo sends no API key to a local server. If requests fail with HTTP 401 (API key required), a key was set earlier, in oMLX's admin page or with OMLX_API_KEY: turn on Allow inference without API key in the admin page's settings, or unset OMLX_API_KEY. With that setting on, listing models and chat work, but oMLX still asks for the key on the route that says which models are loaded, so setup cannot mark them (see below).

  4. Check that the server lists the model:

    curl -sS http://127.0.0.1:8000/v1/models

    The reply's data list holds an entry with "id": "Qwen3-8B-4bit". It can also list MLX models from your Hugging Face cache. Failed to connect means that nothing listens on that port: check the port in oMLX's startup log. API key required means that a key is set: see step 3.

  5. Run a task with that id:

    melo -u http://127.0.0.1:8000/v1 -m Qwen3-8B-4bit "What is 6*7?"

    oMLX loads the model on its first request, which can take a minute for a large model. If that request times out, add -X request_timeout_s=600 (-X KEY=VALUE changes one setting for one run). Without -m, melo asks oMLX which models it has and uses the only chat model or the one that is loaded, for a task and for melo -u http://127.0.0.1:8000/v1 without a task (the interactive UI); with several chat models and not exactly one loaded, it exits 2, lists them and asks for --chat-model <id>. Name the model with -m to skip that lookup.

To make oMLX your default, run melo in a terminal before any configuration is saved: it finds oMLX on port 8000, lists its models and saves the one you pick; First run shows the exchange. oMLX loads a model when the first request for it arrives, so a listed model is not always in memory, and loading a large one can take minutes. Setup therefore chooses like this, and with several chat models it asks oMLX which are loaded (GET /v1/models/status, one second at most):

  • One chat model: it is the default.
  • Several, and oMLX says which are loaded: setup marks them (loaded) and makes the first of them the default.
  • Several, and none is loaded or oMLX does not say: there is no default: nothing is highlighted and Enter does nothing until you move to a model with ↑ ↓ (answers piped in: type the number of the model to use; Enter alone asks again), because choosing for you could start a long load of a large model. While a key is set, oMLX does not say, even with Allow inference without API key on, and setup prints The server did not say which models are loaded (it needs a key for that). A model that has an alias in oMLX is listed under the alias, and the status reply names the alias beside the folder name (model_alias, as oMLX 0.7.1rc1 sends it), so the model is marked and can be the default under the alias. A server whose reply has no alias cannot mark such a model.

With a configuration saved already, run step 5 first, so that the model is loaded, then melo setup: in default mode it offers the server it finds with the first run's questions. In the full menu (after Use another server, or in developer mode), choose oMLX or vLLM (3) as the chat backend, enter http://127.0.0.1:8000/v1 and the model id, and choose 5 (None) as the embedding backend unless oMLX also serves an embedding model. Configuration shows the file they save and the table to add to turn off a Qwen3 model's thinking. The web workspace then uses that model; it reads the configuration file.
