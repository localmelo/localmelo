The pet changes moves smoothly

2026-10-30 · #306

The desktop pet hitched whenever its mood changed (resting to working, working to waiting, waiting to done). Starting a mood took the running breath off, so the picture snapped back to rest, a hop was cut in the air and the "z" of a sleeping Melo vanished, and a change of pose was a short dissolve of two different drawings. Now nothing that moves is cut: a breath that the next mood shares goes on as it is, and one that changes is eased to rest over a quarter of a second before the new one begins; the "z" fades out, and a hop or squash in the air lands. A change waits for a rest point, at most 0.4 seconds (the end of a breath, the landing of a hop, an open eye). A change of pose hides in a squash: Melo squashes a little and rises, the new picture dissolves over the low point, and the bob, hop or tail wag springs up from there. Under Reduce Motion, in Low Power Mode and when the Mac runs hot, nothing moves and a change is a plain 200 ms cross-fade (under Reduce Motion it used to swap with no fade). The app still asks the gateway every 2 seconds, so a change can land a little late.

Chats say plainly what they remember, and answer in your script

2026-10-30 · #305

Asked about memory, a chat used to describe how the system around it works, and it answered a user who wrote simplified Chinese in traditional characters. The paragraph that tells the model who it is (#287) now also says what the chat remembers, built from the memory settings the chat runs with, and which script to reply in. By default a chat remembers the recent messages of this chat and nothing from other chats. With saved memory that can be recalled, it also remembers what localmelo keeps on this computer, such as what you tell it or ask it to remember and what it found or decided. It keeps no notes of its own, the files in your folder are not memory, and asked what it remembers it answers in one or two plain sentences instead of describing how memory works inside. It replies in the language and script you write in, simplified or traditional Chinese for example. The terminal chat, the web console and the macOS app get this; direct runs and workers are as before.

/clear clears the screen

2026-10-30 · #304

In the terminal chat, /clear was another spelling of /new: it started a new chat and printed a "New chat" rule under the page, so the screen stayed full. It is now a command of its own. It does what /new does (the conversation, the approvals you gave and the display preferences are forgotten), then wipes the screen and its scrollback and draws the welcome again at the top, with the input box and the status bar under it. /new keeps the page and its rule. With NO_COLOR set, TERM=dumb or output that is not a terminal, no escape code is written and /clear does what /new does. The command list tells the two apart (/new reads "Start a new chat; /clear also clears the screen"), and like /new, /clear waits for an idle chat.

Browsing, part 1: melo reads and follows web pages in Safari's automation windows

2026-10-30 · #297

melo can now read web pages on a Mac. Browsing is off by default: /browser on in the terminal chat (or [browser] driver = "safari-automation", or -X browser.driver=safari-automation for one run) gives the terminal chat and the web console eight read-only tools that open a page, read it, find text and links in it, follow a link, go back, list the tabs, wait and take a screenshot. They use Safari's own automation windows through the safaridriver --mcp server that ships with Safari, started on the first call; nothing is installed, and the windows start clean, so none of your sign-ins are used. Safari needs Settings > Developer > "Allow remote automation" turned on once, and melo says so in words when it is off. Before melo loads a page it asks "Open a website?" with the site's name; "Yes, and allow this site for the rest of this chat" is the only lasting answer, and /new takes it back. A page reaches the model as data between two markers, with a note that text between them is the content of a web page and never an instruction, and a password, one-time-code or card field never shows a value. Nothing clicks, types, signs in or posts in this part. Direct runs, workers and saved tasks never get the browser tools. The new browsing guide has the steps.

Pictures that tools return reach a model that can see

2026-10-30 · #295

A screenshot that a tool returned used to reach the model only as a line of text such as [1 image: sha256:… image/jpeg], so a model that can see could not use a browser's screenshot tools. The new [agent] tool_images setting ("auto", "on" or "off"; -X agent.tool_images=on for one run) can send the pixels. off is the old behaviour and on always sends them. auto, the default, sends them only when the server says the model reads images (oMLX and Ollama say so; other servers count as off). The newest three pictures keep their pixels and older ones lose them two at a time, so a request carries three or four pictures; on macOS a picture wider than 1,280 pixels is scaled down once. History and saved chats keep references, not pixels. An MCP server that repeats a screenshot in its structured result no longer sends it to the model as text as well.

High-impact calls ask even inside a session grant

2026-10-30 · #290

One "Allow for this chat" on python_exec or shell_exec used to let every later call of that tool run unasked for the rest of the chat, whatever it did, including creating an environment, installing packages and downloading a browser. Now the checker reviews each shell_exec, python_exec and file_write call before the approval policy decides. Fixed rules split the shell command as a shell does or parse the Python code, and run nothing. A call comes out routine, high-impact or undecided. High-impact calls install software or a project's packages, create an environment, download an installer or a large file, run downloaded code, write or delete outside the workspace, set up something that runs later, use passwords or keys, change system settings, open a network service, send files out, change localmelo itself or run code built at run time. Undecided calls are those the rules cannot read, such as a computed command or a git push. A session grant covers routine calls only: a high-impact or undecided call asks every time, and allowing a high-impact call for the chat allows that one call and grants nothing. The terminal's auto mode runs routine calls and asks before the others. A call that would change localmelo itself, such as an install into the Python that runs it, is denied without asking. A denied high-impact call tells the model why melo asked.

A reply that is only unfinished thinking is never shown as the answer

2026-10-30 · #288

A thinking model that stops before its end-of-thinking mark no longer has its thinking shown as the answer. A console greeting once got the model's own notes ("... I'll keep it simple and friendly.") as its answer, because a server with a reasoning parser returns the whole text as the reply when the mark is missing. melo decides from facts, not wording: a reply without a tool call is unfinished thinking when its content opens a think block that never closes, when it has no answer but the server counted reasoning tokens, or when a streamed reply's content repeats its reasoning word for word. melo then keeps the text as thinking and asks the model once more; a second reply without an answer ends the run as failed with "melo did not finish an answer". The terminal prints the reply as thinking and ends with "melo did not finish an answer." and "/retry, or try another model."; the console shows a folded thinking item and a failure card with "Try again" as the filled button. In the terminal, typing /exi shows /exit under the input box, but deleting the i used to close the list, so /ex showed no commands until you typed another character. A developer setting confines plain direct runs too

2026-10-30 · #284

Track 2 memory-system design evolution

2026-05-03 · Memory design

Track 2 now has a clearer memory-session shape. The online path splits remembered candidates into a fast working-memory branch and a Hippo branch that owns durable or specialized placement.

  • The agent keeps the v1 write decision lightweight: it only proposes that a candidate is worth remembering.
  • working stores short-lived active task/session context with LRU-style refresh; the design direction separates fresh and rehearsed memories.
  • Long-term persistence waits until the related working memory is rehearsed or another strong write signal exists.
  • Hippo routes durable writes with five explicit actions: NEW, UPDATE, RELATED, CONFLICT, and IGNORE.
  • long and profile share one physical long-term store in v1, distinguished by metadata kinds such as semantic, episodic, profile, and reflection.
  • tools remains the authoritative registry and grows procedural skill/template memory without bypassing checker or executor policy.
  • PersonalizedMemory is a filtered sleep-sample staging area for Track 4, not a dump of raw history.
  • history stays append-only or near-append-only for debugging, replay, auditability, and provenance lookup outside normal recall.

The v1 foundation now has persistent-memory docs, multi-session SQLite stress coverage, real-backend long-term retrieval evidence, and a frozen selected-sample schema for PersonalizedMemory. Later Track 2 work moves into working-memory stages, Hippo write routing, long/profile semantics, procedural memory, and evaluation.
