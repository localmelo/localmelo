Roadmap Updates

Roadmap and updates

What is planned before v0.1.0, and what has changed so far, newest first.

Roadmap

The v0.1.0 milestone is due 2026-12-20. The roadmap is tracked in #2.

PhaseDatesScopeIssue
Phase 12026-10-19 to 2026-11-01Core loop v2 and the command line#3
Phase 22026-11-02 to 2026-11-22Memory: notes, retrieval and long-term promotion—none
Phase 32026-11-23 to 2026-12-06Safety and privacy#29

Planned:

  • the interactive CLI's next parts: diffs in approvals, sessions you can resume (melo -c, melo -r), attached files and shell commands;
  • conversations that survive a gateway restart, with the agent's work shown live in the web workspace;
  • keeping the model's reasoning as memory notes, with switchable retrieval (bm25, llm, embedding);
  • running several tasks at once on one local model server, with your conversation answered first;
  • a percent bar on the progress line for tasks you run again and again, off until their repeated runs pass the replay.

The maintainer's memory design, parts of which are not built yet, is on the memory design page.

Updates

The changelog lists each change since 2026-10-22 in detail.

A turn's work, as it happens

2026-10-27

  • The interactive UI now draws every event of a turn: the model's thinking as Thought for 1.2s and an excerpt, intermediate text, the last message when it differs from the answer, retries that count down, empty-reply, stuck and budget notices, and reflections, including the ones melo could not read.
  • The live area shows the run's progress facts (step, attempt, phase and cycle, tests, time), the running tool's clock and limit, and on a session's first turn a dim row of what the past runs did, worded exactly as the direct-mode progress line.
  • New commands: /verbose for longer excerpts, the tool arguments and 20 output lines; /thinking to turn the excerpt off; /expand for one tool call's whole output; /progress for the facts the live area rests on.

Forget a task's memory

2026-10-27 · #64

  • Python code can forget one task's memory or all of it: await hippo.forget(task_id) removes the task's rows from tasks, steps and llm_calls, and the long-term entries whose metadata names it (its reflections); await hippo.forget_all() empties history and long-term memory, step summaries included. Working memory, procedural memory and sessions are left alone.
  • A forget overwrites what it deletes and truncates the WAL, so the text does not stay in the database or its -wal file. There is no command or page for it yet. See Reset memory.

A session that is running a task is not closed

2026-10-27 · #63

  • DELETE /v1/sessions/<id> leaves a session whose task is still running alone and answers HTTP 409 with the gateway's error body, error and session_id; idle sessions close as before. The task keeps running, and the session can be closed after it ends.
  • Stopping the gateway still closes every session, a busy one included; a task still running then ends as crashed. The /v1/agent API still has no route that stops a run.

New memory files are private to you

2026-10-27 · #62

  • A new long_term.db, with its -wal and -shm, is created with mode 0600, as history.db and procedures.db already were. Before, it usually got 0644, so other users of the computer could read the step summaries and reflections in it. An existing file keeps its mode; a memory directory localmelo creates is still 0700.

Session turns can report their progress

2026-10-27 · #60

  • SessionRunner(..., progress=True) asks each turn's run for its run.progress events and stores them with the turn; the flag stays on the runner, replace_agent included. run_turn and start_turn take routine=NAME and pass it to the run only when given.
  • localmelo.support.progress_line.format_past(payload, width) gives the progress line's past facts and items alone, with the same wording and widths. The interactive UI does not ask for progress yet, and the line itself is unchanged.

Shell commands no longer take over the terminal

2026-10-27 · #59

  • shell_exec now gives every command /dev/null as its standard input, in every mode. A command whose standard input was a pty that was not melo's controlling terminal could take that pty as its controlling terminal and hang it up when it exited, which made a completed melo run end with exit code 120 instead of 0.

The progress line names the task it borrows from

2026-10-27 · #56

  • A similar task's past steps now say like <routine title>: instead of like a similar task:, naming the routine (its --routine name, else the start of its query).
  • A shell_exec command that arrived as an array of strings, which the tool refuses, is labelled and classified by its words, so ["ls", "-la"] reads as a read command instead of {command:. Procedural memory stores the same label.

A picked Ollama server is saved as Ollama

2026-10-27 · #55

  • The first run, the Save URL · MODEL as the default backend? question after --base-url, and /backend used to save every server as vllm. Saving now asks the server GET /api/version once: one that answers like Ollama is saved as the ollama backend, with Ollama's own API and a 300 s chat timeout; any other OpenAI-compatible server is still saved as vllm.
  • A saved Ollama server used to run with vLLM's 120 s chat timeout, and the banner called it vLLM.

An interactive UI in the terminal

2026-10-27 · #53

  • In a terminal, melo without a task now opens a chat that shows its work: a banner with the model, the workspace and the tools, each tool call as a block with the first lines of its output, a spinner with the step and the time while the model works, and the answer as Markdown. It replaces the conversation loop of the next entry; melo "" keeps that loop.
  • Type / to see the commands and what they do. /model and /backend switch the model and the server, and save them as the default (a session opened with --base-url saves nothing); /new starts a new conversation.
  • Commands, Python and file writes ask first: allow once, allow the tool for the session, or say no with a reason. --yolo skips the questions, and --workspace DIR sets the folder the file tools stay in.
  • Chinese and other wide characters type, delete and wrap whole. Esc stops a turn, the Up arrow recalls earlier messages, and Alt+Enter or Ctrl+J starts a new line.
  • Without a terminal, melo now says what to run instead and exits with code 2; melo --serve starts the gateway. See The interactive UI.

Type melo to start a conversation

2026-10-27 · #52

  • In a terminal, melo without a task opens the conversation loop on the saved model server, and names the model and the server first. It used to start the gateway; melo --serve still does, and so does melo without a terminal.
  • The first time, with no configuration, melo looks for a model server on this computer, asks you to confirm its URL and to pick a model from the server's list, and saves both. It only asks the server for its model list, so no model is loaded for it.
  • melo --base-url URL without a task opens the loop on that server, with the first chat model it lists unless you name one with --chat-model.
  • The setup wizard keeps your saved values as its defaults, lets you retry a failed check, and explains an HTTP 401 from a local server: localmelo sends no API key to local servers. Without a terminal, melo --serve with no configuration prints one line instead of a traceback.

A progress line in the terminal

2026-10-27 · #51

  • While melo "<task>" runs on a terminal, one dimmed line on stderr shows the step, the phase, the running tool and the time. It is erased before the answer.
  • When the task has run before with memory kept (--memory-dir), the line adds what the last run took and its steps; a similar task's runs are marked as such. --routine NAME groups differently worded runs of one task.
  • The line never wraps, draws nothing in the background, and never holds up the run, even when the terminal's output is paused. --progress off turns it off. Pipes, files, --output-format json and the exit codes are unchanged. See Progress line.

Runs learn the steps of recurring tasks

2026-10-27 · #46

  • Each run that ends normally now records what it did in procedural memory: the classes of its tool calls, short labels, its steps and its time. A run that completed also updates the step template of its task. With persistence on this goes to procedures.db in the memory directory; otherwise it stays in RAM.
  • A Python caller can follow a run with run.progress events (progress=True): the step, the phase and the test counts, and, for a task done before, what earlier runs took and their named steps. The percent bar stays off until replayed runs show that it is reliable.
  • Request bodies, the output, the JSON line, the exit codes and the history rows are unchanged.

Groundwork for a progress display

2026-10-26 · #45

  • Procedural memory learns the steps of a task you run again and again, such as a test suite you fix every day. From earlier runs it keeps the kinds of tool calls they made, short labels, and how many steps and how long they took, never what the model said.
  • A first run is exploration and gets no estimate. Once a task has completed runs, a display can show what they took; a percent bar also needs runs that agree with each other and a model whose past estimates were close. On the benchmark runs measured so far, that check did not yet tell good estimates from poor ones clearly enough, so the planned progress display starts without the bar.
  • melo-procedures learns these step templates from a history.db and replays the rules offline, so they are measured before anything is shown. Runs do not read or write procedural memory yet.

Every model call kept in history

2026-10-26 · #42

  • With persistence on, history.db keeps every reply of the model with its reasoning: one row per planning or reflection reply, linked to the tool steps it made. The planned memory of the model's reasoning will be built from these rows.
  • Text and reasoning pass a minimal redaction of secrets, and reasoning is kept for 30 days (LOCALMELO_THINKING_RETENTION_DAYS changes it). melo-retrieve --export-run turns a run's calls into a corpus for comparing retrievers.
  • Each chat request names its kind in an X-Localmelo-Call-Kind header, so a proxy can tell planning from reflection. The JSON line, the exit codes and the request bodies are unchanged.

Conversations that survive a restart, in the Python API

2026-10-26 · #41

  • A session keeps a conversation in SQLite. Each turn begins with a stored row and ends exactly once with a status and a cause, also when the process that ran it stops or dies, and a fresh agent can resume the conversation.
  • A message sent twice with the same request id runs once, the last turn can be undone, and a person can answer a tool's approval request from another page. An event stream replays to a client that reconnects every event it missed.
  • Sessions are part of the experimental Python API. melo and the gateway do not use them yet: the planned interactive CLI and web console will keep their conversations there.

Groundwork for running several tasks at once

2026-10-26 · #39

  • A scheduler will share one local model server between your conversation, background tasks and chats. Its policy decides which model call goes next and why a task waits, and keeps your conversation answering first.
  • A simulator replays workloads through the policy, so its variants can be compared offline, on synthetic workloads or on traces from the benchmark.
  • Nothing uses the scheduler yet: runs and the gateway work as before. The next step puts it in front of the model server.

Compare memory retrievers offline

2026-10-26 · #38

  • melo-retrieve runs labelled queries against a corpus with the bm25, llm or embedding retriever and reports how often each finds the right documents, and how fast.
  • It can also turn a run's model calls into such a corpus: notes on the model's reasoning, code drafts and chunks of its thinking.
  • melo does not use these retrievers yet. A benchmark comparison decides which one becomes the default.

A web workspace and a conversation in the terminal

2026-10-26 · #35

  • The gateway's page is now a web workspace: pick a model from your server, keep several chats with their own drafts, search them, read answers with code, tables and links, and stop a run. It also fits a phone-sized screen.
  • Chats last while the gateway runs, and reloading the page brings them back.
  • In a web chat, the melo "" loop and a gateway session, each message sees the earlier answers.
  • melo "" opens a conversation in the terminal. melo on its own still starts the gateway.

Events, stopping and approvals in the Python API

2026-10-26 · #37

  • Python code can follow a run as it happens: run_task(..., on_event=sink) reports each step, model reply, tool call and reflection, with secrets redacted.
  • A run with an event sink or an approval policy can be stopped: it ends as cancelled, and the interrupted step is closed cleanly.
  • An approval policy decides whether shell_exec, python_exec, file_write and other marked tools may run, and AgentOptions(workspace_root=...) keeps the file tools inside one directory.
  • Conversations can carry over between runs and agents. Direct mode and the gateway are unchanged.

The gateway refuses requests from other sites

2026-10-26 · #36

  • On localhost or a loopback IP address, such as the default 127.0.0.1, the gateway refuses requests whose Host is not 127.0.0.1, localhost or [::1] with its port (HTTP 421), and requests that web pages at another origin send through your browser (HTTP 403). A web page can no longer reach the gateway through DNS rebinding and run tasks with your tools.
  • No web page can show the gateway's pages in a frame.
  • On any other host, such as 0.0.0.0, the gateway makes no such checks and logs a warning when it starts: it has no authentication.

Reflections stop fewer unfinished runs

2026-10-23 · #34

  • Before, a reflection could end a run whose task was unsolved although attempts and steps were left: its own utility score had to reach a threshold, and a reflection that could not be read, or was too long, ended the run.
  • Now the next attempt starts when the reflection chooses continue and its three checks hold. An unreadable reflection no longer ends a run that has attempts and steps left, and a long one is trimmed. --reflection-gate utility keeps the earlier behavior.
  • On 12 coding exercises run 5 times each with one local model, the new default passed 59/60 runs and the earlier behavior 50/60. Runs without reflection (--attempt-policy none) passed 59/60 too: the new default matches them and does not beat them.
  • Conditions and limits: Evaluations.

Run options, run results and exit codes

2026-10-22 · #25, #26, #27, #28, #30, #31, #32

A direct melo "<task>" run is now something a script or a benchmark can drive.

  • Run options: --max-steps, --attempt-policy, --tool-exposure, --builtins, --memory, --memory-dir and --timeout; --embedding-base-url and --embedding-model for long-term memory in a --base-url run; and AgentOptions in the Python API (#30).
  • Every run ends with one of nine statuses. --output-format json prints the run record as one JSON line, and the exit code is 0 for completed, 1 for crashed and 2 for any other status or a usage error (#30).
  • Failed model requests are retried when a retry may succeed, and --request-timeout and request_timeout_s set the chat request timeout (#30).
  • SIGTERM and SIGHUP end a direct run within 8 seconds, with its task record saved (#30).
  • A step runs only the tools it offered, and a built-in tool call whose arguments have the wrong type is refused before it runs (#30).
  • Tools from local MCP servers, with --mcp-config and --mcp-only, and tools that return images (#27, #30).
  • Tool calls reach OpenAI-compatible models as real tool-call turns, every call of a step runs, and extra_body adds fields to chat requests (#26).
  • A reflection reply without a JSON object is asked for once more, without tools (#31).
  • #32: in retrieve mode, every step offers all registered built-in tools, then the extra tools found by hints and by BM25 with IDF, both sorted by name.
  • The MIT license (#28), and a uv development environment with a committed uv.lock (#25).

Real-backend memory test archived

2026-05-10 · #4

Long-term memory that persists across sessions was tested with three local servers, oMLX, Ollama and MLC LLM, all with the same Qwen3 0.6B embedding model family. All three completed the four scenarios. The scores and end-to-end times are in the archived summary; they were measured on the 2026-05-10 code. oMLX is an OpenAI-compatible server, tested through its endpoint; it is not a built-in backend.

Track 2 memory-system design evolution

2026-05-03 · Memory design

Track 2 now has a clearer memory-session shape. The online path splits remembered candidates into a fast working-memory branch and a Hippo branch that owns durable or specialized placement.

  • The agent keeps the v1 write decision lightweight: it only proposes that a candidate is worth remembering.
  • working stores short-lived active task/session context with LRU-style refresh; the design direction separates fresh and rehearsed memories.
  • Long-term persistence waits until the related working memory is rehearsed or another strong write signal exists.
  • Hippo routes durable writes with five explicit actions: NEW, UPDATE, RELATED, CONFLICT, and IGNORE.
  • long and profile share one physical long-term store in v1, distinguished by metadata kinds such as semantic, episodic, profile, and reflection.
  • tools remains the authoritative registry and grows procedural skill/template memory without bypassing checker or executor policy.
  • PersonalizedMemory is a filtered sleep-sample staging area for Track 4, not a dump of raw history.
  • history stays append-only or near-append-only for debugging, replay, auditability, and provenance lookup outside normal recall.

The v1 foundation now has persistent-memory docs, multi-session SQLite stress coverage, real-backend long-term retrieval evidence, and a frozen selected-sample schema for PersonalizedMemory. Later Track 2 work moves into working-memory stages, Hippo write routing, long/profile semantics, procedural memory, and evaluation.

Saved memory, bounded reflection and setup checks

2026-04-29 · #8 to #20

  • Saved memory (history and long-term memory in SQLite, when persistence is turned on) moved to asynchronous aiosqlite, with serialized writes.
  • Working memory keeps only the latest reflection, and a reflection over its size limit stops the run instead of growing the prompt.
  • The setup wizard sends a test request to each server before it saves the configuration.
  • Chat, the agent's model wrapper, became internal: Agent is the public entry point.
  • The docs gained minimal check commands for each mode, and tests/smoke/ gained pytest checks against real local backends.

Backend registry and an agent loop with attempts

2026-03-29 · #5

  • A backend registry with local adapters for Ollama, MLC LLM, vLLM and SGLang, and cloud adapters for OpenAI, Anthropic, Google Gemini and NVIDIA.
  • Chat and embedding backends chosen separately (chat_backend and embedding_backend).
  • An agent loop with attempts, a structured reflection between them, and a gate that decides whether to continue.
  • A chat provider for Ollama's own API that separates the model's thinking from its answer.
  • Benchmark scenarios and reports for comparing backends.

Initial code layout

2026-03-25

  • Provider interfaces in melo/, so the agent does not depend on any one backend.
  • Scaffolding for an offline melo/sleep/ package, which the agent does not use.
  • Tests for the new layout.
