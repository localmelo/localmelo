Updates

The changelog lists each change since 2026-10-22 in detail.

Task command

Unreleased

melo-task creates, inspects and controls gateway tasks, and follows their events. Terminal state does not guarantee complete event replay.

Clearer Python check labels

Not yet released

Attempt digests name a recognizable Python test runner and, when safe to show, a target's basename instead of the first code line. Other Python checks use a neutral label. Results use counts, an exit code or completed, not arbitrary output. Hidden paths and agent scratch notes are omitted; Python file writes are not inferred as files. Verification eligibility is unchanged.

Worker briefs and event streams

Unreleased

Direct workers read a brief and return a versioned JSON result or stream events; inbox steering follows separately.

Negative and Chinese notes

Unreleased

Heuristic notes can retain some English negative and Chinese residence or cancellation assertions verbatim; source matching is more conservative for negatives and conflicting event times. Coverage is limited; similar assertions with opposite detected polarity are kept as conflicts, not silently deduplicated.

Worker history in the workspace

2026-10-28 · #130

Workers lists saved and imported runs with filters and paging. Each run opens as a read-only snapshot; refresh unfinished runs manually. Review redacted records before sharing.

Optional fixed prefix

Unreleased

A versioned prefix freezes the local date and stable instructions per run. Schema changes are reported as expected invalidations, not measured cache misses.

Optional captured history

Unreleased

Keep a bounded, pattern-redacted tool-result copy separate from the model preview. Tool-side acquisition omissions may be unknown, and redaction can miss secrets.

Opt-in context accounting

2026-10-28

Planning and reflection attempts report estimates and fit request copies to the configured budget. This is not a context bound, and the output reserve is not enforced. See configuration.

Session details and appearance

2026-10-28 · #124

The workspace adds a details drawer for tools, grants, memory and runs, plus connection testing and a saved theme preference. Store, model and reconnect banners remain visible alongside other notices.

Worker history

2026-10-28 · #123

Direct runs can be saved as worker sessions, dsh JSONL logs imported, and the history filtered and read through the local gateway API. Redaction is pattern-based; review records before sharing.

Workspace controls and recovery

2026-10-28 · #122

The workspace adds connection settings, earlier-turn paging, failure and stopped controls, and per-tab outbox recovery. Approval cards render pending requests with a 500 ms guard; console sessions ask before file_write and python_exec, while legacy /v1 has no approval policy. See the web workspace guide.

An attempt's digest says what the attempt did

2026-10-28 · #116

  • In the compress modes, an attempt's digest now names the paths its successful file_write calls wrote (at most six, workspace-relative, then +N), the last shell_exec or python_exec check and its result (test counts, exit code or last output line), up to three decisions, and the task's first sentence or heading instead of a fixed 300-character cut.
  • An observed line that is empty or only a boolean, None, an exit code or punctuation no longer enters a digest or makes one a rehearsal candidate. Over the limit, open questions drop first, then observed lines, decisions, facts and files, then the task shortens; the outcome and the verification stay. legacy and direct mode without memory are unchanged. See reasoning notes.

A whole terminal chat in a reasoning and recall mode

2026-10-28 · #115

  • The interactive UI now takes the reasoning and recall options for every turn of the session: --reasoning, --reasoning-field, --replay-turns, --note-writer, --retriever, --recall-* and --retrieval-extra-body, from flags or the saved [agent] and [retrieval] tables. Explicit flags win, retrieval flags stay inert in legacy, and there is no /reasoning command; /model and /backend keep the mode across a switch.
  • Console sessions run the configured reasoning mode (default legacy) and the saved recall settings without changing legacy /v1. A resumed chat uses the retained window under the current process's mode: pairs resume without old thinking, while a checkpoint resume can send retained, redacted thinking, and a rejected mode switch keeps the old agent and closes the new providers.
  • [agent] tool_env names extra environment variables that shell_exec and python_exec inherit in config-backed direct runs, the UI and console sessions. Names are validated and missing variables skipped, only names are saved, and --base-url runs and sessions expose nothing new; SSH-agent and proxy access are explicit capability grants. See the interactive UI and tool environment.

Heuristic notes keep real facts and cite the right record

2026-10-28 · #114

  • Replies without a note block can yield up to 12 keyed facts, and an explicit note can also hold 12. Questions, options, plans and negated or cancelled statements are not promoted as positive facts, and a claim about the agent's own work is filtered unless a keyed content clause follows it; task:/code markers and completed outcome digests stay exempt.
  • Source matching scores typed keys independently, keeps date years, currencies and whole phone numbers, rejects conflicts, and leaves ties and unmatched items unsourced even after admission. Bare slash dates use US order when ambiguous; quantity/count contexts, mixed numbers and 24/7 are excluded, and digit runs over 20 characters are ignored. Extraction is still heuristic and CJK-only keys are not extracted. See reasoning notes.

The gateway's session file can hold the scheduler's tasks

2026-10-28 · #113

  • sessions.db gains the scheduler's component version 1: tasks, task_deps, priority_events, questions, sched_rules, sched_log and idle_windows, created in one transaction in that file only. PRAGMA user_version stays the session schema's, a newer component is refused, and a second gateway on the same file is refused by its owner lock.
  • A task's id is its kind="task" session's id, and the task is created with that session, its first priority event and a log row in one transaction. UNIQUE(origin, request_key) makes a repeated create idempotent while a reused key with a different payload is a conflict, and an actual level change writes a priority event and the log. TaskSpec normalizes an untrusted request, pins a user-selected P0-P5 only through the trusted adapter, and resolves a worker's folder under the user's home or [gateway] workspace; the user's P0 is single. Only user and user_rule origins get remembered approvals, unmarked MCP tools and session grants, and 30-day retention clears the log and idle windows.
  • ChatGate.register_task() gives a worker its task lifecycle: its calls are logged as session_kind="task", never take the lane, and only the runner ends it. No /api/tasks route or worker run is on main yet; the console wiring is next. See the scheduler.

The web console's page shows a chat as it runs

2026-10-28 · #111

  • The page at / now talks only to /api: the session list with its machine snapshot, one chat's turns, its event stream (SSE, reopened from the last applied event id), keyed sends that the store is asked about before Retry is offered, stop, close, the level chip and the typing heartbeat. A refused or unknown send goes back to the chat's draft, so a reload keeps it, and #/s/<id> opens a chat even when the list's first page does not hold it.
  • A turn reads as the terminal's: the user's message, a work group with one card per tool call (Running, Waiting: <held>, Needs approval, [ok] with a non-zero exit, blocked, not run, Interrupted), folded reasoning and reflections, notices, the live row (step 4 · attempt 2 · Verify (cycle 1) · tests 3/8) and the answer with its duration, steps, tokens and Copy response. The page is plain ES modules with no build step.
  • The console's sessions persist in ~/.cache/localmelo/gateway/sessions.db and reopen from their transcript, and the page uses the gateway's configured model. Connection settings, approval cards and the failure block's Continue/Try again follow in a later update; until then a waiting approval shows as Needs approval. / and every /v1/* route keep their behaviour. See the web workspace.

Direct and Python runs no longer offer shell_exec by default

2026-10-28 · #110

  • Direct mode and the Python API's default python mode now register only file_read, file_write and python_exec. --builtins all (or naming shell_exec) restores the old set, and a named shell then runs; --builtins is still a usage error with --serve and --daemon. A call to a built-in the run does not offer returns shell_exec is not available in this run. Available tools: …, naming the run's tools.
  • The six-pattern command blocklist is gone: the tool's tier and the run's mode decide, not the command's spelling. The JSON line's config gains mode, and config.builtins and config.tools lose shell_exec in a direct run. The melo "" loop says once at start that shell_exec is off and that melo "" --builtins all turns it on. The benchmark measured 12 of 12 tasks with the default set and 11 of 12 with the shell on. See the command line.

Gateway and console sessions no longer offer shell_exec

2026-10-28 · #104

  • Gateway and console sessions now run in a new gateway tool mode and register only file_read, file_write and python_exec: shell_exec is not registered at all, so the model never sees it. Legacy /v1 has no approval policy; console sessions ask before file_write and python_exec. The console's approvals arrive over the same unauthenticated loopback API, so any local process could approve its own request; Python code can still start a process. A gateway or console session cannot be given shell_exec by its default set, and an explicit AgentOptions(builtins=…) that names it is refused by the checker in gateway mode, with the mode and --builtins all in the reason.
  • AgentOptions gains mode: direct, interactive, gateway or python, the Python API's default, and the command line sets its surface's mode. The interactive UI keeps shell_exec behind its approval panel (--yolo asks nothing). Direct mode and the Python API's default follow in the tool-defaults update above. See permission tiers and the Python API.

A note's facts cite the results that established them

2026-10-28 · #103

  • A note's items now take their source_ids from the observation that established them, even when it came in an earlier reply of the same task: the reply's own tool results first, then the results still in the window, then the rest of the task's records, newest first, up to the last 200. A record matches only on a strong key (a number, a date or time, an identifier containing a digit, or a capitalised name that does not start its sentence) or two distinctive non-filler words; a note with records but no match gets no item source, so “Done.” no longer cites an unrelated “no harm done” record. This fills provenance.source_ids for facts copied from an earlier tool result and for the digest built from them, and another task's records are never used.
  • The recall header the model sees no longer carries the retrieval latency: it is (retriever bm25), not (retriever bm25, 12 ms). Identical runs now produce identical prompt bytes, so a block kept in the window does not break the prefix cache; the time stays in llm_calls.recall_json, in the recall event and in memory_stats. See recall in the loop and long-term memory.

Name, undo, inspect and copy a terminal chat

2026-10-28 · #101

  • /title [text] shows or sets a 1–200-character title, including before the first message: it is kept until the session is created, and /new or a successful resume clears an unsaved one.
  • /undo forgets the newest finished turn and keeps its typed message in the ↑ history; files and commands it ran stay changed. A committed undo reports success even after Esc, and /retry re-runs that undone turn without removing the previous live one.
  • /usage shows the recorded steps, tool calls, tokens and time of each turn, undone work included, with ? for a missing counter, +? on a partial total and labeled rows below 72 columns; /memory inspects a copy of the working window, its counts, the long-term backend and the restore mode actually used, without a model call or a memory write.
  • /copy [turn] copies a stored, redacted answer's Markdown instead of the wrapped display, keeping indentation and trailing newlines; an explicit turn number may pick an undone answer. On macOS it uses pbcopy, and under SSH, elsewhere or when that fails it sends an OSC 52 request and says so; nothing touches the clipboard without the command. See Inspect, undo or copy a conversation.

A remember request stores the fact it carries

2026-10-28 · #100

  • A request such as Remember that … or 记住… now also stores the fact it carries after the marker, admitted by user_request beside the run's episodic digest, instead of storing only the digest. The fact is semantic unless it is first-person (profile), the redaction, meta-noun and question rules apply to it, and a to-do such as remember to buy milk still stores no fact.
  • A thought chunk is now superseded at its attempt's boundary together with that attempt's notes, so a later recall renders it with the (superseded) marker and names its attempt instead of passing for the current attempt's thinking.
  • melo-retrieve --export-store DIR and --export-decisions DIR print zero entries and exit 0 when the directory has no long_term.db yet, instead of failing with “No such file”; a path that is not a directory keeps the missing-file usage error. See long-term memory and offline retrieval.

A task run can work in --workspace DIR

2026-10-28 · #98

  • --workspace DIR now works with a task, not only in the interactive UI: the run sets the same workspace_root the Python API takes, so file_read and file_write stay inside the folder and shell_exec and python_exec start there. Without the flag a run keeps the current folder, exactly as before; ~ is expanded and the path resolved like the UI's.
  • A path that is not a folder exits 2 with one line, melo: --workspace: not a directory: DIR, and melo "" and --serve refuse the flag like every other direct-mode option. Direct mode still has no approvals; the folder limits only the file tools. See the command line and with a workspace root.

Long-term memory keeps only what it can vouch for

2026-10-28 · #97

  • long_term.db is now a typed store: each entry has a kind (semantic, episodic, profile or reflection), a source, a status, the signal that admitted it and its provenance (task and session ids, step and attempt, the paths and commands it touches) beside the text and the vector, plus a decisions table. An existing file migrates in place to user_version 1, its rows and the search order intact.
  • A candidate is admitted only by a rehearsal (a later note restating it, a successful call acting on it, a reflection citing it), a user request or statement, or --admit-on-outcome on for the final attempt digest; the policy picks NEW, UPDATE, RELATED, CONFLICT or IGNORE, and every stored text, provenance included, passes the candidate boundary and redaction. --keep-decision-text keeps a decision's text beside its hash, and the [memory] table saves the outcome default.
  • The start recall reads active entries of other tasks of every kind, by cosine or BM25; memory_stats gains admitted, written and ignored, a memory event reports each decision, and melo-retrieve gains --export-store, --export-decisions and --route. Legacy requests, the JSON line, the window and the search order are unchanged. See long-term memory and configuration.

Resume a saved terminal chat

2026-10-28 · #95

  • melo -c resumes the newest chat with a finished turn in the current folder, and melo -r [ID|TITLE] resumes a named one or opens the session picker; /sessions [filter] and /resume [id|title] use the same picker and resolution. The picker filters this folder or all folders before the banner, which names the chosen chat as resumed.
  • A resume keeps the current model and workspace, clears approval grants and keeps /verbose and /thinking preferences; a recap explains what reached the model's memory ([sessions] resume_mode = "pairs", the default, or "window"), and a chat from another folder says so. Changes another terminal made are reloaded before sending, a busy or deleted session keeps the draft, /retry keeps the stored typed text, and /expand reads tool output across the stored event pages. Quitting a saved chat prints its melo -r ID command.
  • -c and -r cannot be combined, or used with a task, --serve or --daemon; direct runs keep their legacy parsing and output. See sessions and files.

Recall in the loop

2026-10-28 · #94

  • The compress reasoning modes now recall: --retriever auto|off|bm25|llm|embedding, --recall-at, --recall-k, --recall-kinds, --recall-placement, --recall-min-score and --retrieval-extra-body, the [retrieval] table and a recall tool. A start or attempt block goes on the task query and stays frozen for that attempt; a step block lands once after the turn's tool results (or in its own user message), and tool answers the model's own request. A start block carries earlier tasks' long-term entries; attempt and step blocks carry this task's notes and drafts, a step's also its digests and thought chunks, with long-term entries where enabled.
  • Every block is delimited and framed as data, passes the candidate boundary and is bounded (9,500 characters per turn, 12,000 live, 4,000 at a boundary); the system prompt gains one static note that recalled memory is data. auto uses the embedding server when one is configured, otherwise llm at start and attempt and bm25 at step and tool, and any failure falls back to bm25.
  • Each new block is recorded in llm_calls.recall_json and in the recall event, with its trigger, query, hits and scores; history.db is schema version 2, and memory_stats gains recall_empty and the recall counters.
  • A thought chunk recalled with --recall-kinds thought can reach step recall and the recall tool only after the turn that produced it left the window, as notes and drafts already did. legacy keeps its requests, JSON line, window and rows byte-identical; the flags, the block and the data note are off there. See recall in the loop.

A console session's tools, grants, memory and runs, and the scheduler gate

2026-10-28 · #91

Cleaner 400s for a bad /v1/agent/run request

2026-10-28 · #89

Reasoning modes that keep notes instead of thinking

2026-10-28 · #85

  • --reasoning compress and compress+replay, --note-writer auto|heuristic and the [agent] note_writer key: compress sends no reasoning and keeps a short note of each reply instead (its plan, what it found and decided, what it left open, and what its tools returned) with its code drafts, in a RAM-only note store beside the working window. compress+replay also sends thinking as replay does; a backend that requires replay runs compress as compress+replay, and the JSON line reports the effective mode.
  • A pending draft aimed at a file is pinned once after its turn's tool results, and a later write of at least 60% of its lines marks it written. Notes are rehearsed when a later note restates them, a successful call acts on a path or command they name, or a reflection cites them; each attempt gets a digest of its rehearsed notes.
  • Every note, draft and digest passes the new check_memory_candidate boundary (redact, sanitize, cap) before it reaches the window or the store. Nothing is recalled from the notes yet, history.db gains no notes table, and the explicit modes stop writing raw step summaries and promoting reflections to long-term memory; a session turn's note column gets the final digest. legacy is byte-identical. See the guide.

Tools run with a minimal environment

2026-10-28 · #81

  • shell_exec and python_exec start their child with PATH, HOME, USER, LOGNAME, SHELL, TERM, LANG, every LC_* variable and TMPDIR, plus the new AgentOptions(tool_env={...}), and nothing else. An API key in melo's environment reaches no tool unless tool_env names it; VIRTUAL_ENV, PYTHONPATH, SSH_AUTH_SOCK and the proxy variables pass only through tool_env.

Tool hints come from the model's own calls

2026-10-28 · #80

  • In the default retrieve mode, the extra tools a step offers are the ones the model has already called in the conversation and the three closest matches for the task by keyword search. A tool named in the task, in a tool result, in recalled memory or in a reflection no longer offers that tool, so text in a run cannot put back in front of the model a tool it never called.
  • The built-in tools and the re-offer after a refused call are unchanged, and all still offers every registered tool on every step.

Python code always runs in a child process

2026-10-28 · #79

  • Python code now runs in a child Python in every mode, not only with a workspace root: code that loops, sleeps or calls os._exit() no longer holds or ends melo. The tool's time limit (60 seconds by default, 10 minutes in the interactive UI) and a run's timeout_s kill the child with every process it started; the child also gets a one-hour CPU-time limit and an open-file limit of 1,024.
  • The code reaches the child on its standard input, a pipe, never in its command line, so ps does not show it and a call has no argument-length limit; the child then gets end-of-file on standard input. The code runs as __main__ with sys.argv == ["-c"] in a fresh namespace, so module state does not carry from one call to the next, and writes to stdout or stderr, from a subprocess too, are the call's output instead of melo's.
  • A failure now reads Python exited with code <n>: and the end of the child's output instead of the exception's text, and sys.exit(0) is a success.

Choose how a reply's reasoning is sent back

2026-10-28 · #78

  • Direct runs take --reasoning legacy|drop|replay (the default is legacy), --reasoning-field (auto, reasoning_content or reasoning) and --replay-turns N, or the [agent] keys reasoning and replay_turns in config.toml. legacy leaves the request unchanged, drop never sends reasoning, and replay sends it on the assistant turns in scope, by default only the current task's.
  • replay keeps at most 40,000 characters of one turn's reasoning (a longer turn's reasoning is skipped and counted); a backend with requires_reasoning_replay = true gets every assistant turn in the window, keeps the final answer's thinking when record_answers is on, and refuses drop.
  • Outside legacy, the JSON line adds config.reasoning, config.replay_turns, usage.reasoning_chars and the memory_stats replay counters; a legacy record is byte-identical to before. The interactive UI gained --reasoning-field in #115.

The gateway reads the GPU lock and the battery

2026-10-28 · #76

  • The web workspace's header shows a foreign GPU lock (holder and purpose, with (recorded) or (chats wait)), your own lock, an unreadable lock, · ETA passed, and the battery percent and state on battery power. The same change is logged to machine.jsonl beside calls.jsonl.
  • [scheduler] lock_gate defaults to record: the lock and battery are shown and logged and no request changes. wait holds every workspace call, embeddings included, while a foreign lock is present; the chat says Waiting: Reservation.

The web workspace's chats go through the scheduler

Approvals ask by permission tier

2026-10-27 · #66

Track 2 memory-system design evolution

2026-05-03 · Memory design

Track 2 now has a clearer memory-session shape. The online path splits remembered candidates into a fast working-memory branch and a Hippo branch that owns durable or specialized placement.

  • The agent keeps the v1 write decision lightweight: it only proposes that a candidate is worth remembering.
  • working stores short-lived active task/session context with LRU-style refresh; the design direction separates fresh and rehearsed memories.
  • Long-term persistence waits until the related working memory is rehearsed or another strong write signal exists.
  • Hippo routes durable writes with five explicit actions: NEW, UPDATE, RELATED, CONFLICT, and IGNORE.
  • long and profile share one physical long-term store in v1, distinguished by metadata kinds such as semantic, episodic, profile, and reflection.
  • tools remains the authoritative registry and grows procedural skill/template memory without bypassing checker or executor policy.
  • PersonalizedMemory is a filtered sleep-sample staging area for Track 4, not a dump of raw history.
  • history stays append-only or near-append-only for debugging, replay, auditability, and provenance lookup outside normal recall.

The v1 foundation now has persistent-memory docs, multi-session SQLite stress coverage, real-backend long-term retrieval evidence, and a frozen selected-sample schema for PersonalizedMemory. Later Track 2 work moves into working-memory stages, Hippo write routing, long/profile semantics, procedural memory, and evaluation.
