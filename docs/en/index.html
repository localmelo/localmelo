localmelo

A local personal agent that runs tasks with tools and memory on your own model server or a cloud API. It runs from the command line or as a small HTTP service.

pre-alpha
Get started GitHub ↗

Quick start

You need Python 3.11 or later, Git and uv, on macOS (developed and tested) or Linux (should work, untested). Windows is not supported. Install it with uv (or with pip):

Keep the directory name localmelo: the package is built from it.

Start a model server, for example Ollama with a model pulled by ollama pull qwen3:8b, and run a task. The answer is printed on stdout.

What you can do

Each card opens the matching reference page on GitHub.

Run tasks Run one task per command, within a step budget, with reflection between attempts and an optional time limit, or chat in the terminal with melo: it shows the model's thinking, each tool call and the run's progress as they happen, shows the diff a file write will make before you approve it, asks before it runs a command or writes a file, and resumes a saved chat in the folder with melo -c or melo -r; /title, /undo, /usage, /memory and /copy name, undo, inspect and copy the conversation. Tools and MCP Use four built-in tools and the tools of local MCP servers: a gateway or console chat gets three, without shell_exec; each step offers the built-in tools, the ones the model has already called and the closest matches for the task, and runs only those; their children get a minimal environment plus tool_env, and a Python call runs in a child process that its time limit can stop. Model servers Connect to Ollama, oMLX, MLC LLM, vLLM or SGLang servers that you run, or to the OpenAI, Anthropic, Google Gemini or NVIDIA API. Gateway and web workspace Serve the agent over HTTP with sessions, and use it from a web workspace with your server's models. Worker history Optionally save direct runs or import dsh logs, then read and filter their history through the local gateway API. API v2 Read the web console's sessions, turns, stored events (a Server-Sent Events stream too), image blobs, submission lookups, tools, grants, memory and runs over /api, and create a session or start, retry, stop and approve its turns there; it is loopback-only and only grows. Memory Keep working memory, a history of tasks and steps, and long-term memory with an embedding server, saved to SQLite when you turn persistence on; the saved text is redacted, long-term entries are typed and admitted only by a rehearsal, a user statement or the opt-in outcome digest, the compress reasoning modes keep a short note of each reply in RAM and recall it at start, attempt and step, and you can forget a task's memory or all of it from Python. Embedding setup Add the embedding model long-term memory needs: the first run or the setup wizard offers one the chat server already lists, with steps for Ollama, oMLX, vLLM, SGLang and MLC. Python API Experimental Run tasks from Python code: follow each step as an event, stop a run, approve tool calls, and keep the file tools inside one directory. Memory retrieval Compare the bm25, llm and embedding memory retrievers on labelled queries with melo-retrieve; the compress reasoning modes use the same retrievers in the loop, and auto picks one. Scripts and benchmarks Read one JSON line per run and a fixed exit code, so scripts can rely on the outcome, and choose how a reply's reasoning is sent back or kept on later turns (--reasoning legacy, drop, replay, compress or compress+replay).

Roadmap

The v0.1.0 milestone is due 2026-12-20.

Compress-mode memory can extract keyed facts from replies; source attribution remains heuristic and can leave facts unsourced.

Planned:

  • the interactive CLI's remaining parts: attached files and shell commands;
  • a console page that shows the agent's work live, and web-workspace chats that survive a gateway restart (the console's sessions already persist and reopen after one);
  • running several tasks at once on one local model server, with your conversation answered first;
  • a percent bar on the progress line for tasks you run again and again, off until their repeated runs pass the replay.

See the roadmap and updates for the phases, their issues and dated changes.

Security

Tools run with your account's permissions, and there is no sandbox. The model can run shell commands and Python code, and read or write any file you can. New memory files are created readable only by you (mode 0600). The gateway has no authentication, so keep it on 127.0.0.1 (the default): there it refuses requests to its API that web pages at other sites send through your browser.

Read the security policy and what the checks do.

Pre-alpha: commands and APIs may change before v0.1.0.
