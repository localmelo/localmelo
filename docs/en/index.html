localmelo

A local personal agent that runs tasks with tools and memory on your own model server or a cloud API. It runs from the command line or as a small HTTP service.

pre-alpha
Get started GitHub ↗

Quick start

You need Python 3.11 or later, Git and uv, on macOS (developed and tested) or Linux (should work, untested). Windows is not supported. Install it with uv (or with pip):

Keep the directory name localmelo: the package is built from it.

Start a model server, for example Ollama with a model pulled by ollama pull qwen3:8b, and run a task. The answer is printed on stdout.

What you can do

Each card opens the matching reference page on GitHub.

Run tasks Run one task per command, within a step budget, with reflection between attempts and an optional time limit, or chat in the terminal with melo: it shows the model's thinking, each tool call and the run's progress as they happen, shows the diff a file write will make before you approve it, asks before it runs a command or writes a file, and resumes a saved chat in the folder with melo -c or melo -r; /title, /undo, /usage, /memory and /copy name, undo, inspect and copy the conversation, and a whole chat can run in a reasoning and recall mode (--reasoning, --retriever and the recall options). Tools and MCP Use four built-in tools and the tools of local MCP servers: a gateway or console chat gets three, without shell_exec; each step offers the built-in tools, the ones the model has already called and the closest matches for the task, and runs only those; their children get a minimal environment plus tool_env, and a Python call runs in a child process that its time limit can stop. Model servers Connect to Ollama, oMLX, MLC LLM, vLLM or SGLang servers that you run, or to the OpenAI, Anthropic, Google Gemini or NVIDIA API. Gateway and web workspace Serve the agent over HTTP, with sessions that survive a restart, and use the web console's live page at http://127.0.0.1:8401/: the session list, a chat's turns with a work card for each tool call, the progress row, Stop and a level chip; the page talks only to /api. Worker history Run a worker from a brief file, send instructions through an explicit inbox file or an inherited pipe fd that tools cannot write, and receive a JSON result or event stream; save or import runs and inspect read-only history. API v2 Read the web console's sessions, turns, stored events (a Server-Sent Events stream too), image blobs, submission lookups, tools, grants, memory and runs over /api, and create a session or start, retry, stop and approve its turns there; it is loopback-only and only grows. Memory Keep working memory, a history of tasks and steps, and long-term memory, saved to SQLite when you turn persistence on; compress reasoning modes keep short notes and recall them at start, attempt and step. Heuristic notes can retain some negative and Chinese statements, but extraction and source attribution can be wrong or incomplete. You can forget a task's memory or all of it from Python. Embedding setup Add the embedding model long-term memory needs: the first run or the setup wizard offers one the chat server already lists, with steps for Ollama, oMLX, vLLM, SGLang and MLC. Python API Experimental Run tasks from Python code: follow each step as an event, stop a run, approve tool calls, and keep the file tools inside one directory. Memory retrieval Compare the bm25, llm and embedding memory retrievers on labelled queries with melo-retrieve; the compress reasoning modes use the same retrievers in the loop, and auto picks one. Scripts and benchmarks Read one JSON line per run and a fixed exit code, so scripts can rely on the outcome, and choose how a reply's reasoning is sent back or kept on later turns (--reasoning legacy, drop, replay, compress or compress+replay).

Security

Tools run with your account's permissions, and there is no sandbox. The model can run shell commands and Python code, and read or write any file you can. New memory files are created readable only by you (mode 0600). The gateway requires a bearer token or browser session and refuses non-loopback binds. Run melo --gateway-login in a terminal for a one-use link. A token holder can act as you; same-user processes are not isolated, and browser cookies are not isolated by localhost port.

Read the security policy and what the checks do.
