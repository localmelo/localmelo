网关和控制台会话不再提供 shell_exec

2026-10-28 · #104

  • 网关和控制台会话现在运行在新的 gateway 工具模式中，只注册 file_read、file_write 和 python_exec：shell_exec 完全不注册，模型根本看不到它。这两种界面都没有审批策略：控制台的审批会通过同一个未认证的回环 API 到达，所以任何本地进程都能批准自己的请求；Python 代码仍然可以启动进程。网关或控制台会话不能通过默认组合拿到 shell_exec，显式写出它的 AgentOptions(builtins=…) 会被检查器在 gateway 模式下拒绝，并在原因里写明模式和 --builtins all。
  • AgentOptions 新增 mode：direct、interactive、gateway 或 python（Python API 的默认值），命令行会设置各自界面的模式。交互式界面仍把 shell_exec 放在审批面板之后（--yolo 不询问），直接模式不变。针对六种破坏性命令模式的黑名单仍适用于 direct 和 python 模式，所以不传审批策略的 Python 调用者不会比以前更弱：rm -rf /、mkfs、dd if=、fork 炸弹、shutdown 和 reboot 都会被拒绝，而交互式界面改为询问审批面板。详见权限级别（英文）和Python API（英文）。

笔记中的事实会引用确立它的结果

2026-10-28 · #103

  • 笔记的条目现在会从确立它们的观察中取得 source_ids，即使这个观察来自同一任务更早的回复：先找这次回复自己的工具结果，再找仍在窗口里的结果，然后是任务其余的记录（最新的在前，最多保留最后 200 条）。只有共享一个强键（数字、日期或时间、含数字的标识符，或不在句首的大写名称）或两个有区分度的非填充词时才算匹配；有记录但都不匹配的笔记不会给条目任何来源，所以只写着“Done.”的笔记不会再引用一条无关的“no harm done”记录。这会为从更早的工具结果复制的事实以及由它们构成的摘要补全 provenance.source_ids，并且永远不会使用其他任务的记录。
  • 模型看到的召回标题不再带检索耗时：现在是 (retriever bm25)，而不是 (retriever bm25, 12 ms)。相同的运行现在会产生相同的提示词字节，所以保留在窗口里的块不会破坏前缀缓存；耗时仍保留在 llm_calls.recall_json、recall 事件和 memory_stats 中。详见循环中的召回（英文）和长期记忆（英文）。

命名、撤销、查看和复制终端对话

2026-10-28 · #101

  • /title [text] 显示或设置 1–200 个字符的标题，第一条消息之前也可以设置：它会保留到会话创建时，/new 或成功恢复会话会清除尚未保存的标题。
  • /undo 撤掉最新一个已完成的回合，并把它的输入文字保留在 ↑ 历史里；它运行过的文件和命令仍然保持改动。已提交的撤销在按 Esc 之后仍然报告成功，/retry 可以重新运行这个被撤销的回合，而不会移除之前仍在的回合。
  • /usage 显示每个回合记录的步数、工具调用、令牌和用时（包括已撤销的工作），缺少的计数显示 ?，部分总计以 +? 结尾，窄于 72 列时改用带标签的多行布局；/memory 查看工作窗口的副本、它的计数、长期记忆后端和实际使用的恢复方式，不调用模型，也不写入记忆。
  • /copy [turn] 复制已保存、已脱敏回答的 Markdown，而不是终端换行后的显示，保留缩进和末尾换行；显式回合号也可以选择已撤销的回答。macOS 上使用 pbcopy，在 SSH 下、其他平台或调用失败时发送 OSC 52 请求并如实说明；没有这个命令就不会进行任何剪贴板操作。详见查看、撤销或复制对话（英文）。

记住请求会保存它携带的事实

2026-10-28 · #100

  • Remember that … 或 记住… 这样的请求现在还会保存标记之后携带的事实，由 user_request 与本次运行的情节摘要一起写入，而不是只保存摘要。除非是第一人称（profile），这条事实是 semantic；脱敏、元名词和问句规则同样适用于它，而 remember to buy milk 这样的待办仍然不会写入任何事实。
  • 思考片段现在会和所属尝试的笔记一起，在该尝试的边界被标记为已取代，所以之后召回时会带上 (superseded) 标记并写明所属尝试，而不会被当成当前尝试的思考。
  • 目录里还没有 long_term.db 时，melo-retrieve --export-store DIR 和 --export-decisions DIR 会输出零条记录并以 0 退出，而不是报 “No such file”；路径不是目录时仍然保留文件缺失的用法错误。详见长期记忆（英文）和离线检索（英文）。

任务运行可以工作于 --workspace DIR

2026-10-28 · #98

  • --workspace DIR 现在可以用于任务，而不只在交互式界面里：这次运行会设置与 Python API 相同的 workspace_root，所以 file_read 和 file_write 只能访问该目录内的文件，shell_exec 和 python_exec 也在该目录中启动。不给这个旗标时，运行仍像以前一样使用当前文件夹；~ 会被展开，路径的解析方式与界面相同。
  • 路径不是文件夹时以退出码 2 结束，并只输出一行 melo: --workspace: not a directory: DIR；melo "" 和 --serve 会像拒绝其他直接模式旗标一样拒绝它。直接模式仍然没有审批；这个目录只限制文件工具。详见命令行（英文）和工作区根目录（英文）。

长期记忆只保留能被验证的内容

2026-10-28 · #97

  • long_term.db 现在是带类型的存储：每条记录在文本和向量之外，还有类型（semantic、episodic、profile 或 reflection）、来源、状态、允许它写入的信号，以及来源信息（任务和会话 ID、步骤和尝试、涉及的路径和命令），另有一张 decisions 表。已有的文件会原地迁移到 user_version 1，记录和搜索顺序保持不变。
  • 只有这些信号能让一条候选写入：排练（后来的笔记重述它、成功的调用用到它，或反思引用它）、用户的请求或陈述，或作用于最终尝试摘要的 --admit-on-outcome on；策略在 NEW、UPDATE、RELATED、CONFLICT 和 IGNORE 中选择，写入的每段文字（包括来源信息）都要经过候选边界和脱敏。--keep-decision-text 会在哈希旁保留决定对应的文字，[memory] 表保存结果摘要的默认设置。
  • 起始召回会按余弦或 BM25 读取其他任务的各类型有效记录；memory_stats 增加 admitted、written 和 ignored，每个决定都有对应的 memory 事件，melo-retrieve 增加 --export-store、--export-decisions 和 --route。legacy 的请求、JSON 行、窗口和搜索顺序都不变。详见长期记忆（英文）和配置（英文）。

恢复已保存的终端对话

2026-10-28 · #95

  • melo -c 恢复当前文件夹中最近一个已有完成回合的对话，melo -r [ID|TITLE] 恢复指定的对话或打开会话选择器；/sessions [filter] 和 /resume [id|title] 使用同一个选择器和同样的解析方式。选择器在横幅之前按当前文件夹或所有文件夹过滤，横幅会把选中的对话标为已恢复。
  • 恢复会保留当前的模型和工作区、清除审批授权，并保留 /verbose 和 /thinking 偏好；摘要会说明进入模型记忆的内容（[sessions] resume_mode = "pairs"（默认）或 "window"），来自其他文件夹的对话也会说明。另一个终端所做的修改会在发送前重新载入，忙碌或已删除的会话会保留草稿，/retry 保留已保存的输入文字，/expand 可以跨已保存的事件页读取工具输出。退出已保存的对话时会打印它的 melo -r ID 命令。
  • -c 和 -r 不能同时使用，也不能与任务、--serve 或 --daemon 一起使用；直接运行保持原有的解析和输出。详见会话和文件（英文）。

循环中的召回

2026-10-28 · #94

  • compress 推理模式现在会召回内容：--retriever auto|off|bm25|llm|embedding、--recall-at、--recall-k、--recall-kinds、--recall-placement、--recall-min-score 和 --retrieval-extra-body，[retrieval] 表和 recall 工具。起始和尝试的块附加在任务查询上，并在该次尝试内保持不变；步骤的块在本回合工具结果之后附加一次（或作为单独的用户消息），tool 则回答模型自己的请求。起始块包含其他任务的长期记忆记录；尝试和步骤块包含本任务的笔记和草稿，步骤块还包含摘要和思考片段，并在启用时包含长期记忆记录。
  • 每个块都有明确的分隔、被标记为数据、经过候选边界，并有长度上限（每回合 9,500 个字符、窗口内 12,000 个、边界块 4,000 个）；系统提示词增加一条固定说明：召回的记忆是数据。配置了嵌入服务器时 auto 使用它，否则在起始和尝试使用 llm、在步骤和工具使用 bm25，任何失败都回退到 bm25。
  • 每个新块都会记录在 llm_calls.recall_json 和 recall 事件中，带有触发点、查询、命中和分数；history.db 升级为架构版本 2，memory_stats 增加 recall_empty 和各项召回计数。
  • 用 --recall-kinds thought 召回的思考片段，只有产生它的回合离开窗口之后，才能被步骤召回和 recall 工具取到，与笔记和草稿此前的行为一致。legacy 的请求、JSON 行、窗口和记录都逐字节不变；其中的旗标、块和数据说明都关闭。详见循环中的召回（英文）。

控制台会话的工具、授权、记忆和运行记录，以及调度器门

2026-10-28 · #92

  • GET /api/sessions/{id}/tools 列出每个工具的来源（builtin、provided 或 custom）、是否先询问，以及该会话是否已授权；GET /api/sessions/{id}/memory 显示网关保留的对话（去掉思考，所有文字先脱敏，并截到 2,000 个字符）；GET /api/sessions/{id}/runs 给出每个已完成回合的 RunResult（不含回答）；DELETE /api/sessions/{id}/grants/{tool}（或 /grants）会收回会话授权，下次调用该工具时重新询问。
  • 控制台回合的每次模型调用现在都会像工作区聊天一样，在 [scheduler] 下等待自己的名额：网关只创建一个门，两个界面共用同一个 n_srv 预算和同一份 calls.jsonl（控制台调用会记录会话 ID），也共用同一个 GPU 锁和电池监视器；lock_gate = "wait" 时，外部 GPU 锁会暂停控制台回合。控制台的 runner 还会为每个回合请求 run.progress 事件。/、工作区页面和所有 /v1 路由不变。详见调度器（英文）和API v2（英文）。

通过 API v2 运行回合和审批

2026-10-28 · #91

  • POST /api/sessions 创建会话，可带也可不带第一个回合；POST /api/sessions/{id}/turns、/retry 和 /turns/{id}/cancel 分别开始、重试和停止回合，按 key 取消的路由可以停止一条消息，POST /api/approvals/{request_id} 回答审批请求，PATCH 和 DELETE 可以重命名、移动或删除会话。
  • 回合在后台开始，事件通过会话的事件流送达：approval.requested 等待通过 API 给出的回答，回合以 turn.finished 结束，再从该回合的记录里读取结果。client_request_id 让创建会话或回合可以安全重复；每个会话同时只运行一个回合（409 session_busy）；在等待审批时停止，会撤回审批卡片。
  • 每个请求字符串都必须是合法的 UTF-8（孤立代理项会得到 400 invalid_request）。参考文档新增了这些路由，以及一个经过测试的 Python 脚本：创建会话、跟随事件流、回答审批并读回答案。/、工作区页面和所有 /v1 路由不变。详见API v2（英文）。

/v1/agent/run 的无效请求返回更清晰的 400

2026-10-28 · #89

  • session_id 不是字符串（数字、列表）时，现在会得到该路由自己的 400 {"error": "Invalid session_id format: …"}，与其他无效 ID 相同，而不是 FastAPI 的纯文本 500。
  • 100,000 字符的上限改为在去掉首尾空白之后计算——也就是智能体实际运行的文本——所以去掉空白后不超长的带空白查询会被接受；空查询仍然是 400。详见网关和 HTTP API（英文）。

保留笔记而不是思考的推理模式

2026-10-28 · #85

  • --reasoning compress 和 compress+replay、--note-writer auto|heuristic，以及 [agent] 的 note_writer 键：compress 不发送推理，改为在对话窗口旁的内存笔记库中，为每条回复保留一条简短的笔记（计划、发现和决定、尚未确定的事项，以及工具返回的内容）和它的代码草稿。compress+replay 还会像 replay 一样发送思考；要求重放的后端会把 compress 当作 compress+replay 运行，JSON 行会报告实际生效的模式。
  • 指向某个文件的待定草稿会在本回合工具结果之后固定一次；之后写入至少 60% 的行就算已写入。后来的笔记重述、成功的调用用到笔记中的路径或命令、或反思引用这些笔记时，笔记会被排练（rehearsed）；每次尝试会得到一份由已排练笔记组成的摘要（digest）。
  • 每条笔记、草稿和摘要进入窗口或笔记库之前，都要经过新的 check_memory_candidate 边界（脱敏、清理、限长）。笔记目前还不能被召回，history.db 不增加笔记表；在显式模式下，不再把原始步骤摘要写入长期记忆，也不再提升反思；会话回合的 note 列会得到最终的摘要。legacy 逐字节不变。详见指南（英文）。

网页控制台的 API v2 提供读取接口

2026-10-28 · #84

  • 网关会打开自己的控制台会话库，并提供 GET /api/health、会话列表和单个会话、会话的回合及其事件、Server-Sent Events 流（支持 Last-Event-ID 和一次性补齐）、图片 blob，以及按 client_request_id 查询提交。控制台按需打开会话的智能体，并在空闲清扫或打开数量上限关闭它之后恢复对话。
  • 会话库打不开时，health 仍然回答，读取接口回答 503 store_unavailable，网关每 5 秒重试一次。
  • /api 只在回环地址上提供，所有响应带统一的错误格式和 Cache-Control: no-store，并且只增不改；/ 和所有 /v1 路由不变，目前还不能通过它开始、停止或重试回合。详见API v2 参考（英文）。

保存的记忆里不再留有密钥

2026-10-28 · #83

  • 任务的 query 和 result、每一步的 thought、工具调用的参数、工具结果的输出和错误，以及长期记忆保存的文字（步骤摘要和提升的反思），现在都用与模型调用和事件相同的脱敏规则写入：sk- 密钥、GitHub 令牌、AWS access key id、Bearer 后面的令牌，以及关键词旁边的一次性验证码。
  • 运行和模型仍然看到原文：工作记忆、请求、事件和运行的 result 都不变，保存的图片仍然只是引用。详见隐私（英文）。

工具在最小环境中运行

2026-10-28 · #81

  • shell_exec 和 python_exec 启动子进程时只带 PATH、HOME、USER、LOGNAME、SHELL、TERM、LANG、所有 LC_* 变量和 TMPDIR，再加上新增的 AgentOptions(tool_env={...})，别的都不带。melo 环境里的 API 密钥不会到达任何工具；VIRTUAL_ENV、PYTHONPATH、SSH_AUTH_SOCK 和代理变量只能通过 tool_env 传入。
  • MCP 服务器也拿到同样的基础环境（现在包括所有 LC_* 变量），再加上它自己条目里的 env。详见工具（英文）。

工具提示只来自模型自己的调用

2026-10-28 · #80

  • 默认的 retrieve 模式下，每一步额外提供的工具只有模型在这次对话中已经调用过的工具，以及按关键词搜索与任务最接近的三个匹配。任务、工具结果、召回的长期记忆或反思里出现的工具名不再提供那个工具，所以运行中的文字无法把模型从未调用过的工具重新放到它面前。
  • 内置工具和调用被拒绝后的再次提供都不变；all 仍然在每一步提供所有已注册的工具。

Python 代码始终在子进程中运行

2026-10-28 · #79

  • Python 代码现在在所有模式下都在子 Python 中运行，而不只是设置了工作区根目录时：循环、休眠或调用 os._exit() 的代码不会再占住或结束 melo。工具的时间限制（默认 60 秒，交互式界面中 10 分钟）和一次运行的 timeout_s 会连同它启动的所有进程一起终止子进程；子进程还有一小时的 CPU 时间限制和 1,024 个打开文件的上限。
  • 代码通过标准输入（一个管道）交给子进程，而不在它的命令行里，所以 ps 看不到代码，调用也不受命令行长度限制；此后子进程从标准输入读到的是文件结尾。代码以 __main__ 运行，sys.argv == ["-c"]，每次调用都是新的命名空间，所以模块状态不会从一次调用带到下一次；写入标准输出或标准错误的内容（包括子进程写入的）都是这次调用的输出，而不是 melo 的输出。
  • 失败时现在显示 Python exited with code <n>: 和子进程输出的末尾，而不是异常的文字；sys.exit(0) 算成功。

Python API 支持事件、停止任务和审批

2026-10-26 · #37

  • Python 代码可以实时跟踪一次运行：run_task(..., on_event=sink) 会报告每一步、模型的每条回复、每次工具调用和每次反思，并隐去其中的密钥。
  • 带事件接收函数或审批策略的运行可以被停止：它以 cancelled 结束，被打断的那一步会被妥善收尾。
  • 审批策略决定 shell_exec、python_exec、file_write 等标记过的工具能否运行；AgentOptions(workspace_root=...) 把文件工具限制在一个目录内。

网关拒绝来自其他网站的请求

2026-10-26 · #36

  • 监听 localhost 或回环 IP 地址（例如默认的 127.0.0.1）时，网关会拒绝 Host 不是 127.0.0.1、localhost 或 [::1] 加端口的请求（HTTP 421），也会拒绝其他来源的网页通过浏览器发来的请求（HTTP 403）。网页不能再通过 DNS 重绑定访问网关、用你的工具执行任务。
  • 任何网页都不能在 frame 里显示网关的页面。
  • 如果监听地址不是 localhost 或回环 IP 地址（例如 0.0.0.0），网关不做这些检查，并在启动时记录一条警告：网关没有身份验证。

反思提前结束的未完成运行更少了

2026-10-23 · #34

  • 以前，即使还有尝试次数和步数、任务也还没有完成，反思也可能结束运行：反思自己的效用分数必须达到一个阈值，读不出或过长的反思也会结束运行。
  • 现在，只要反思选择 continue 并且它的三项检查都成立，就开始下一次尝试。读不出的反思不再结束还有尝试次数和步数的运行，过长的反思会被截短。--reflection-gate utility 保留之前的行为。
  • 用一个本地模型把 12 个编程练习各运行 5 次：新的默认设置通过了 59/60 次，之前的行为通过了 50/60 次。不使用反思（--attempt-policy none）也通过了 59/60 次：新的默认设置与它持平，并没有超过它。

运行选项、运行结果和退出码

2026-10-22 · #25、#26、#27、#28、#30、#31、#32

现在，直接模式下的一次 melo "<task>" 运行可以交给脚本或基准测试来驱动。

  • 运行选项：--max-steps、--attempt-policy、--tool-exposure、--builtins、--memory、--memory-dir 和 --timeout；在 --base-url 运行中启用长期记忆的 --embedding-base-url 和 --embedding-model；以及 Python API 中的 AgentOptions（#30）。
  • 每次运行都以九种状态之一结束。--output-format json 会把运行记录输出为一行 JSON；退出码在 completed 时为 0，crashed 时为 1，其他状态或用法错误时为 2（#30）。
  • 失败的模型请求在重试可能成功时会自动重试；--request-timeout 和 request_timeout_s 用来设置对话请求超时（#30）。
  • SIGTERM 和 SIGHUP 会在 8 秒内结束一次直接模式的运行，并保存它的任务记录（#30）。
  • 每一步只能运行本步提供的工具；内置工具的调用如果参数类型不对，会在运行前被拒绝（#30）。
  • 支持本地 MCP 服务器提供的工具（--mcp-config 和 --mcp-only），工具也可以返回图片（#27、#30）。
  • 工具调用会以真正的工具调用轮次发给兼容 OpenAI 接口的模型，一步中的每个调用都会执行；extra_body 可以为对话请求添加字段（#26）。
  • 反思的回复中没有 JSON 对象时，会不带工具再请求一次（#31）。
  • #32：在检索模式下，每一步先提供所有已注册的内置工具，再从其他工具中提供对话已提到或调用过的工具，以及用带 IDF 的 BM25 检索到的工具，两部分都按名称排序。
  • 采用 MIT 许可证（#28），开发环境改用 uv，并把 uv.lock 提交到仓库（#25）。

Track 2 记忆系统设计演化

2026-05-03 · 记忆设计

Track 2 现在有了更清晰的 memory-session 结构：online path 会把值得记忆的 candidate 拆到两条并行分支，一条进入快速的 working memory，另一条进入负责 durable 或 specialized placement 的 Hippo。

  • agent 在 v1 中只做轻量 write proposal：判断 candidate 是否值得记忆，保持 bool 决策。
  • working 存短期 active task/session context，使用 LRU-style refresh；设计方向区分 fresh 和 rehearsed memories。
  • long-term persistence 需要等待相关 working memory 进入 rehearsed，或出现其他 strong write signal。
  • Hippo 用五类明确 action 路由 durable writes：NEW、UPDATE、RELATED、CONFLICT 和 IGNORE。
  • long 和 profile 在 v1 中共享一个 physical long-term store，通过 semantic、episodic、profile、reflection 等 metadata kinds 区分。
  • tools 仍是 authoritative registry，同时扩展 procedural skill/template memory，但不能绕过 checker 或 executor policy。
  • PersonalizedMemory 是 Track 4 的 filtered sleep-sample staging area，不是 raw history dump。
  • history 保持 append-only 或 near-append-only，只用于 debugging、replay、auditability 和 provenance lookup，不参与 normal recall。

v1 foundation 已经补齐 persistent-memory 文档、multi-session SQLite stress coverage、真实 backend long-term retrieval evidence，以及 PersonalizedMemory selected-sample schema freeze。后续 Track 2 会进入 working-memory stages、Hippo write routing、long/profile semantics、procedural memory 和 evaluation。
