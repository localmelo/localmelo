网页工作区的聊天开始经过调度器

2026-10-27 · #69

  • 网页工作区里每个聊天发出的规划、反思和向量调用现在都经过调度器的策略：聊天调用要么立刻发出，要么等一个槽位；向量调用从不被扣住，但会计入在途数量；等待时页面显示 Waiting: Resources（或策略给出的其他原因）。
  • 标题栏的等级按钮（P1 到 P4，默认 P2）决定这个聊天相对其他聊天的顺序；你正在输入的聊天就是快车道，在不超出服务器槽位的前提下优先放行。
  • [scheduler] policy 默认是 off：只把每次调用记录到 ~/.cache/localmelo/scheduler/，不扣住任何调用。fcfs 和 class 会真正执行策略。直接运行、命令行和 /v1/agent/run 都不变。

    • 回合的工作实时可见

    2026-10-27

    • 交互式界面现在会把回合的每个事件画出来：模型的思考（Thought for 1.2s 加一段摘录）、中间文本、与最终答案不同的最后一条消息、带倒计时的重试、空回复/卡住/步数预算通知，以及反思（包括读不出来的反思）。
    • 实时区域显示本回合的进度事实（步数、尝试、阶段和轮次、测试、用时）、正在运行的工具的计时和时限；会话的第一个回合还会用一行暗色文字显示上次运行做了什么，措辞与直接模式的进度行一致。
    • 新增命令：/verbose 显示更长的摘录、工具参数和 20 行输出；/thinking 关闭思考摘录；/expand 打印某个工具调用的完整输出；/progress 显示实时区域依据的进度事实。

    在 Python 中忘掉一个任务的记忆

    2026-10-27 · #64

    • Python 代码可以忘掉一个任务的记忆，也可以清空全部记忆：await hippo.forget(task_id) 会删除该任务在 tasks、steps 和 llm_calls 表中的行，以及元数据中指明该任务的长期记忆条目（即该任务的反思）；await hippo.forget_all() 会清空历史记录和长期记忆，包括步骤摘要。工作记忆、程序记忆和会话不受影响。
    • 遗忘时，被删除的内容会被覆写，WAL 会被截断，所以文本不会留在数据库或其 -wal 文件里。目前还没有对应的命令或页面。详见重置记忆（英文）。

    运行任务中的会话不会被关闭

    2026-10-27 · #63

    • DELETE /v1/sessions/<id> 在会话的任务还在运行时不会关闭它，而是返回 HTTP 409 和网关的错误响应体（error 和 session_id），并让任务和会话继续运行；空闲的会话仍和以前一样关闭。任务结束后可以再关闭会话。
    • 停止网关时仍会关闭所有会话，包括正在运行的会话；仍在运行的任务随后以 crashed 结束。/v1/agent API 仍然没有停止运行的路由。

    新建的记忆文件仅自己可读

    2026-10-27 · #62

    • 新建的 long_term.db 及其 -wal 和 -shm 文件使用 0600 权限，和 history.db、procedures.db 一样。以前它通常是 0644，同一台电脑上的其他用户可以读到其中的步骤摘要和反思。已有文件会保留原来的权限；localmelo 创建的记忆目录仍然是 0700。

    会话的每一轮可以报告进度

    2026-10-27 · #60

    • SessionRunner(..., progress=True) 会让每一轮运行报告 run.progress 事件，并把这些事件和该轮一起保存；这个开关保留在 SessionRunner 上，replace_agent 之后仍然有效。run_turn 和 start_turn 接受 routine=NAME，只在给出时传给运行。
    • localmelo.support.progress_line.format_past(payload, width) 单独给出进度行中的“过去的运行”和步骤部分，措辞和宽度规则与直接模式相同。交互式界面目前还不会请求进度事件，进度行本身没有变化。

    Shell 命令不再接管终端

    2026-10-27 · #59

    • shell_exec 现在在每种模式下都把 /dev/null 作为命令的标准输入。如果命令的标准输入是一个不是 melo 控制终端的 pty，它可能在启动时把这个 pty 当作自己的控制终端，并在退出时挂断它，导致已经完成的 melo 运行以退出码 120 而不是 0 结束。

    进度行会说明借用了哪个任务

    2026-10-27 · #56

    • 相似任务的历史步骤现在显示为 like <routine title>:，而不是 like a similar task:，并写明是哪个任务（--routine 的名字，否则是该任务查询的开头）。
    • 如果 shell_exec 的命令以字符串数组的形式传入（工具会拒绝这种形式），现在会按命令的单词来标记和分类，因此 ["ls", "-la"] 会被当作读取命令，而不是 {command:。程序记忆也保存同样的标签。

    选中的 Ollama 服务器会保存为 Ollama

    2026-10-27 · #55

    • 首次运行、--base-url 之后出现的 Save URL · MODEL as the default backend? 问题，以及 /backend，以前都会把服务器保存为 vllm。现在保存时会向该服务器请求一次 GET /api/version：像 Ollama 一样应答的服务器会保存为 ollama 后端，使用 Ollama 自己的 API 和 300 秒的对话超时；其他兼容 OpenAI 接口的服务器仍然保存为 vllm。
    • 以前，这样保存的 Ollama 服务器会使用 vLLM 的 120 秒对话超时，横幅也显示 vLLM。

    终端里的交互式界面

    2026-10-27 · #53

    • 在终端中不带任务运行 melo，现在会打开一个边做边显示的对话界面：横幅显示模型、工作区和工具；每个工具调用显示为一个块，附带输出的前几行；模型工作时，旋转指示显示当前步数和用时；答案按 Markdown 输出。它取代了下一条更新中的对话循环，melo "" 仍然打开那个循环。
    • 输入 / 会列出命令及其说明。/model 和 /backend 切换模型和服务器，并保存为默认值（用 --base-url 打开的界面不保存）；/new 开始新的对话。
    • 运行命令、Python 代码或写文件之前会先询问：允许这一次、在本次会话中允许这个工具，或者拒绝并说明原因。--yolo 跳过询问，--workspace DIR 指定文件工具只能在其中操作的文件夹。
    • 中文和其他宽字符的输入、删除和换行都按整字处理。Esc 停止当前回合，上方向键调出之前的消息，Alt+Enter 或 Ctrl+J 换行。
    • 没有终端时，melo 现在会提示应该运行什么，并以退出码 2 结束；请用 melo --serve 启动网关。详见交互式界面（英文）。

    输入 melo 即可开始对话

    2026-10-27 · #52

    • 在终端中不带任务运行 melo，会用保存的模型服务器打开对话循环，并先显示模型和服务器。以前它会启动网关；现在 melo --serve 仍然启动网关，没有终端时的 melo 也一样。
    • 第一次运行、还没有配置时，melo 会在本机查找模型服务器，请你确认地址并从服务器列出的模型中选一个，然后保存下来。它只向服务器请求模型列表，不会因此加载模型。
    • 不带任务运行 melo --base-url URL，会用该服务器列出的第一个对话模型打开对话循环；用 --chat-model 可以指定模型。
    • 配置向导会把已保存的值作为默认值，检查失败时可以重试，并会说明本地服务器返回的 HTTP 401：localmelo 不向本地服务器发送 API 密钥。没有终端且没有配置时，melo --serve 只输出一行提示，不再输出 traceback。

    终端里的进度行

    2026-10-27 · #51

    • 在终端里运行 melo "<task>" 时，stderr 上会有一行暗色的进度，显示当前步数、阶段、正在运行的工具和用时；输出答案之前会擦掉。
    • 如果这个任务以前在保留记忆（--memory-dir）时运行过，进度行还会显示上一次运行用了多少步、多长时间以及它的步骤；来自相似任务的会单独标明。--routine NAME 可以把措辞不同的同一任务归到一起。
    • 进度行不会折行，在后台运行时不画，也不会拖慢运行，即使终端暂停了输出。--progress off 可以关掉它。管道、文件、--output-format json 和退出码都没有变化。详见进度行（英文）。

    运行会学习反复执行的任务的步骤

    2026-10-27 · #46

    • 每次正常结束的运行都会把自己做了什么记进程序记忆：工具调用的类型、简短的标签、步数和用时。成功完成的运行还会更新所属任务的步骤模板。开启持久化时写入记忆目录里的 procedures.db，否则只留在内存中。
    • Python 调用方可以通过 run.progress 事件（progress=True）跟踪一次运行：当前第几步、处在哪个阶段、测试通过了几个；如果这个任务以前做过，还有之前的运行用了多少步、多长时间，以及它们的具名步骤。在重放结果证明百分比进度条足够可靠之前，进度条保持关闭。
    • 请求体、输出、JSON 行、退出码和历史记录的行都没有变化。

    进度显示的基础

    2026-10-26 · #45

    • 程序记忆会学习你反复运行的任务的步骤，比如每天都要修的一套测试。它从之前的运行中保存工具调用的类型、简短的标签，以及步数和用时，从不保存模型说的话。
    • 第一次运行是探索，不做估计。任务有了完成的运行之后，显示可以给出之前的运行用了多少步、多长时间；百分比进度条还要求这些运行彼此一致，并且模型过去的估计足够准确。在目前测量过的基准运行上，这项检查还不能足够清楚地区分好的估计和差的估计，所以计划中的进度显示先不带进度条。
    • melo-procedures 从 history.db 学习这些步骤模板，并离线重放这些规则：先测量，再显示。运行目前既不读取也不写入程序记忆。

    历史记录保存每次模型调用

    2026-10-26 · #42

    • 开启持久化后，history.db 会保存模型的每一次回复及其推理：每次规划或反思的回复一行，并关联到它产生的工具步骤。计划中的“模型推理记忆”将基于这些记录构建。
    • 回复文本和推理会经过最基本的密钥脱敏，推理默认保留 30 天（可以用 LOCALMELO_THINKING_RETENTION_DAYS 修改）。melo-retrieve --export-run 可以把一次运行的模型调用导出为语料，用来比较检索器。
    • 每个对话请求都会在 X-Localmelo-Call-Kind 请求头中注明调用类型，代理因此能区分规划和反思。JSON 行、退出码和请求体都没有变化。

    重启后仍在的对话（Python API）

    2026-10-26 · #41

    • 会话把对话保存在 SQLite 中。每一轮都从一行已保存的记录开始，并且只结束一次，带有状态和原因；即使运行它的进程停止或崩溃也是如此。新的智能体可以恢复这段对话。
    • 用同一个请求 ID 发送两次的消息只运行一次，最后一轮可以撤销，工具的审批请求也可以由人在另一个页面上回答。事件流会给重新连接的客户端补发它漏掉的每一个事件。
    • 会话属于实验性的 Python API。melo 和网关目前还没有使用会话：计划中的交互式命令行和网页控制台会把对话保存在这里。

    同时运行多个任务的基础

    2026-10-26 · #39

    • 调度器将让你的对话、后台任务和聊天共用一个本地模型服务器。它的策略决定下一个发给模型的调用，说明每个任务为什么在等，并让你的对话优先得到回答。
    • 模拟器用这个策略重放工作负载，可以离线比较策略的几种变体，用合成的工作负载或基准测试的记录都行。
    • 目前只有网页工作区的聊天经过这道门；直接运行和命令行仍然和以前一样。下一步会把它们的调用也放进来。

    离线比较记忆检索器

    2026-10-26 · #38

    • melo-retrieve 用 bm25、llm 或 embedding 检索器在语料上运行带标注的查询，报告每种检索器找到正确文档的比例和速度。
    • 它还能把一次运行中的模型调用导出为这样的语料：模型推理过程的笔记、代码草稿和思考片段。
    • melo 还没有使用这些检索器。默认用哪一种，由基准测试的比较结果决定。

    网页工作区和终端里的对话

    2026-10-26 · #35

    • 网关的页面换成了网页工作区：从你的服务器上选择模型，同时保留多个对话、各自保存草稿，可以搜索对话，回答里的代码、表格和链接都能正确显示，也可以停止正在进行的运行。手机大小的屏幕也能使用。
    • 只要网关在运行，对话就一直保留，刷新页面后会恢复。
    • 在网页对话、melo "" 对话循环和网关会话里，每条消息都能看到之前的回答。
    • melo "" 会在终端里打开一个对话。只运行 melo 仍然会启动网关。

    Python API 支持事件、停止任务和审批

    2026-10-26 · #37

    • Python 代码可以实时跟踪一次运行：run_task(..., on_event=sink) 会报告每一步、模型的每条回复、每次工具调用和每次反思，并隐去其中的密钥。
    • 带事件接收函数或审批策略的运行可以被停止：它以 cancelled 结束，被打断的那一步会被妥善收尾。
    • 审批策略决定 shell_exec、python_exec、file_write 等标记过的工具能否运行；AgentOptions(workspace_root=...) 把文件工具限制在一个目录内。
    • 对话可以在多次运行之间、在不同智能体之间延续。直接模式和网关的行为不变。

    网关拒绝来自其他网站的请求

    2026-10-26 · #36

    • 监听 localhost 或回环 IP 地址（例如默认的 127.0.0.1）时，网关会拒绝 Host 不是 127.0.0.1、localhost 或 [::1] 加端口的请求（HTTP 421），也会拒绝其他来源的网页通过浏览器发来的请求（HTTP 403）。网页不能再通过 DNS 重绑定访问网关、用你的工具执行任务。
    • 任何网页都不能在 frame 里显示网关的页面。
    • 如果监听地址不是 localhost 或回环 IP 地址（例如 0.0.0.0），网关不做这些检查，并在启动时记录一条警告：网关没有身份验证。

    反思提前结束的未完成运行更少了

    2026-10-23 · #34

    • 以前，即使还有尝试次数和步数、任务也还没有完成，反思也可能结束运行：反思自己的效用分数必须达到一个阈值，读不出或过长的反思也会结束运行。
    • 现在，只要反思选择 continue 并且它的三项检查都成立，就开始下一次尝试。读不出的反思不再结束还有尝试次数和步数的运行，过长的反思会被截短。--reflection-gate utility 保留之前的行为。
    • 用一个本地模型把 12 个编程练习各运行 5 次：新的默认设置通过了 59/60 次，之前的行为通过了 50/60 次。不使用反思（--attempt-policy none）也通过了 59/60 次：新的默认设置与它持平，并没有超过它。
    • 条件和局限见评测（英文）。

    运行选项、运行结果和退出码

    2026-10-22 · #25、#26、#27、#28、#30、#31、#32

    现在，直接模式下的一次 melo "<task>" 运行可以交给脚本或基准测试来驱动。

    • 运行选项：--max-steps、--attempt-policy、--tool-exposure、--builtins、--memory、--memory-dir 和 --timeout；在 --base-url 运行中启用长期记忆的 --embedding-base-url 和 --embedding-model；以及 Python API 中的 AgentOptions（#30）。
    • 每次运行都以九种状态之一结束。--output-format json 会把运行记录输出为一行 JSON；退出码在 completed 时为 0，crashed 时为 1，其他状态或用法错误时为 2（#30）。
    • 失败的模型请求在重试可能成功时会自动重试；--request-timeout 和 request_timeout_s 用来设置对话请求超时（#30）。
    • SIGTERM 和 SIGHUP 会在 8 秒内结束一次直接模式的运行，并保存它的任务记录（#30）。
    • 每一步只能运行本步提供的工具；内置工具的调用如果参数类型不对，会在运行前被拒绝（#30）。
    • 支持本地 MCP 服务器提供的工具（--mcp-config 和 --mcp-only），工具也可以返回图片（#27、#30）。
    • 工具调用会以真正的工具调用轮次发给兼容 OpenAI 接口的模型，一步中的每个调用都会执行；extra_body 可以为对话请求添加字段（#26）。
    • 反思的回复中没有 JSON 对象时，会不带工具再请求一次（#31）。
    • #32：在检索模式下，每一步先提供所有已注册的内置工具，再从其他工具中提供对话已提到或调用过的工具，以及用带 IDF 的 BM25 检索到的工具，两部分都按名称排序。
    • 采用 MIT 许可证（#28），开发环境改用 uv，并把 uv.lock 提交到仓库（#25）。

    Track 2 记忆系统设计演化

    2026-05-03 · 记忆设计

    Track 2 现在有了更清晰的 memory-session 结构：online path 会把值得记忆的 candidate 拆到两条并行分支，一条进入快速的 working memory，另一条进入负责 durable 或 specialized placement 的 Hippo。

    • agent 在 v1 中只做轻量 write proposal：判断 candidate 是否值得记忆，保持 bool 决策。
    • working 存短期 active task/session context，使用 LRU-style refresh；设计方向区分 fresh 和 rehearsed memories。
    • long-term persistence 需要等待相关 working memory 进入 rehearsed，或出现其他 strong write signal。
    • Hippo 用五类明确 action 路由 durable writes：NEW、UPDATE、RELATED、CONFLICT 和 IGNORE。
    • long 和 profile 在 v1 中共享一个 physical long-term store，通过 semantic、episodic、profile、reflection 等 metadata kinds 区分。
    • tools 仍是 authoritative registry，同时扩展 procedural skill/template memory，但不能绕过 checker 或 executor policy。
    • PersonalizedMemory 是 Track 4 的 filtered sleep-sample staging area，不是 raw history dump。
    • history 保持 append-only 或 near-append-only，只用于 debugging、replay、auditability 和 provenance lookup，不参与 normal recall。

    v1 foundation 已经补齐 persistent-memory 文档、multi-session SQLite stress coverage、真实 backend long-term retrieval evidence，以及 PersonalizedMemory selected-sample schema freeze。后续 Track 2 会进入 working-memory stages、Hippo write routing、long/profile semantics、procedural memory 和 evaluation。
