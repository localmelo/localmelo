架构

localmelo 的各部分如何协同工作：melo/ 中是智能体及其检查、记忆和工具，support/ 中是后端、网关和配置。

组件

每个组件目前做什么，以及代码在哪里。路径都相对于仓库根目录。

命令行

melo 命令。给出任务时，它以直接模式运行：创建一个智能体，运行这个任务，以文本或一行 JSON 输出结果，并用退出码表示运行是如何结束的。在终端中不带任务时，它打开交互式界面：输入框和状态栏固定在底部，每一轮边运行边输出到终端的滚动区：每个工具调用一个块，旋转指示显示当前步数和用时，答案按 Markdown 输出。界面在会话上运行每一轮（保存在 ~/.cache/localmelo/cli/sessions.db），运行 shell_exec、python_exec 和 file_write 之前会在面板中询问，把文件工具限制在工作区内，并把 /model 和 /backend 选择的模型和服务器保存到配置文件（用 --base-url 打开的界面不保存）。没有终端时，单独的 melo 以退出码 2 结束。任务为空字符串（melo ""）时，它打开简单的对话循环，每一轮都能看到之前的回答。--serve 启动网关；--daemon 用来管理 macOS 后台服务。使用 --base-url 时，智能体直接连接该服务器，不读取配置文件；不使用它时，使用配置中的后端。无论是否使用 --base-url，--chat-model 和 --request-timeout 都会设置对话模型和对话请求的超时，并且都不会修改配置文件。

关键文件：__main__.py；交互式界面在 support/cli/ 中：launch.py（终端检查、工作区和模型服务器）、app.py（输入框和按键）、session.py（每一轮和命令）、render.py（工具块、旋转指示和答案）和 approvals.py；以及 support/sessions/agents.py。

网关

melo --serve 启动的 HTTP 服务器。它提供 HTTP API（/v1/health、/v1/agent/run、/v1/sessions），最多保留 50 个会话，每个会话都有一个根据配置文件创建的智能体。会话的智能体会保留自己的回答，所以每个请求都能看到之前的回答。每个请求在运行前都要通过检查：任务的长度和会话 ID。

在 / 上，它提供网页工作区。网页工作区不读取配置文件：它列出你输入地址的服务器上的模型，最多保留 12 个自己的对话，支持搜索、每个对话各自的草稿，以及 Stop 按钮（停止运行，运行以 cancelled 结束）。每个对话都有自己的智能体，带四个内置工具和自己的工作记忆。所有对话把历史记录写入同一个库，选择了嵌入模型时也把长期记忆写入同一个库，都在 ~/.cache/localmelo/playground/ 中。对话在网关运行期间保留，但创建对话时会关闭空闲超过 2 小时的对话；已有 12 个对话时，会替换最久没有活动的空闲对话。

网关没有身份验证。监听 localhost 或回环地址（例如默认的 127.0.0.1:8401）时，它会拒绝 Host 不是 127.0.0.1、localhost 或 [::1] 加网关端口的请求（HTTP 421），以及其他来源的网页通过浏览器向它的 API 发来的请求（HTTP 403）。任何网页都不能在 frame 里显示网关的页面。监听其他地址（例如 0.0.0.0）时，它不做这些检查，并在启动时记录一条警告。

关键文件：support/gateway/__init__.py、session.py、guard.py（Host 和 Origin 检查）、webapp.py 和 playground.py（网页工作区的路由和对话）、static/（网页工作区的页面），以及用于 macOS 后台服务的 daemon.py。

MCP 服务器

通过 stdio 使用 Model Context Protocol 通信的本地服务器，列在 --mcp-config 指定的 JSON 文件中。第一次运行开始时，support/mcp 会启动每个服务器，列出它的工具，并以 mcp__<server>__<tool> 的名称把这些工具注册到工具注册表和执行器中。MCP 工具可以在直接模式和 Python API 中使用，网关会话和交互式界面中不能使用。服务器的 require_approval 可以让它的全部工具（或其中列出的工具）在调用前先询问运行的审批策略；没有审批策略的运行（例如直接模式的运行）会直接运行这些工具，不经询问。

关键文件：support/mcp/config.py、client.py、provider.py，以及 melo/contracts/tools.py 中的工具提供方接口。

智能体

运行循环。每一步都会根据任务、工作记忆、召回的长期记忆和最新的反思构建提示词，向模型提供一组工具，发送一次规划请求，然后运行回复中的工具调用。如果回复只有文本、没有工具调用，它就是最终答案，运行以 completed 结束。在默认的 reflect 策略下，步骤按尝试分组，每次尝试最多 10 步；一次尝试没有得到答案就结束时，由反思决定是否开始下一次尝试。每次运行都以九种状态之一结束（被停止的交互式运行以 cancelled 结束，见下文），并返回一个 RunResult。模型请求失败时，如果重试可能成功，最多重试两次。

调用 run_task 的 Python 代码可以跟踪和控制一次运行。传入 on_event 时，它会以事件的形式收到每一步、模型的每条回复、每次工具调用、每条通知和每次反思，模型文本中的密钥会被隐去。传入 approval 时，由审批策略决定每个需要审批的工具调用能否运行。带其中任意一个的运行是交互式运行：取消它时，运行以 cancelled 结束，被打断的那一步会被妥善收尾。设置 AgentOptions(record_answers=True) 时，工作记忆会保留每次运行的回答；conversation() 和 load_conversation() 可以把对话带到另一个智能体。直接模式和 HTTP API 既不传入事件接收函数，也不传入审批策略。网页工作区会传入事件接收函数，所以在网页工作区中点 Stop，运行会以 cancelled 结束。

关键文件：melo/agent/agent.py、melo/agent/options.py（AgentOptions）、melo/agent/_chat.py（规划和反思请求、重试）、melo/agent/_events.py 和 melo/contracts/events.py（事件）、melo/contracts/approvals.py（审批策略）、melo/schema.py（RunResult 和各项上限）。

检查器

在一次运行的各个边界进行检查：

  • 规划请求之前：提示词最多 100,000 个字符，本步提供的工具列表必须有效；
  • 规划请求之后：回复中的每个工具调用都要有名称和唯一的 ID；
  • 工具运行之前：shell_exec 会拒绝六种破坏性的命令模式；
  • 工具运行之后：超过 50,000 个字符的输出会被截断；
  • 写入记忆之前：限制写入的大小；
  • 事件交给 Python 代码之前：模型回复文本中常见格式的 API 密钥、bearer 令牌和一次性验证码会被替换为 [redacted]；
  • 在网关中：检查每个请求的任务和会话 ID。

规划请求前后的检查一旦失败，运行就以 failed 结束。被拒绝的工具调用不会运行：模型会把这次拒绝当作工具返回的错误。

关键文件：melo/checker/checker.py、validators.py、payloads.py、redaction.py。

执行器

按顺序运行一步中的工具调用。以下调用会被拒绝：本步没有提供的工具、参数不是 JSON 对象的调用，以及内置工具参数类型不对的调用；剩下的每个调用再交给检查器检查。设置了工作区根目录时，工作区策略接着解析文件工具的路径，并拒绝根目录之外的路径。设置了审批策略时，需要审批的工具的调用接着等待审批策略的决定；获准之后，如果设置了工作区根目录，文件路径会被重新解析，路径在等待期间发生了变化的调用会被拒绝。每个工具都有时间限制，从审批之后开始计时：shell_exec 30 秒，file_read 和 file_write 60 秒，MCP 工具使用其服务器的 timeout。在交互式界面中，shell_exec 和 python_exec 的时间限制是 10 分钟。shell 命令的标准输入是 /dev/null，因此它不会读取终端。没有工作区根目录时，python_exec 的代码在 localmelo 进程内运行，无法中断。拒绝、审批不通过、超时或出错都会作为工具的错误返回。

四个内置工具是 shell_exec、python_exec、file_read 和 file_write。直接模式和网关不给它们设置工作区根目录，所以文件工具可以访问你能访问的任何文件。在 Python API 中，AgentOptions(workspace_root=…) 会启用 policy.py：文件工具只能访问根目录内的文件；shell_exec 和 python_exec 在根目录中以子进程运行，但不受这个限制。只有带审批策略的运行才会审批。

关键文件：melo/executor/executor.py、builtins.py、policy.py、melo/contracts/approvals.py。

记忆

工作记忆保存一次运行或一个网关会话中的对话：最近 20 条消息，只在内存中。历史记录保存每个任务和每一步；开启持久化后，还保存每次模型调用及其推理。长期记忆需要嵌入后端：它把步骤摘要和反思连同嵌入向量一起保存，并在每一步召回最接近的 5 条。程序记忆保存每次运行的步骤，并学习你反复运行的任务的步骤。历史记录、长期记忆和程序记忆默认留在内存中；开启持久化后，分别写入 history.db、long_term.db 和 procedures.db。新建的文件只有你能读取（权限 0600）。Python API 可以用 Hippo.forget(task_id) 忘掉一个任务的历史记录行和指明该任务的长期记忆反思，用 forget_all() 清空历史记录和长期记忆（包括步骤摘要）。工具注册表保存所有已注册的工具，以及检索模式使用的 BM25 索引。

melo/memory/retrieval/ 中有三种可切换的检索器：bm25、llm 和 embedding。它们检索由一次运行的模型调用构建的文档：melo/memory/notes.py 从模型回复中提取的推理笔记、代码草稿和思考片段，以及反思。运行目前还不使用它们：melo-retrieve 命令（support/retrieve.py）在带标注的查询上离线比较这些检索器，并能把以 raw-call JSONL 记录的模型调用导出为语料。开启持久化后，melo 写入的 history.db 也记录每次模型调用，melo-retrieve 同样能导出它。详见离线检索（英文）。

会话（实验性）把整段对话保存在 sessions.db 中：每一轮都是一行记录，只结束一次，带有状态和原因；会话的事件也一起保存；窗口检查点（window checkpoint）让新的智能体从上一个智能体停下的地方继续。用 progress=True 创建的 SessionRunner 会让每一轮运行报告 run.progress 事件，并把这些事件和该轮一起保存。网关的文件和终端的文件是分开的。交互式界面在会话上运行每一轮，但目前还不能恢复会话；网关还没有使用会话（代码在 support/sessions/）。详见会话（英文）。

关键文件：melo/memory/coordinator.py、short/（工作记忆）、history/、long/、tools/（工具注册表）、bm25.py。

记忆设计（计划中）：记忆设计页保留了维护者为记忆撰写的设计，其中部分内容尚未实现。

配置和向导

~/.cache/localmelo/config.toml 记录对话后端、嵌入后端及其设置。在终端中第一次运行时，melo 用 GET /v1/models 查找模型服务器，询问地址和模型并保存：Ollama 服务器保存为 ollama 后端，其他兼容 OpenAI 接口的服务器保存为 vllm。配置向导（melo --reconfigure）会询问所有后端设置，向每个服务器发送测试请求，保存文件，然后打开交互式界面；加上 --serve 时则启动网关。直接模式和网关都根据这个文件创建智能体。

关键文件：support/config.py、support/onboard.py、support/onboard_probe.py、support/backends/discovery.py。

提供方

连接模型服务器的 HTTP 客户端：兼容 OpenAI 的对话接口（/chat/completions）、Ollama 自己的 /api/chat，以及兼容 OpenAI 的嵌入接口。它们实现 melo/contracts/providers.py 中的接口，应用对话请求超时，并把每个失败的请求报告为 ProviderError，同时说明重试是否可能成功。

关键文件：melo/contracts/providers.py、support/providers/llm/、support/providers/embedding/。

后端

每个后端键对应一个适配器：mlc、ollama、vllm 和 sglang 用于你自己运行的服务器，openai、anthropic、gemini 和 nvidia 用于云端 API。每个适配器检查配置文件中属于自己的表，并创建提供方。后端只负责连接：模型服务器由你自己启动和停止。

关键文件：support/backends/registry.py、base.py、local/、cloud/。

melo/sleep/、melo/memory/personalized/ 和 support/melo_serving/ 中的代码，智能体目前还没有使用。melo/memory/retrieval/ 和 melo/memory/notes.py 目前只供 melo-retrieve 使用；support/scheduler/（调度策略核心及其模拟器）目前只有测试在使用。

边界

边界规则意义
melo/ 和 support/ melo/ 包含智能体以及提供方要实现的接口，不在模块级别导入 support/。唯一的桥梁是 Agent(config=…)：调用它时，它通过 support/backends 创建提供方。 智能体可以使用你自己创建的提供方运行（例如测试用的假提供方），新增后端也只需要修改 support/。
智能体和执行器 每一步只能运行本步提供的工具，每个调用都要先通过检查。这些检查只是防护措施，不是沙箱：工具以你的账户权限运行。 模型只能调用本步展示给它的工具，被拒绝的调用永远不会运行。
智能体和记忆 写入记忆要经过检查器的大小限制。只有配置了嵌入后端并且记忆开启时，才会写入长期记忆。 提示词和存储都不会无限增长。
后端和模型服务器 后端只连接一个地址。localmelo 不负责下载、启动或部署模型。 模型服务器始终由你掌控。

目前已有的功能

  • 直接模式：运行选项、九种运行状态、文本或 JSON 输出，以及固定的退出码。
  • 终端中的交互式界面（单独的 melo，support/cli/）：实时的工具块和旋转指示、审批、带补全的 / 命令、/model 和 /backend；以及简单的对话循环（melo ""）。
  • 四个内置工具，以及本地 MCP 服务器提供的工具（在直接模式和 Python API 中）。
  • Python API（实验性）：运行事件、停止运行、工具调用的审批策略、限制文件工具的工作区根目录，以及可以在多次运行之间延续的对话。
  • 会话（实验性）：保存在 SQLite 中的对话，每一轮只结束一次，重启后仍在，并能在新的智能体上恢复（support/sessions/）；runner 可以让每一轮报告进度事件。交互式界面把它的每一轮保存在会话中；网关目前还没有使用会话。
  • 网关：HTTP API、只在空闲时响应关闭请求的会话、网页工作区、监听回环地址时拒绝其他网站请求的检查，以及 macOS 后台服务。
  • 支持 Ollama、MLC LLM、vLLM、SGLang 和四个云端 API 的后端。
  • 工作记忆、历史记录和长期记忆；开启持久化后会保存到 SQLite，保存的历史记录还包括每次模型调用及其推理，默认保留 30 天；Python API 还可以忘掉一个任务或全部记忆。
  • melo-retrieve：离线比较 bm25、llm 和 embedding 三种记忆检索器。运行目前还不使用这些检索器。
  • 程序记忆：每次运行都会记录自己的步骤，完成的运行还会更新所属任务的步骤模板；开启持久化后写入 procedures.db。Python 调用方传入 progress=True 就能收到 run.progress 事件，目前不带百分比进度条。在终端里，melo "<task>" 会把它们画成 stderr 上的一行进度（support/progress_line.py）。melo-procedures 可以离线重放进度规则。
  • 调度器的策略核心，以及离线测试它的模拟器（support/scheduler/）。运行和网关目前都还不使用它。
