组件

每个组件目前做什么，以及代码在哪里。路径都相对于仓库根目录。

命令行

melo 命令。给出任务时，它以直接模式运行：创建一个智能体，运行这个任务，以文本或一行 JSON 输出结果，并用退出码表示运行是如何结束的。在终端中不带任务时，它打开交互式界面：输入框和状态栏固定在底部，每一轮边运行边输出到终端的滚动区：模型的思考、每个工具调用一个块、重试、通知和反思，答案按 Markdown 输出；输入框上方的实时区域显示步数、阶段、正在运行的工具和本回合的进度事实，会话的第一个回合还会显示上次运行的步骤。界面在会话上运行每一轮（保存在 ~/.cache/localmelo/cli/sessions.db），可以用 melo -c 或 melo -r 恢复工作区中已保存的对话（/sessions 和 /resume 打开同一个选择器），运行 shell_exec、python_exec 和 file_write 之前会在面板中询问，把文件工具限制在工作区内，并把 /model 和 /backend 选择的模型和服务器保存到配置文件（用 --base-url 打开的界面不保存）。它还可以用 /title、/undo、/usage、/memory 和 /copy 命名、撤销、查看和复制对话。没有终端时，单独的 melo 以退出码 2 结束。任务为空字符串（melo ""）时，它打开简单的对话循环，每一轮都能看到之前的回答。--serve 启动网关；--daemon 用来管理 macOS 后台服务。使用 --base-url 时，智能体直接连接该服务器，不读取配置文件；不使用它时，使用配置中的后端。无论是否使用 --base-url，--chat-model 和 --request-timeout 都会设置对话模型和对话请求的超时，并且都不会修改配置文件。

关键文件：__main__.py；交互式界面在 support/cli/ 中：launch.py（终端检查、工作区和模型服务器）、app.py（输入框和按键）、session.py（每一轮和命令）、render.py（思考、通知、反思、工具块、实时区域和答案）和 approvals.py；以及 support/sessions/agents.py。

网关

melo --serve 启动的 HTTP 服务器。它提供 HTTP API（/v1/health、/v1/agent/run、/v1/sessions），最多保留 50 个会话，每个会话都有一个根据配置文件创建的智能体。会话的智能体会保留自己的回答，所以每个请求都能看到之前的回答。每个请求在运行前都要通过检查：任务的长度和会话 ID。

在 /api/ 上，它提供 API v2，也就是网页控制台的 API：health、会话列表和单个会话、会话的回合及其事件、Server-Sent Events 流、图片 blob、提交查询，以及会话的工具、授权、记忆和运行记录；还有运行会话的写入接口——创建会话（可带或不带第一个回合）、开始、重试和停止回合、按 key 取消消息、回答审批、重命名或移动会话，以及删除会话。控制台回合在网关进程中运行，每个会话同一时间只运行一个；它的模型调用和工作区聊天一样经过同一个调度器门。控制台按需打开会话的智能体，并在空闲清扫、打开数量上限或网关重启关闭它之后恢复对话。API v2 只在回环地址上提供，所有响应带统一的错误格式和 Cache-Control: no-store，并且只增不改。详见API v2（英文）。

在 / 上，网页工作区使用控制台的 API v2 和持久会话库。它显示每轮的工作和答案、连接设置、较早的回合、停止或失败状态，并在收到审批请求时显示审批卡片；详情抽屉显示工具、会话授权、记忆和运行记录，设置包括连接测试和浏览器本地主题；控制台会话使用 RememberingPolicy，在 file_write 和 python_exec 前请求审批；旧版 /v1 没有审批策略。每个对话使用配置中的模型和三个内置工具 file_read、file_write、python_exec（没有 shell_exec）。模型调用共享调度器的门，标题栏显示 GPU 锁和电池状态。

页面按最新在前列出会话，支持搜索和每个对话的草稿，显示工具工作、折叠的推理、通知、进度和答案，并从最后保存的事件重开事件流。会话保存在 ~/.cache/localmelo/gateway/sessions.db，重启后仍然保留；智能体按需打开（最多同时 8 个，空闲 15 分钟后关闭但保留对话）。

网关没有身份验证。监听 localhost 或回环地址（例如默认的 127.0.0.1:8401）时，它会拒绝 Host 不是 127.0.0.1、localhost 或 [::1] 加网关端口的请求（HTTP 421），以及其他来源的网页通过浏览器向它的 API 发来的请求（HTTP 403）。任何网页都不能在 frame 里显示网关的页面。监听其他地址（例如 0.0.0.0）时，它不做这些检查，并在启动时记录一条警告。

关键文件：support/gateway/__init__.py、session.py、guard.py（Host 和 Origin 检查）、webapp.py 和 playground.py（旧的 /v1/playground 路由及其背后的对话）、console/（控制台的会话库、API v2 路由和页面的数据）、static/（页面：workspace.js、turns.mjs 和 markdown.mjs），以及用于 macOS 后台服务的 daemon.py。

MCP 服务器

通过 stdio 使用 Model Context Protocol 通信的本地服务器，列在 --mcp-config 指定的 JSON 文件中。第一次运行开始时，support/mcp 会启动每个服务器，列出它的工具，并以 mcp__<server>__<tool> 的名称把这些工具注册到工具注册表和执行器中。MCP 工具可以在直接模式、Python API 和交互式界面中使用（--mcp-config，或配置文件顶层的 mcp_config 键）；网关会话暂时还不能使用。服务器的 require_approval 可以让它的全部工具（或其中列出的工具）在调用前先询问运行的审批策略；没有审批策略的运行（例如直接模式的运行）会直接运行这些工具，不经询问。每个服务器都以与工具子进程相同的最小环境启动，再加上它自己条目里的 env。

关键文件：support/mcp/config.py、client.py、provider.py，以及 melo/contracts/tools.py 中的工具提供方接口。

智能体

运行循环。每一步都会根据任务、工作记忆、召回的长期记忆和最新的反思构建提示词，向模型提供一组工具（默认的 retrieve 模式下包括内置工具、它在这次对话中已经调用过的工具，以及与任务最接近的三个匹配），发送一次规划请求，然后运行回复中的工具调用。如果回复只有文本、没有工具调用，它就是最终答案，运行以 completed 结束。在默认的 reflect 策略下，步骤按尝试分组，每次尝试最多 10 步；一次尝试没有得到答案就结束时，由反思决定是否开始下一次尝试。每次运行都以九种状态之一结束（被停止的交互式运行以 cancelled 结束，见下文），并返回一个 RunResult。模型请求失败时，如果重试可能成功，最多重试两次。

调用 run_task 的 Python 代码可以跟踪和控制一次运行。传入 on_event 时，它会以事件的形式收到每一步、模型的每条回复、每次工具调用、每条通知和每次反思，模型文本中的密钥会被隐去。传入 approval 时，由审批策略决定每个需要审批的工具调用能否运行。带其中任意一个的运行是交互式运行：取消它时，运行以 cancelled 结束，被打断的那一步会被妥善收尾。设置 AgentOptions(record_answers=True) 时，工作记忆会保留每次运行的回答；conversation() 和 load_conversation() 可以把对话带到另一个智能体。直接模式和旧版 /v1 既不传入事件接收函数，也不传入审批策略。网页工作区会传入事件接收函数和审批策略，所以在网页工作区中点 Stop，运行会以 cancelled 结束。

关键文件：melo/agent/agent.py、melo/agent/options.py（AgentOptions）、melo/agent/_chat.py（规划和反思请求、重试）、melo/agent/_events.py 和 melo/contracts/events.py（事件）、melo/contracts/approvals.py（审批策略）、melo/schema.py（RunResult 和各项上限）。

检查器

在一次运行的各个边界进行检查：

  • 规划请求之前：提示词最多 100,000 个字符，本步提供的工具列表必须有效；
  • 规划请求之后：回复中的每个工具调用都要有名称和唯一的 ID；
  • 工具运行之前：由工具的权限级别和模式决定。interactive 界面提供 shell_exec；direct、python 和 gateway 默认不提供它，若仍注册了 exec 工具，除非 direct 或 python 调用方在 builtins 中点名，否则会被拒绝；网关即使点名也会拒绝。带审批策略的运行会在每次权限级别不是 read 的调用前询问，并且不再按命令的写法拒绝任何命令；
  • 工具运行之后：超过 50,000 个字符的输出会被截断；
  • 写入记忆之前：限制写入的大小；
  • 事件交给 Python 代码之前：模型回复文本中常见格式的 API 密钥、bearer 令牌和一次性验证码会被替换为 [redacted]；
  • 在网关中：检查每个请求的任务和会话 ID。

规划请求前后的检查一旦失败，运行就以 failed 结束。被拒绝的工具调用不会运行：模型会把这次拒绝当作工具返回的错误。

关键文件：melo/checker/checker.py、validators.py、payloads.py、redaction.py。

执行器

按顺序运行一步中的工具调用。以下调用会被拒绝：本步没有提供的工具、参数不是 JSON 对象的调用，以及内置工具参数类型不对的调用；剩下的每个调用再交给检查器检查。设置了工作区根目录时，工作区策略接着解析文件工具的路径，并拒绝根目录之外的路径。设置了审批策略时，权限级别不是 read、或被标记为需要审批的工具的调用接着等待审批策略的决定；获准之后，如果设置了工作区根目录，文件路径会被重新解析，路径在等待期间发生了变化的调用会被拒绝。每个工具都有时间限制，从审批之后开始计时：shell_exec 30 秒，file_read 和 file_write 60 秒，MCP 工具使用其服务器的 timeout。在交互式界面中，shell_exec 和 python_exec 的时间限制是 10 分钟。shell 命令的标准输入是 /dev/null，因此它不会读取终端。python_exec 的代码始终在子进程中运行，时间限制或取消会终止它：没有工作区根目录时在当前目录，有根目录时在根目录。shell_exec 或 python_exec 的子进程只拿到 PATH、HOME、USER、LOGNAME、SHELL、TERM、LANG、所有 LC_* 变量和 TMPDIR，外加 AgentOptions(tool_env=…)：除 tool_env 点名之外，melo 环境里的 API 密钥不会到达任何工具，VIRTUAL_ENV、PYTHONPATH、SSH_AUTH_SOCK 和代理变量只能通过 tool_env 传入。拒绝、审批不通过、超时或出错都会作为工具的错误返回。

四个内置工具是 shell_exec、python_exec、file_read 和 file_write。默认只有交互式界面拿到全部四个；直接运行、网关、控制台会话以及库默认的 python 模式只拿到 file_read、file_write 和 python_exec：这些模式不提供 shell_exec（direct 和 python 模式没有审批策略，网关的 /v1 路由也不询问；控制台通过 API v2 询问，但运行在同一个 gateway 模式下，所以同样没有 shell，Python 代码仍然可以启动进程），direct 或 python 调用方用 --builtins all 或点名 shell_exec 才会启用；网关和控制台即使点名也会拒绝。直接运行和 /v1 网关会话不给它们设置工作区根目录，所以文件工具可以访问你能访问的任何文件；直接模式传入 --workspace DIR 时会设置下面 Python API 中的同一个根目录，控制台对话则以 [gateway] workspace（默认 ~/localmelo-workspace）为根目录。在 Python API 中，AgentOptions(workspace_root=…) 会启用 policy.py：文件工具只能访问根目录内的文件；shell_exec 和 python_exec 在根目录中以子进程运行，但不受这个限制。只有带审批策略的运行才会审批。

关键文件：melo/executor/executor.py、builtins.py、policy.py、melo/contracts/approvals.py。

记忆

在 compress 模式下，启发式笔记最多可提取 12 条事实，包括部分英文否定句和中文居住、取消陈述，保留原文。否定陈述只有在记录中完整出现才会匹配来源；事件时间冲突也会拒绝匹配。提取和匹配仍是启发式规则；相近陈述被识别为肯定与否定相反时会作为冲突保留，结构化的更新替代尚未实现。详见推理笔记（英文）。

工作记忆保存一次运行或一个网关会话中的对话：最近 20 条消息，只在内存中。历史记录保存每个任务和每一步；开启持久化后，还保存每次模型调用及其推理。在 legacy 中，长期记忆需要嵌入后端：它把步骤摘要和反思连同嵌入向量一起保存，并在每一步召回最接近的 5 条。在 compress 模式下，长期记忆是带类型的存储：每条记录都有类型（semantic、episodic、profile 或 reflection）、来源、状态和允许它写入的信号，文本和向量旁还有来源信息，每条候选都有对应的决定（NEW、UPDATE、RELATED、CONFLICT 或 IGNORE）；只有排练、用户的请求或陈述，或作用于最终尝试摘要的 --admit-on-outcome on 才能让候选写入。程序记忆保存每次运行的步骤，并学习你反复运行的任务的步骤。历史记录、长期记忆和程序记忆默认留在内存中；开启持久化后，分别写入 history.db、long_term.db 和 procedures.db。新建的文件只有你能读取（权限 0600）。写入历史记录和长期记忆的文字会先脱敏：sk- 密钥、GitHub 令牌、AWS access key id、Bearer 后面的令牌，以及关键词旁边的一次性验证码，与事件和模型调用已有的规则相同；运行、它的请求和模型仍然看到原文。Python API 可以用 Hippo.forget(task_id) 忘掉一个任务的历史记录行和指明该任务的长期记忆反思，用 forget_all() 清空历史记录和长期记忆（包括步骤摘要）。工具注册表保存所有已注册的工具，以及检索模式使用的 BM25 索引。

在 compress 和 compress+replay 推理模式下，每条回复都会变成一条简短的笔记（计划、发现、决定和尚未确定的事项，以及工具返回的内容）和它的代码草稿，保存在对话窗口旁的内存笔记库中；后来的笔记、调用和反思用到它时，笔记会被排练并汇总成该次尝试的摘要。每条笔记、草稿和摘要进入窗口或笔记库之前，都要经过 check_memory_candidate 边界（脱敏、清理、限长）。compress 模式会把这些内容召回：在起始、尝试和步骤，一个带分隔、被标记为数据的块携带本任务的笔记、草稿和思考片段，以及其他任务的长期记忆有效记录，由 --retriever auto|off|bm25|llm|embedding 选择检索器（配置了嵌入服务器时用 embedding，否则在起始和尝试用 llm、在步骤和工具用 bm25，任何失败都回退到 bm25），由 --recall-at 和 --recall-placement 决定位置，并经过检查和长度限制；思考片段只有产生它的回合离开窗口之后才能被召回。history.db 版本 2 会把每个新块记录在 recall_json 中，recall 事件带有命中的内容。详见推理笔记（英文）和循环中的召回（英文）。

melo/memory/retrieval/ 中有三种可切换的检索器：bm25、llm 和 embedding。它们检索由一次运行的模型调用构建的文档：melo/memory/notes.py 从模型回复中提取的推理笔记、代码草稿和思考片段，以及反思。compress 模式在循环中使用它们（见上）；melo-retrieve 命令（support/retrieve.py）在带标注的查询上离线比较这些检索器，并能把以 raw-call JSONL 记录的模型调用导出为语料。开启持久化后，melo 写入的 history.db 也记录每次模型调用，melo-retrieve 同样能导出它。详见离线检索（英文）。

会话（实验性）把整段对话保存在 sessions.db 中：每一轮都是一行记录，只结束一次，带有状态和原因；会话的事件也一起保存；窗口检查点（window checkpoint）让新的智能体从上一个智能体停下的地方继续。用 progress=True 创建的 SessionRunner 会让每一轮运行报告 run.progress 事件，并把这些事件和该轮一起保存。网关的文件和终端的文件是分开的。交互式界面在会话上运行每一轮，并可以用 melo -c 或 melo -r 恢复已保存的对话；网页控制台在网关自己的会话库中运行并读取它的会话，而网关的 /v1 会话仍留在内存中（代码在 support/sessions/ 和 support/gateway/console/）。详见会话（英文）。

直接运行可以用 --save-session 选择保存为单回合 worker 会话，也可以导入 dsh JSONL 日志。网关从 CLI 文件只读查询这些历史，不支持修改或实时跟随。

关键文件：melo/memory/coordinator.py、short/（工作记忆）、history/、long/、tools/（工具注册表）、bm25.py。

记忆设计（计划中）：记忆设计页保留了维护者为记忆撰写的设计，其中部分内容尚未实现。

配置和向导

~/.cache/localmelo/config.toml 记录对话后端、嵌入后端及其设置。在终端中第一次运行时，melo 用 GET /v1/models 查找模型服务器，询问地址和模型并保存：Ollama 服务器保存为 ollama 后端，其他兼容 OpenAI 接口的服务器保存为 vllm。服务器列出嵌入模型时，它会为长期记忆提供一个；嵌入模型指南（英文）覆盖 Ollama、oMLX、vLLM、SGLang 和 MLC。配置向导（melo --reconfigure）会询问所有后端设置，向每个服务器发送测试请求，保存文件，然后打开交互式界面；加上 --serve 时则启动网关。直接模式和网关都根据这个文件创建智能体。

关键文件：support/config.py、support/onboard.py、support/onboard_probe.py、support/backends/discovery.py。

提供方

连接模型服务器的 HTTP 客户端：兼容 OpenAI 的对话接口（/chat/completions）、Ollama 自己的 /api/chat，以及兼容 OpenAI 的嵌入接口。它们实现 melo/contracts/providers.py 中的接口，应用对话请求超时，并把每个失败的请求报告为 ProviderError，同时说明重试是否可能成功。

关键文件：melo/contracts/providers.py、support/providers/llm/、support/providers/embedding/。

后端

每个后端键对应一个适配器：mlc、ollama、vllm 和 sglang 用于你自己运行的服务器，openai、anthropic、gemini 和 nvidia 用于云端 API。每个适配器检查配置文件中属于自己的表，并创建提供方。后端只负责连接：模型服务器由你自己启动和停止。

关键文件：support/backends/registry.py、base.py、local/、cloud/。

melo/sleep/、melo/memory/personalized/ 和 support/melo_serving/ 中的代码，智能体目前还没有使用。melo/memory/retrieval/ 和 melo/memory/notes.py 供循环中的召回和 melo-retrieve 使用；support/scheduler/ 是调度策略核心及其模拟器，网关的门用它来调度网页工作区的聊天和控制台的回合，support/gateway/machine_monitor.py 为工作区读取 GPU 锁和电池。

边界

边界规则意义
melo/ 和 support/ melo/ 包含智能体以及提供方要实现的接口，不在模块级别导入 support/。唯一的桥梁是 Agent(config=…)：调用它时，它通过 support/backends 创建提供方。 智能体可以使用你自己创建的提供方运行（例如测试用的假提供方），新增后端也只需要修改 support/。
智能体和执行器 每一步只能运行本步提供的工具，每个调用都要先通过检查。这些检查只是防护措施，不是沙箱：工具以你的账户权限运行。 模型只能调用本步展示给它的工具，被拒绝的调用永远不会运行。
智能体和记忆 写入记忆要经过检查器的大小限制。只有配置了嵌入后端并且记忆开启时，才会写入长期记忆。 提示词和存储都不会无限增长。
后端和模型服务器 后端只连接一个地址。localmelo 不负责下载、启动或部署模型。 模型服务器始终由你掌控。

目前已有的功能

  • 直接模式：运行选项（包括用 --workspace DIR 指定任务工作的文件夹，以及如何把回复的推理发回或保留：legacy、drop、replay、compress 或 compress+replay）、九种运行状态、文本或 JSON 输出，以及固定的退出码。
  • 可选的上下文统计估算规划和反思请求，并记录服务器报告的输入 token 用量；它不会裁剪请求，也不会强制限制输出预留。
  • 终端中的交互式界面（单独的 melo，support/cli/）：实时的工具块和旋转指示、审批（写文件时显示将要做出的改动）、带补全的 / 命令、/model 和 /backend、/approvals、/status、/mcp 和 /retry、MCP 服务器文件（--mcp-config 或配置文件的 mcp_config）、可以用 melo -c、melo -r、/sessions 和 /resume 恢复的已保存对话，用 /title、/undo、/usage、/memory 和 /copy 命名、撤销、查看和复制对话，以及为整段对话选择推理和召回模式（--reasoning、--reasoning-field、--replay-turns、--note-writer、--retriever、--recall-* 和 --retrieval-extra-body，来自旗标或已保存的默认值）；以及简单的对话循环（melo ""）。
  • 四个内置工具（其中 python_exec 在所有模式下都在子进程中运行；直接运行、Python API 默认的 python 模式、网关会话和控制台会话只拿到三个，没有 shell_exec），以及本地 MCP 服务器提供的工具（在直接模式、Python API 和交互式界面中）。
  • 工具子进程和 MCP 服务器只拿到最小环境（PATH、HOME、USER、LOGNAME、SHELL、TERM、LANG、LC_*、TMPDIR），再加上 AgentOptions(tool_env) 或服务器条目里的 env；配置文件支持的直接运行、界面和控制台会话还会解析 [agent] tool_env 里的名称，其他变量都不继承。
  • 每一步提供内置工具、模型在这次对话中已经调用过的工具，以及与任务最接近的三个匹配（默认的 retrieve 模式）；all 在每一步提供所有工具。
  • Python API（实验性）：运行事件、停止运行、工具调用的审批策略、限制文件工具的工作区根目录，以及可以在多次运行之间延续的对话。
  • 会话（实验性）：保存在 SQLite 中的对话，每一轮只结束一次，重启后仍在，并能在新的智能体上恢复（support/sessions/）；runner 可以让每一轮报告进度事件。交互式界面把它的每一轮保存在会话中，网页控制台在网关自己的会话库中运行并读取会话；/v1 HTTP API 目前还不使用会话。
  • 网关：HTTP API、/api 下控制台的 API v2（health、会话、回合、事件流、blob、提交查询、工具、授权、记忆和运行记录，以及创建会话并开始、重试、停止和审批其回合的写入接口）、只在空闲时响应关闭请求的会话，以及 / 上控制台的实时页面（会话列表、对话的回合和通过 SSE 保存的事件、每个工具调用一张工作卡片、实时进度行、Stop、优先级标签和输入心跳；页面只访问 /api，使用配置的模型）。页面的对话和控制台回合经过调度器的策略（默认 off），标题栏显示 GPU 锁和电池。网关还保留原来的 /v1/playground 路由、监听回环地址时拒绝其他网站请求的检查，以及 macOS 后台服务。
  • 支持 Ollama、MLC LLM、vLLM、SGLang 和四个云端 API 的后端。
  • 工作记忆、历史记录和长期记忆；开启持久化后会保存到 SQLite，compress 模式下长期记忆是带类型的存储，记录带有类型、来源、状态、允许写入的信号和来源信息，每条候选都有对应的决定；保存的文字会先脱敏，保存的历史记录还包括每次模型调用及其推理，默认保留 30 天；Python API 还可以忘掉一个任务或全部记忆。
  • 推理笔记：compress 和 compress+replay 模式会在对话窗口旁的内存笔记库中，为每条回复及其代码草稿保留一条简短的笔记，并把它们排练成该次尝试的摘要（摘要写明这次尝试写过的文件、最后一次检查及其结果、它的决定和最终结果）；compress 模式还会在起始、尝试和步骤召回这些笔记、草稿和思考片段，以及其他任务的长期记忆有效记录（--retriever、--recall-* 和 recall 工具）。
  • melo-retrieve：离线比较 bm25、llm 和 embedding 三种记忆检索器，也可以导出带类型的存储或其决定，并为基准测试给候选文件打分。compress 模式在循环中使用同一组检索器；legacy 运行不使用它们。
  • 程序记忆：每次运行都会记录自己的步骤，完成的运行还会更新所属任务的步骤模板；开启持久化后写入 procedures.db。Python 调用方传入 progress=True 就能收到 run.progress 事件，目前不带百分比进度条。在终端里，melo "<task>" 会把它们画成 stderr 上的一行进度（support/progress_line.py）。melo-procedures 可以离线重放进度规则。
  • 调度器的策略核心，以及离线测试它的模拟器（support/scheduler/），以及网关共用的门（gate）、GPU 锁读取器和电池读取器（support/gateway/chat_gate.py、machine_monitor.py）。页面的对话和控制台会话的回合都经过它；直接运行、melo "" 和 /v1 HTTP API 不经过。
  • 调度器的任务库（网关 sessions.db 中的组件版本 1）：带 P0-P5 的任务、依赖、优先级事件、问题、规则、日志和空闲窗口，与任务的 kind="task" 会话在同一个事务中创建，以 (origin, request_key) 幂等，工作区解析到用户主目录或 [gateway] workspace 下；ChatGate.register_task() 给 worker 一个生命周期。main 上还没有 /api/tasks 路由或 worker 运行。
