开发者说明

为 localmelo 搭建开发环境、运行测试和检查、添加后端、内置工具或检查，并提交改动。

仓库

  • 包含 pyproject.toml 的目录本身就是 localmelo 包；没有 localmelo/localmelo/。
  • melo/agent/agent.py 以 localmelo.melo.agent.agent 导入；克隆目录请保持名为 localmelo。
  • melo/ 是核心：运行循环、检查、执行器、记忆和提供方契约。
  • support/ 是核心之外的部分：后端和模型提供方、网关、终端界面、MCP、配置和配置向导。
  • tests/ 与这两部分一一对应。docs/ 里是 Markdown 页面和网站。

核心不导入 support/。唯一的桥是 Agent(config=...)。

  • tests/test_layering.py 在 melo/ 下发现任何形式（普通、相对或通过 importlib）导入 support/ 时失败。
  • 它允许两处：仅用于类型检查的 Config，以及 _providers_from_config 内部的 get_backend。
  • prompt_toolkit 和 rich 不进入核心和后端；会话和终端界面不依赖网关。
  • 核心需要 support/ 里的代码时，把契约放进 melo/contracts/。

开发环境

你需要 Python 3.11 或更高版本、Git 和 uv；只有控制台的 JavaScript 测试需要 Node（版本见 .nvmrc）。

  • uv 根据 uv.lock 创建 .venv/，使用 .python-version 中的 Python 3.13；localmelo 支持 3.11 或更高版本。
  • --extra dev 加入 pytest、ruff、black、mypy 和 pre-commit；--extra gateway 加入 FastAPI 和 uvicorn。
  • uv run pre-commit install 安装的钩子会在每次提交时运行 ruff、black、mypy 和完整测试。

运行命令行

melo 安装在 .venv/bin/，不在 PATH 上。在克隆目录里通过 uv 运行：

  • 在其他地方，指明克隆目录：uv run --project DIR melo …。
  • 运行需要模型服务器：传入 -u http://127.0.0.1:11434/v1 -m qwen3:8b，或者先运行一次 uv run melo setup。
  • 把 HOME 指向临时文件夹，运行就不会动到你自己的 ~/.cache/localmelo。

代码检查和类型

Black 按 88 列格式化。Ruff 启用 E、W、F、I、N、UP、B 和 SIM；E501 交给 black 处理。Mypy 要求每个函数都有类型标注（disallow_untyped_defs），并检查没有标注的函数体，__main__.py 除外。pre-commit 运行的是同样的三项检查。

添加后端

后端只是连接器：它们校验配置并构建提供方对象，从不启动或部署模型。添加一个后端：

  1. 在 support/backends/local/ 或 support/backends/cloud/ 中写一个实现 BaseBackend 的类（support/backends/base.py）：key、display_name、validate、validate_embedding、has_embedding、build_chat_provider 和 build_embedding_provider。大多数服务器可以共用 support/backends/openai_compat.py 里兼容 OpenAI 的代码。
  2. 在 support/backends/registry.py 的 ensure_defaults_registered() 中注册它。
  3. 把它的 key 加到 support/config.py 的 VALID_CHAT_BACKENDS；如果它提供嵌入，也加到 VALID_EMBEDDING_BACKENDS。
  4. 为它添加配置表：在 Config 上加一个字段，并把名字写进 _LOCAL_SECTIONS 或 _CLOUD_SECTIONS，让 load() 和 save() 能处理它。修改配置结构时，请在 load() 里添加迁移，而不是让已有的配置文件失效。
  5. 把它加到 support/onboard.py 的配置向导中：CHAT_BACKENDS、EMBEDDING_BACKENDS、默认值（_LOCAL_DEFAULTS、_CLOUD_DEFAULTS 或 _EMBEDDING_DEFAULTS）和 _CHAT_SETUP。
  6. 在 tests/backends/ 中添加测试。连接检查要 mock：测试绝不能连接真实服务器。
  7. 写文档：docs/configuration.md（英文）中的后端表和示例。

添加内置工具

一个内置工具由一个 ToolDef（名称、说明、JSON 参数和语义标签）和一个返回文本的异步函数组成。两者都放在 melo/executor/builtins.py 中，_builtin() 装饰器会把它们加入 BUILTINS。melo/executor/__init__.py 里的 register_builtins() 会把每一个都注册到执行器和记忆的工具注册表中，并把权限级别不是 read 的工具标记为需要审批。

  1. 在 melo/executor/builtins.py 中添加 ToolDef 和函数，并用 @_builtin(...) 装饰。语义标签是 BM25 搜索用来匹配任务的词。每个已注册的内置工具在每一步都会提供；在其他提供方工具中，retrieve 模式提供模型已经调用过的工具和与任务最匹配的三个。
  2. 为它指定权限级别：把名字加入 melo/checker/tiers.py 的 BUILTIN_TIERS（read、write、exec 或 network）。有一个测试保证这张表和内置工具名一致，所以新增内置工具必须同时指定级别。运行有审批策略时，级别不是 read 的调用都会先询问；APPROVAL_BUILTINS 由这张表推导得出。
  3. 如果它需要工作区根目录，请把它的受限版本加入同一个文件中的 rooted_builtins()。启动子进程的工具会把子进程的退出状态写入 TOOL_EXIT_CODE，tool.finished 事件因此带有 exit_code。
  4. 在 tests/executor/ 中添加测试。
  5. 写文档：docs/tools.md；智能体需要知道时，也更新 docs/for-agents.md 和 docs/llms.txt。

添加检查

检查器会在每个边界上校验。检查失败是控制流，不是异常：它返回 allowed=False 和一个原因，智能体会重新规划或进行反思。一个有明确数据结构的边界包含三部分和一个调用点：

  1. 在 melo/checker/payloads.py 中添加一个描述输入的数据类。
  2. 在 melo/checker/validators.py 中添加返回 ValidationResult 的校验函数。
  3. 在 melo/checker/checker.py 的 Checker 上添加调用该函数的方法。
  4. 让调用点通过这个方法进行检查。

检查器自身的检查点 pre_plan、post_plan 和 pre_execute 返回的是 CheckResult。现有的边界包括：网关入口、会话状态变化、工具解析、执行器结果、记忆写入、规划提示词以及工具调用的结构。测试加在 tests/checker/ 中，并写明被拒绝的输入和原因。

提交和 pull request

  • 提交信息写成 [Area] Imperative summary，例如 [Agent] Sort the retrieved extra tools by name。常用的领域包括 CLI、Agent、Executor、Memory、Tests、Docs、Gateway、Backends、Sessions 和 Scheduler。
  • pull request 的标题要加类型，例如 [Feature][CLI] … 或 [Bug][Memory] …。
  • 一个 pull request 只做一件事。改动较大时，请先开一个 issue；路线图见路线图 issue。
  • 行为改动需要测试。不要为了让改动通过而削弱或删除已有的测试；如果确实要改测试，请在 pull request 里说明原因。
  • 在同一个 pull request 中更新文档：英文页面、对应的中文版本（README.zh-CN.md 和 docs/zh-CN/）、智能体依赖的行为所对应的 docs/for-agents.md 和 docs/llms.txt，以及 CHANGELOG.md 的 Unreleased 一节：写上 pull request 的编号，如 ([#NN])，并在文件末尾加上对应的链接。
  • 改动终端里 melo 的显示内容或网站时，请在 pull request 中附上截图。
  • 代码、注释、测试和文档一律用英文。

文档和网站

  • GitHub Pages 发布 main 分支的 docs/ 文件夹；网站页面在 docs/en/ 和 docs/zh-CN/ 中。
  • 英文页面和它的中文对应页共用 id、章节、顺序、代码和图片。
  • 网站页面和 README 遵循给人阅读的页面：短要点、先图后文、不写 PR 编号。
  • 图片放在 docs/assets/img/，WebP 格式，宽度不超过 1280 像素。
  • docs/ 中的页面链接到外部文件时使用绝对的 github.com 地址。

新的 Markdown 页面要加进 docs/zh-CN/README.md 的索引；维护文档（英文）说明了结构和术语表。
