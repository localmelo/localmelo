# localmelo for agents

Humans: start at the [README](https://github.com/localmelo/localmelo#readme) or the [website](https://localmelo.github.io/localmelo/).

## What it is

- A local agent: it runs one task with tools (shell, Python, files, MCP) and memory, on a model server the user runs (oMLX, Ollama or any OpenAI-compatible server) or a cloud API. It never downloads, starts or serves models.
- Three surfaces: the `melo` CLI (a fixed exit code per run, and one JSON line with `--output-format json`), the Python `Agent` (experimental), an HTTP gateway on 127.0.0.1.
- Pre-alpha: CLI, HTTP API and Python API may change before v0.1.0.
- An arm64 macOS development app, signed ad hoc, is built and installed for the user with `uv run python scripts/build_macos_app.py --install` (`~/Applications/LocalMelo.app`, replaced only when its bundle id is `org.localmelo.app`; `~/.local/bin/melo` linked only when no other `melo` is on `PATH`; `--uninstall` removes both and nothing else; no admin rights, no developer account; the build's Swift compiler is the `DEVELOPER_DIR` in the environment, else `/Applications/Xcode.app`, else the folder `xcode-select -p` names when it holds `swiftc` (the Command Line Tools), and with none the build stops before any work and prints `The app needs Apple's Swift compiler. Install it with: xcode-select --install`); see [macOS app](guides/macos-app.md). Its page instance check is not authentication; it checks the port owner and the instance before sending any login code, binds the code to that instance, before starting one, attaches to a running gateway (the terminal's): `~/.cache/localmelo/gateway/endpoint.json` parsed by `gatewayEndpoint` in `GatewayPolicy.swift` (host `127.0.0.1`, pid alive, `GET /` with the file's `X-LocalMelo-Gateway` id: `gatewayStart`, `attachConfirmed`), then the same listener-pid and instance checks and one-use codes for that gateway's instance (empty for one a terminal started); Quit leaves an attached gateway running (no dialog; the menu item reads `Quit localmelo (the gateway keeps running)`, `quitTitle`), and when it ends the window says `The gateway it was using has stopped. Only that UI streams. `[cli] status_line = "auto"` (default; no flag) shows the bottom bar's usage and work zones; `"off"` keeps only the run zone and `ctx N` of the last request (see the interactive UI entry for the bar). An invalid `[cli]` value warns and falls back; direct mode and the gateway do not read it. See [provider reference](reference/python-api.md#custom-model-providers).

## Rules (read before running anything)

- Tools run as the user with no sandbox (except confined writes of worker runs and saved tasks on macOS): never on untrusted input or near data the user cannot lose. Pass `--builtins none` (or `--mcp-only`) when no built-in tool is needed. A direct run offers no `shell_exec` by default; `--builtins all` (or naming it) turns it on, and it then runs unapproved.
- Never expose the gateway: non-loopback binds are refused; no reverse proxy or Tailscale Serve. Protected APIs need a bearer or browser session. The token file does not isolate malicious same-UID processes; localhost cookies are not port-isolated. Tools run with the user’s permissions, not in a sandbox.
- Never edit the user's `~/.cache/localmelo/config.toml` or delete `~/.cache/localmelo/` (cleaning `~/.cache` deletes both). For tests or your own backend, run `melo` with a temporary `HOME`.
- No API keys in the config file; `api_key_env` holds the variable's name.
- Never run `--daemon install` in tests. Never run bare `melo` (no task) in a pty or terminal under the user's `HOME`: with no config it asks setup questions and writes `~/.cache/localmelo/config.toml`; it also writes `~/.cache/localmelo/cli/sessions.db`, `cli_history` and `logs/cli.log`. Without a TTY, bare `melo` exits 2 with three stderr lines, and `--serve` with no config exits 1 with one; neither asks anything. `--reconfigure` without a TTY reads the wizard's answers from stdin (EOF: `Setup cancelled.`, exit 0).

## Install

```bash
git clone https://github.com/localmelo/localmelo.git
cd localmelo                 # keep this name: the package is built from this directory
uv sync --extra gateway      # pip: python3 -m venv .venv && . .venv/bin/activate && pip install -e ".[gateway]"
uv run melo --help
```

- `melo` lands in `.venv/bin/`, not on PATH. Below, `melo` means `uv run melo` in the clone, `uv run --project CLONE melo` elsewhere, or `CLONE/.venv/bin/melo` (for background jobs; see Gotchas). Scripts: `uv run [--project CLONE] python SCRIPT.py` or `CLONE/.venv/bin/python SCRIPT.py`. Under a temporary `HOME` prefer the `.venv/bin/` paths: `uv run` keeps its cache in `$HOME/.cache/uv` and may resolve and download again.
- Python >= 3.11; the `gateway` extra (fastapi, uvicorn) is needed for `--serve`. A renamed clone or ZIP folder gives `ModuleNotFoundError: No module named 'localmelo'`.
- Commands: `melo`, `melo-retrieve` and `melo-procedures` (offline only). macOS tested; Linux untested; no Windows.

## Use it

### CLI, one task (best for scripts)

```bash
melo --base-url http://127.0.0.1:8000/v1 --chat-model MODEL \
  --output-format json --timeout 300 --builtins none -- "What is the capital of France?"
echo $?   # 0 completed; 1 crashed (JSON line) or no/invalid config (no JSON line); 2 other status (JSON line) or usage error (no JSON line)
```

- `--base-url` is used verbatim (include `/v1`): no API key, a 120 s chat request timeout unless `--request-timeout`; without `--chat-model` it first asks `GET URL/models` and requests the only chat model (not an `embed`/`rerank` id) or, between several, the one `GET URL/models/status`/`GET <root>/api/ps` report loaded; several and none known loaded (a 401 or no status route, or none or several in memory): stderr `melo: error: URL serves several models and it is not known which one is loaded:` + the list + (after a 401 from the status route) `The server did not say which models are loaded (it needs a key for that).` + `Pass --chat-model <id>.`, exit 2, no chat request (`--brief`: a `startup_error` result with `exit_code` 2 and that text on one line; plain `--output-format json`: no record); a list that cannot be read keeps `default`, with `melo: warning: Could not list the models at URL (REASON); asking for the model 'default'.` on stderr in text output only; with `--chat-model` nothing is listed. The same holds for `--brief` and `melo ""`. The three `[agent]` context-accounting keys still apply. Cloud APIs need the config file.
- oMLX (supported; recommended on Apple silicon, macOS 15+): `omlx serve --model-dir DIR --port 8000` (a port saved in oMLX's settings.json wins when `--port` is left out; each subfolder of DIR with a `config.json` is a model; its folder name, or an alias set in oMLX, is the model id), then `--base-url http://127.0.0.1:8000/v1 --chat-model ID` (without `--chat-model`, melo asks the server for its models: see the previous item). In the config file it is the `vllm` backend, spelled `omlx` (`chat_backend = "omlx"`, `embedding_backend = "omlx"`): it loads as `vllm`, keeps its settings in `[vllm]` and is saved as written. First-run setup, `/backend` and `--reconfigure` save `omlx` when the server's model listing has `owned_by` `omlx`, else `ollama` for a server that answers `GET /api/version`, else `vllm`. `/status`, developer mode's banner and `model.backend_label` say `oMLX` when the file says `omlx` or a model listing has `owned_by` `omlx` (it costs no request), else `OpenAI-compatible server`; a file that says `vllm` is renamed after the first listing. oMLX must accept requests without an API key (no `--api-key`, no key from its admin page or `OMLX_API_KEY`, or "Allow inference without API key" on): localmelo sends none to local servers, and HTTP 401 means a key is set. `GET /v1/models/status` stays behind the key even with "Allow inference without API key" on, so with a key set and several chat models setup has no loaded marks and no default. A model with an alias is listed under the alias and the status reply carries `model_alias` (oMLX 0.7.1rc1), so it is marked `(loaded)` and can be the default under the alias.
- `melo -h` is 23 lines: the everyday options (`-s` reads `most model calls per task (default 30)`) and three commands with what each does (`setup`, `serve`, `console`), then `More commands and every setting: melo -h all`. `melo -h all` (also plain `-h` with `[ui] mode = "developer"` or `--developer`) lists every option, command and setting with its default, and each experimental setting names its deciding issue; `melo COMMAND -h` explains one command. Old spellings are not listed but parse as before in both modes. The tier table is in [Default and developer mode](reference/cli.md#default-and-developer-mode).
- Command words and letters are more names for the options below; an old spelling gives the same result, so scripts need no change. A command word counts only as the first argument and only as an exact match, so quote a task that starts with one (`melo "setup the project"`) or put `--` before it; `melo setup a venv` exits 2 with a hint, with no model call. One command word after options and no `--` (`melo -u URL -m x serve`, `melo -X gateway.port=9000 serve`) exits 2 too, with no model call and nothing on stdout, even with `-o json`: `melo: serve is a command: put it first, as in melo serve.` and `To give melo the task "serve", write melo -- serve.`; after `setup`, `serve` and `console` the example keeps your `-X` settings (`melo serve -X gateway.port=9000`); a longer task, an option value (`melo -w serve "fix it"`) and a task after `--` are unaffected. Old to new: `--reconfigure` = `melo setup`; `--serve [--host H] [--port N] [--enable-playground] [--allow-unconfigured]` = `melo serve [--host H] [-p N] [--playground] [--force]`; `--daemon install|uninstall|status|stop` = `melo serve install|uninstall|status|stop`; `--gateway-login` = `melo console`; `--gateway-rotate-token` = `melo console --reset`; `--brief FILE [--parent-run ID] [--save-session T]` = `melo worker FILE [--parent ID] [--title T]`; `--import-session FORMAT FILE` = `melo import FORMAT FILE`; `--chat-model` = `-m/--model`; `--base-url` = `-u/--url`; `--max-steps` = `-s/--steps`; `--output-format` = `-o/--output`; `--mcp-config` = `--mcp`; `--workspace` = `-w`; `--timeout` = `-t`; `--yolo` = `-y`; `--version` = `-V`; `--save-session T` = `--title T` (with a task). A letter takes its value apart (`-s 5`, `-s=5`). `melo task VERB` runs the `melo-task` client; `melo config` shows the config file and what differs from the defaults. - Settings: `-X KEY=VALUE` (or `--set KEY=VALUE`; repeatable; before `--`) changes one `config.toml` key for one run and never writes the file. - Window eviction: `[agent] window_eviction = "chunk"|"boundary"|"slide"` or `--window-eviction`; default `chunk`. `chunk` drops whole units down to 12 messages, and the prompt-cap fit and the `--context-window` fit down to 70% of their limit, keeping the cut until a request passes the limit; `boundary` is `chunk` plus dropping a finished attempt's turns when the next attempt starts; `slide` (the earlier default) drops one unit per step once the 20-message window is full. - Reflection reading (`reflection_gate` `patient` or `flags`; no option): a reply is read as it stands; when it holds no reflection, one repair of a `{...}` the decoder rejects (the first 8 per reply) is tried: delete the `]` or `}` at the error that no opener matches (`unmatched_closer`), delete a comma before a closer (`trailing_comma`), escape raw newline, carriage return and tab characters inside strings (`control_char`), double the backslash at an `Invalid \escape` error so that `\;` reads as the two characters `\;` (`invalid_escape`), or, when the decoder stopped at the colon after a string inside an array, insert a `]` before the comma that precedes that key (`unclosed_array`). Other modes:

- Attempt digests skip headings in the task line; `verified` requires a passing test runner or a check referencing a previously written file. A failed last check removes verification. Python check labels name a recognized runner and, when safe, a target basename; otherwise they use `python check`. Python tool writes are not inferred as `files`; hidden paths and agent scratch notes are omitted. Check results show counts, exit code or `completed`, not arbitrary output.

- Episodic digest recall prefers the same normalized task; keyless digests are cross-task. `[retrieval]` sets `cross_task_ratio` (1.1), `cross_task_cap` (1), and `cross_task_cold` (0; 1 opts into one cold cross-task digest). General memories bypass this gate. A digest without a checked `files:` or `verified:` line is not admitted. Per-record and run-level same/cross counts cover long-store digests only; `task_notes` counts delivered task-local note-store hits (notes, drafts, thoughts and in-task digests); unscoped long hits count in none of the three, and a block that is not sent does not count. See [digest recall](reference/memory.md#digest-recall).

- Compress-mode heuristic notes extract up to 12 facts from visible replies without a note block, including a bounded set of English negative/cancelled and Chinese residence/cancellation forms, verbatim. Questions and plans are excluded. Negative source attribution requires the full assertion in the record; time conflicts reject matches. This is heuristic and can abstain or miss facts; similar opposing detected polarities are conflicts, not duplicates, but structured polarity-aware supersession is off by default. Self-work frames are filtered unless they carry a keyed content clause; completed outcome-admitted digests are exempt. See [memory](concepts/memory.md#reasoning-notes).
- Experimental Python-only `AgentOptions(typed_assertions=True)` enables narrow evidence-checked same-task assertion updates and labelled historical recall in explicit reasoning modes; default off. Order comes from a timezone-aware record `timestamp`/`date` or per-task user message and sentence position (a restart does not link earlier user statements); only exact normalized duplicates stay ignored, different near-duplicates are kept, and recall order uses wall-clock time. Unlinked facts are not treated as the same entity; recall is relevance-limited. See [typed assertions](reference/memory.md#experimental-typed-assertions).

With options omitted it reads configured agent/retrieval defaults; explicit options win. It sets `replay_scope="window"` and retains the surface's tool mode; only legacy without hooks keeps the original config construction path. See [sessions.md](reference/sessions.md).

### HTTP gateway

The gateway reads only `~/.cache/localmelo/config.toml`. For your own backend or a test, give it a temporary `HOME` with its own file (here for any OpenAI-compatible server):

```bash
T=$(mktemp -d); mkdir -p "$T/.cache/localmelo"
cat > "$T/.cache/localmelo/config.toml" <<'EOF'
chat_backend = "vllm"
embedding_backend = "none"

[vllm]
chat_url = "http://127.0.0.1:8000/v1"
chat_model = "MODEL"
EOF
PORT=18401   # a free port that is not the user's gateway port (default 8401)
lsof -nP -iTCP:$PORT -sTCP:LISTEN >/dev/null && { echo "port $PORT taken" >&2; exit 1; }   # run as a script
HOME=$T CLONE/.venv/bin/melo --serve --port $PORT > "$T/gateway.log" 2>&1 & GW=$!   # blocks until stopped

  -d '{"query": "What is the capital of France?"}'

kill -TERM $GW; wait $GW   # exit 143 once runs in flight end; SIGKILL after your own deadline

Unsaved parks retry with the fence closed, then interrupt with a card; while finalization cannot be stored, resume and stop return 503. ## Output and results

The CLI example's JSON line (field order fixed; `RunResult.to_dict()` is the same without `localmelo_version`):

```json
{"task_id": "ee8befecca3b4fd4bae6499fa0c73704", "status": "completed", "result": "Paris is the capital of France.", "error": "", "steps": 1, "attempts": 1, "n_llm": 1, "n_main": 0, "n_aux": 1, "n_tool": 0, "llm_errors": 0, "usage": {"prompt_tokens": 120, "completion_tokens": 12, "total_tokens": 132}, "duration_s": 0.015203958842903376, "config": {"max_steps": 30, ..., "tools": []}, "localmelo_version": "<git describe or version>"}

- `n_llm` requests answered, `llm_errors` failed attempts (sum = requests sent), `n_main` with tools offered, `n_aux` without (reflections and recall's retrieve requests included), `n_tool` tool calls (refused included). `config`: the `AgentOptions` fields except `workspace_root`, `record_answers`, `tool_timeout_s`, `tool_env` and `replay_scope` (`memory_dir` as resolved, `builtins` as registered), and `tools`, every registered tool's name (not only those a step offered). A `legacy` line has none of them and is byte-identical to before. `localmelo_version`: `git describe` of the checkout, else the installed version, else `unknown`.
- Text mode: `result` on stdout (tool writes to fd 1 go to stderr); a non-completed run adds `melo: run ended with status STATUS: ERROR` on stderr and may still print a best-effort result.
- Statuses, exit 2 unless noted:
  - `completed` (exit 0). `timeout`: `Timed out after N s`. `budget_exhausted`: `Max steps reached` or `Max attempts reached`.
  - `failed`: a check refused, or 2 empty replies in a row (an empty reply has no tool call and no letter or digit in any script, so `...` is one; error `empty replies`, or `melo did not finish an answer` when one was only unfinished thinking). `gate_stopped`: the reflection stopped the run with budget left; the `reflection` event's `stop_reason` says which check (`action_not_continue`, `not_feasible`, `not_concrete`, `not_novel`, `utility_below_threshold`), `flags` holds the decision's three booleans, and `gate` the gate in force (a blank rationale's error ends `(stop reason: <code>)`). `stuck` (`--attempt-policy none` only): the same calls or errors repeated.
  - `provider_error`: a chat request still failed after its retries (network errors, timeouts and HTTP 429/502/503/504 are retried twice, after 1 s, then 4 s more), or an embedding request failed (never retried). `setup_error`: an MCP server or tool provider failed to start (permanent for that `Agent`), or a worker inbox could not be read safely (plain message, no traceback; the next run with a readable inbox proceeds).
  - `crashed` (exit 1, or the signal's code below): an unexpected exception or a signal (`Cancelled by SIGTERM` or `Cancelled by SIGHUP`; SIGINT records `CancelledError` and prints a traceback on stderr). `cancelled`: Python runs only.
- Exit 4: a `--brief` run ended `completed` with `tests.state` `failed` (a check failed or was refused); never without a `Check:` line.
- Other exit codes (no JSON line): 2 usage error, bad `--mcp-config`, `--memory-dir` or `LOCALMELO_THINKING_RETENTION_DAYS`; 1 no backend, invalid config or TOML, unset cloud key variable, the wizard needed without a TTY; 3 gateway port in use; 143, 129, 130 for SIGTERM, SIGHUP, SIGINT (the task record is saved as `crashed`); bare `melo`: 2 no TTY, `TERM=dumb` or `--workspace` not a directory, 1 its session file, agent start or log folder failed.

## Configuration

- File: `~/.cache/localmelo/config.toml`, fixed (no flag or env var; set `HOME` to isolate). Missing file = not configured.
- Top level, before any `[table]`: `chat_backend` (`mlc`, `ollama`, `vllm`, `sglang`, `openai`, `anthropic`, `gemini`, `nvidia`) and `embedding_backend` (`mlc`, `ollama`, `vllm`, `sglang`, `none`), both required (`omlx` is accepted in either, as `vllm`); optional `request_timeout_s` (unquoted number > 0).
- Local table (`[mlc]`, `[ollama]`, `[vllm]`, `[sglang]`): `chat_url`, `chat_model`, `embedding_url`, `embedding_model`, `extra_body` (a table merged into every chat request), and the reasoning keys `reasoning_field` (`""`, `auto`, `reasoning_content` or `reasoning`; `[ollama]` takes `""`, `auto` or `thinking` instead) and `requires_reasoning_replay` (`false`). `mlc`, `vllm`, `sglang` add a missing `/v1`; `ollama` chat uses native `/api/chat`. `vllm` fits any OpenAI-compatible server, oMLX included.
- Cloud table (`[openai]`, `[anthropic]`, `[gemini]`, `[nvidia]`): `api_key_env` (the NAME of the env var holding the key; export it where `melo` runs), `chat_model`, `base_url` (used as given), `extra_body`, and the same two reasoning keys. No cloud embeddings.
- `[agent]`: `reasoning` (`legacy`, `drop`, `replay`, `compress` or `compress+replay`), `replay_turns` (an int >= 1, or omit), `note_writer` (`auto` or `heuristic`; omit for `auto`) and `tool_env` (extra inherited names, default `[]`). Direct/UI explicit flags win; console sessions honor the saved mode, defaulting to `legacy`; `/v1` remains unchanged. A `--base-url` run/session ignores these defaults.
- `[agent] tool_env = ["SSH_AUTH_SOCK", "HTTPS_PROXY"]`: portable ASCII names only (`[A-Za-z_][A-Za-z0-9_]*`), no assignments; missing variables skipped. Resolve present values for shell/Python children, save names only, omit values from run config; no MCP env change. These grant SSH-agent access or expose proxy credentials; tools can print/transmit received values. Never add names without the user's need/approval. API callers may pass an explicit mapping instead.

- `[gateway]`: `host` (`127.0.0.1`), `port` (`8401`), `workspace` (`""`, default `~/localmelo-workspace` in the console; written only when set). A configured workspace must be absolute or `~/` and must not resolve to `/` or home. `--host` and `--port` override them for one run. `config.save()` writes via a temporary file and `os.replace`.
- `[scheduler]`: `policy` (`off`, `fcfs` or `class`; default `off`), `n_srv` (`8`), `r_f` (`1`; forced to 0 when `n_srv <= 2`), `n_fg` (`1`), `focus_s` (`10`; a number above 0), `call_log` (`true`), `call_log_dir` (`""`, meaning `~/.cache/localmelo/scheduler`), `gpu_lock_file` (`""`; a path to the shared GPU lock, empty means no lock reader), `lock_self` (`""`; exact holder or `holder:run`), `lock_gate` (`record` or `wait`; default `record`). ## Tools and MCP

- `shell_exec(command)`: stdin `/dev/null`; env = `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TERM`, `LANG`, every `LC_*`, `TMPDIR` plus `AgentOptions.tool_env` (nothing else is inherited); process group killed after 30 s. Not offered by default in `direct`, `python` or `gateway` mode; `--builtins all`, `--builtins shell_exec` or `AgentOptions(builtins={"shell_exec"})` names it in `direct` or `python` mode, and it then runs (an approval policy, if the run has one, still asks). `gateway` refuses it even when named. The interactive UI offers it and asks.
- `python_exec(code)`: a child Python (`sys.executable -c`, a fixed wrapper) with the same env as `shell_exec`, the code on stdin (a pipe; fd 0 is then `/dev/null`, so `input()` gets EOF, and the code is not in argv), in the current directory (or the workspace root); its process group is killed at the tool's limit (60 s by default) or on cancellation; `sys.exit()` ends only the child; a non-zero exit fails with `Python exited with code <n>`, then the last 4,000 characters of its output.
- `list_files(path=".", depth=1)`: the entries of one folder, folders first (`name/`), then files with sizes (`name  1.5 KB`); a symlink is `name@` and never entered; `depth` 1-3; 200 entries, then `... and N more`; `.git` skipped; no file is read; tier `read`, so it never asks. Offered by `interactive` and `gateway`; not by `direct`, `python`, `--brief` or task workers (`--builtins` names it). With a root, `path` is fenced as `file_read`'s is, and none lists the root; without one it lists the process folder or any path given.
- `file_read(path)`: any file the user can read. `file_write(path, content)`: creates or replaces any file the user can write; in a direct run with `--workspace` and in the interactive UI, only inside the workspace.
- A Python run with an approval policy, and the interactive UI (bare `melo`, unless `--yolo`), gate every built-in tool whose permission tier is not `read` (`write`, `exec`, `network`); a Python run also gates a provided tool by its tier. Any tool explicitly marked is asked about too. Direct mode, `melo ""` and legacy `/v1` have no policy; console/workspace sessions use `RememberingPolicy`. Under a policy each `shell_exec`/`python_exec`/`file_write` call is first reviewed by fixed rules (`Checker.review_action`, `localmelo.melo.checker.review`; shlex/ast, nothing runs) into `ApprovalRequest.review` (`ActionReview`: `verdict` `routine`|`high`|`undecided`, `categories`, `reasons`, `paths`). ## Memory

- Working memory: the last 64 messages (20 on a cloud vendor's backend), in RAM. History (task and step records) and long-term memory: RAM unless persisted.
- Persistence: `--memory-dir DIR` or `AgentOptions(memory_dir=DIR)` wins, else `LOCALMELO_PERSIST_MEMORY`. Files: `history.db` always (tasks and steps with their texts redacted: query, result, thought, tool arguments, tool output and error; and in table `llm_calls` every model reply with its redacted reasoning, kind `plan`, `reflect`, `retrieve` or `estimate`, usage and the steps it made; a planning call's `recall_json` holds the recall records it first carried, and `user_version` is 2), `long_term.db` in `legacy` only with an embedding provider and memory on (the explicit reasoning modes create it whenever persistence is on and memory is on), `procedures.db` always (procedural memory: each run's step counts and tool-call labels, added after `run.finished`, a few ms, at most 2 s, skipped after SIGTERM; without persistence it stays in RAM). A directory localmelo creates is `0700`, a new `history.db`, `long_term.db` or `procedures.db` `0600`; an existing file keeps its mode. Export a run's calls: `melo-retrieve --export-run MEMORY_DIR`; procedural memory: `melo-procedures export --memory-dir DIR`.
- Long-term memory needs an embedding backend (setup: `docs/embedding.md`) in `legacy`; the explicit reasoning modes (`compress`, `compress+replay`, `drop`, `replay`) add a text-only store with persistence on and memory on. A new `Agent` or `melo` process recalls earlier runs only through it; history is written but never read back into a run.

Workers (`kind="worker"`) get no memory; `TaskWorkers` runners pass `index_only=True`. **Managing it (the Memory tab, `/memory`, `melo memory`):** `ChatMemory.edit_record(id, text)` rewords a note in place (`SqliteLongTerm.edit_entry`: `text`, vector, `provenance.quote` = the new text, `provenance.edited`, `edited_at`; an `EDIT` decision row; old text overwritten, decision text/sha blanked, WAL checkpointed; empty, over 300 chars or `sensitive()` raises `ValueError`); `delete_entry(id)` (no restore) also deletes the superseded older wordings it replaced and checkpoints the WAL; `forget_all()` empties `records.db` and `index.db` and stamps `meta.forgotten_at` in `index.db` so `reindex(store)` skips turns that ended before it; `forget_chat_notes(session_id)`; `reindex(store)` clears and rebuilds `index.db` from the session store (completed, not undone, answered turns; 16 per embedding batch) and re-embeds notes whose `embed_model` differs from the model now set. A note outlives its chat: `ConsoleSessions.delete(id, forget_notes=False)` / `DELETE /api/sessions/{id}?notes=forget`. API: `GET /api/memory/records[?session_id=]` (rows add `from`, `chat_gone`, `edited`; top level `documents`, `embedding_model`, `last_error`), `PATCH /api/memory/records/{id}` `{text}` (400 with the reason, 404), `DELETE /api/memory/records?all=true` (`{notes, turns}`; 400 without the flag), `PUT /api/memory` `{on}` (saves `[memory] across_chats`), `POST /api/memory/reindex`; `GET /api/models` adds `embedding_models` and `suggested_embedding`, `GET/PUT /api/settings` carry `across_chats`. `melo memory list [-n N] | forget [ID] [-y] | status | reindex` (`support/memory_cli.py`; `forget` asks with `onboard._ask_choice`: a list on a TTY with keep first, a typed number when piped, Esc/EOF keep; `reindex` exits 1 while the gateway owns `gateway/sessions.db`); terminal `/memory` is a `NotePicker` then `Back|Edit it|Delete it` (`support/cli/memory_notes.py`), `/memory window` is the old working-window view. The first-run and `melo setup` embedding question is `Remember across chats with MODEL?` (`Yes, with it`, `No, by words only`).
- R6-lite's typed store: `long_term.db` `user_version` 1, columns `kind`, `source`, `status`, `admitted_by`, `supersedes`, `links_json`, `provenance_json`, `task_id`, `session_id`, `uses`, `created_at`, `last_used_at`, `embed_model`, `embed_dim`, and table `decisions`. A candidate is written only on `rehearsal`, `user_request` (which also admits the fact a remember request carries after its marker, as `semantic`, or `profile` when first-person), `user_statement`, `outcome` (`--admit-on-outcome on`) or the reserved `sleep`; one of `NEW`, `UPDATE`, `RELATED`, `CONFLICT`, `IGNORE` per decision. Every stored text, provenance included, passes `redact_secrets`; `--keep-decision-text` keeps a decision's text (the hash is always kept). `session_id` is `""` in direct mode.
- Read/score the store without a model: `melo-retrieve --export-store DIR|FILE` (active entries; `text`, `provenance.source_ids`; a directory with no `long_term.db` prints zero and exits 0), `--export-decisions DIR|FILE` (seq order; `text` null unless kept; same empty-directory rule), `--route CANDIDATES.jsonl --memory-dir DIR` (one action line per input; an optional `task_key` string is stored in the digest's provenance; `REFUSED` on a boundary or admission refusal; the scratch directory must be explicit and never the user's). See `docs/retrieval.md`.
- Multi-turn chat: one `Agent` with `record_answers=True` (without it, later runs see earlier queries but not answers), or one gateway `session_id`. A run with no answer leaves `INTERRUPT_LABEL` (`cancelled`) or `NO_ANSWER_LABEL` (any other status) in the window and in the saved turn, which people read; a request carries `UNANSWERED_NOTE` as a user message in its place (`Chat._send`), joined to the user messages beside it, because a model copies an assistant message that says it gave no answer.
- Sessions: used by the interactive UI (`~/.cache/localmelo/cli/sessions.db`, every turn with its tool calls and output; your messages also in `cli_history`); Python API experimental (`~/.cache/localmelo/gateway/` by default otherwise). Plain text, files `0600`.
- Delete memory with the Python API: `await agent.hippo.forget(task_id)` removes the task's `tasks`, `steps` and `llm_calls` rows, its typed long entries and its decisions; `forget_all()` removes both stores, step summaries included. No command yet. Sessions (`~/.cache/localmelo/cli/sessions.db`, `~/.cache/localmelo/gateway/sessions.db`), procedures and the web workspace's files (`~/.cache/localmelo/playground/`) go only by deleting them with localmelo stopped. Not encrypted. One gateway's sessions share one set of files.

## Gotchas

- Exit 1 and exit 2 can come with no JSON line (setup or usage error, message on stderr). Check that stdout is non-empty before parsing, then read `status`.
- Always set `--timeout` (or `timeout_s`): the request timeout counts per read, so a server that keeps sending bytes never trips it, and a silent server costs about 3 x the request timeout + 5 s per request (two retries).
- `--serve` silently ignores a positional task; direct mode silently ignores `--host`, `--port`, `--reconfigure`.
- A `session_id` that is not a string, or that does not match `^[a-zA-Z0-9_-]{1,64}$`, gets the 400 `Invalid session_id format`; omit it or send `null` for a new session.
- One `Agent` per concurrent task: `run_task` has no overlap guard (runs share working memory and counters).
- `ollama` backend: `result` can start with a `<think>...</think>` block.
- A reply that starts (after whitespace, any letter case) with a closed `<thinking>...</thinking>` block has that block as its thinking, as a `<think>` block does (`split_thinking`, the stream filter with no hint or the hint `explicit`, `has_think_block`); a `<thinking>` later in the text, or never closed, stays text, and `[cli.reasoning_tags]` `none` keeps the tags literal. A planning reply whose text has no letter or digit in any script (`...`, dashes, emoji) is an empty reply: the model is asked once more (`has_content` in `localmelo.melo.schema`).
- Unfinished thinking: a planning reply with no tool call is unfinished when its content opens `<think>` and never closes it (unless the model's `[cli.reasoning_tags]` is `none`), it has no answer once thinking is set aside and the provider counted `reasoning_tokens`, a streamed reply's content repeats its reasoning word for word, or it has no thinking and no `</think>` while the model's framing ends thinking with a mark (`closing_only` declared by the interactive UI, or `field`: an earlier reply of this provider had reasoning in its own field and this one's usage reports `reasoning_tokens` 0). Its `assistant.message` has all the text as `thinking` and `content` `""`; it counts as an empty reply with a `notice` of kind `unfinished_answer` (`detail` `{}`) and one more planning request; a row of 2 replies without an answer that held one ends `failed` with the error `melo did not finish an answer` (constant `UNFINISHED_ANSWER_ERROR` in `localmelo.melo.schema`), `result` `""`. The text is never `result`, `last_text` or a best effort. Terminal: dim notice, the reply as thinking (`✻ Thought`), end line `melo did not finish an answer.` + `/retry, or try another model.`; console: folded thinking, failure card title `melo did not finish an answer`, filled **Try again**. With thinking off (the provider's request carries `chat_template_kwargs.enable_thinking` false, or `think` false for Ollama; `BaseLLMProvider.thinking_off`) the last two rules do not apply, and a reply with no tool call and no answer text whose reasoning field holds words, with no `reasoning_tokens` counted, takes those words as its `content` (`thinking` `""`), whole or streamed (`melo.schema.answer_from_thinking`, applied in `Chat._send`); counted reasoning tokens, or a `<think>` never closed, still make a reply unfinished.
- Gateway: `python_exec` runs in a child process, so the gateway keeps answering while the code runs, and Stop kills it. `DELETE` on a session running a task: 409 `{"error", "session_id", "code": "session_busy"}`, and the run goes on; `/v1/agent` has no cancel route (the web workspace's cancel is for its own chats). At shutdown every session is closed, a busy one included, and a task still running then ends as `crashed`.
- Stopping: `&` jobs from a non-interactive shell ignore SIGINT; send SIGTERM. Direct mode exits 143 within 8 s. The gateway waits up to 3 seconds for runs in flight, cancels a longer one (its client gets a 500 and the run ends `crashed`), and exits 143.
- Under `uv run`, `$!` is uv: SIGTERM reaches melo, SIGKILL does not (the gateway keeps listening). In scripts start `.venv/bin/melo`, or SIGKILL the child (`pkill -KILL -f 'melo --serve --port PORT'`).
- `--daemon install` takes `--port` but not `--host`, gets no shell env vars (no cloud keys), and its KeepAlive restarts a killed gateway: use `--daemon uninstall`.

## Status of features

- Available: direct mode, the gateway, the interactive UI (bare `melo` in a terminal, with first-run setup, live tool blocks, thinking excerpts, notices, diffs, approvals, `/model`, `/backend`, `-c`/`-r`, `/sessions`, `/resume`, `/title`, `/undo`, `/usage`, `/memory`, `/copy`, MCP servers from `--mcp-config` or `mcp_config`), the `melo ""` loop, MCP stdio servers (the interactive UI, direct mode, the Python API), the macOS background service, and the gateway console's session store (`gateway/sessions.db`), which API v2 runs and reads.
- Experimental: the Python API. Offline only (runs do not use them): `melo-retrieve` and its `bm25`, `llm`, `embedding` retrievers; `melo-procedures` (`episodes`, `replay`, `export`, `forget`: replays the progress rules on recorded runs; every run itself writes procedural memory at its end). The scheduler core in `support/scheduler/` gates the gateway's web-workspace chats and a console session's turns; direct runs and the interactive CLI do not read it. Sessions (`support/sessions/`): used by the interactive UI (`cli/sessions.db`) and the gateway console (`gateway/sessions.db`, writer `gateway`), and by the experimental Python API; direct mode and the legacy `/v1/agent/run` do not use them.
- Planned, not on main: the interactive UI's `!` shell mode and image attachments; more workspace controls; several tasks on one model server, the user's conversation first; a percent bar, off until repeated runs pass the replay.

## Working on the code

- The directory that holds `pyproject.toml` IS the package `localmelo` (`package-dir`: `localmelo = "."`): `melo/agent/agent.py` imports as `localmelo.melo.agent.agent`. Keep the clone named `localmelo`; never create `localmelo/localmelo/`.
- `melo/` is the core (run loop, checks, executor, memory, contracts); `support/` holds backends, providers, gateway, MCP, config, wizard, `melo-retrieve`, `melo-procedures`, scheduler. `melo/` does not import `support/` (exceptions: `tests/test_layering.py`).
- Setup: `uv sync --extra dev --extra gateway`. Tests while working: `uv run pytest --testmon -q` (after its first run, only tests that cover the changed files run). Before a pull request: `uv run pytest -n auto -q` (the offline suite in parallel). A plain run opens no socket: `tests/smoke/test_backend_smoke.py` is skipped unless `LOCALMELO_SMOKE=1`, and `--ignore=tests/smoke/test_backend_smoke.py` still works; pre-commit hooks run it too.
- Lint: `uv run ruff check .`, `uv run black --check .`, `uv run mypy .`. Web workspace JS (Node from `.nvmrc`): `node --test tests/gateway/*.mjs`.
- Commits `[Area] Imperative summary`; PR titles add the type (`[Feature][Agent] ...`). Tests and docs (with `README.zh-CN.md`, `docs/zh-CN/`) in the same PR, in English ([CONTRIBUTING.md](https://github.com/localmelo/localmelo/blob/main/CONTRIBUTING.md)). The full developer guide is the website's [developers page](https://localmelo.github.io/localmelo/en/developers.html): the repository layout, setup, tests, adding a backend, a built-in tool or a check, commits and pull requests, and the docs and website layout.
- Website pages people read (`docs/en/*.html` and `docs/zh-CN/*.html`; rules in `docs/STYLE.md`, "Pages people read"): the roadmap board is the same markup on `index.html` and `updates.html` (`.board` with Now, Next and Later columns, then a `.board-done` strip; a card is a title, one line and a chip `building`, `testing` or `done`, none for work not started); the home page's feature cards are `.show-card` links with a picture from `docs/assets/img/`; the architecture page draws two diagrams as HTML boxes (`#dia-overview`, `#dia-around`) with connectors from the `DIAGRAMS` table in the page's script.
